# ADR-006：通用设备核心与制冰机能力迁移

## 状态

Proposed

## 背景

当前 `device` 实现以制冰机和 DMS 接口为中心，包含设备号、制冰机命令、冰量规格、设备订单和 DMS 路径。后续需要支持多种设备类型，因此需要先抽取通用设备规范，再将制冰机迁移为独立能力模块。

## 决策

将设备模块拆分为：

1. `device-core`：定义设备号、设备类型、租户归属、连接状态、可用/占用状态和通用设备操作订单。
2. `device-ice`：定义制冰机命令、冰量规格、DMS/MQTT 适配和制冰机订单扩展。
3. 旧 `device-api/biz`：迁移期保留兼容外观，不再承载新的具体设备业务。

设备连接状态与可用/占用状态分开建模，允许设备同时在线且占用。通用设备订单只表达设备操作履约，不替代商城支付订单。

本期不新增独立设备绑定/解绑概念；现有设备归属关系继续沿用，未来出现明确的多归属和位置关系需求时再单独设计。

## 取舍

### 采用通用核心 + 能力模块

优点：设备规范、状态和订单生命周期可以复用；制冰机专属字段不会继续污染通用核心；未来增加能力时有明确扩展边界。

代价：需要拆分当前制冰机聚合服务，并增加旧接口、旧数据和 DMS 链路回归测试。

### 通用设备订单暂留在 device-core

设备操作订单与商城支付订单的生命周期不同，暂时放在 device-core 可以减少模块耦合。若未来需要独立计价、支付、退款或财务结算，再拆为商城商业订单和设备履约子订单。

## 影响

- 旧制冰机 API 保留兼容，内部转发到 `device-ice`。
- `ProductSpecEnum`、制冰机命令映射和固定 DMS 路径移出通用核心。
- 订单模块只通过 `device-core-api` 或 `device-ice-api` 调用设备能力，不依赖具体 `-biz`。
- 本期不修改 DMS 服务、MQTT 主题、硬件协议或前端页面。

## 不在本 ADR 范围内

- 其他设备类型的具体能力实现。
- 设备批量导入、独立绑定关系和设备共享。
- 通用设备订单长期归属 device 还是 order 的最终决策。
