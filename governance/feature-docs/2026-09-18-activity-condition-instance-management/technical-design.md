# 活动报名条件实例管理技术设计

## 模块影响

- `backend/yshop-module-activity`：增加条件实例表、管理端 CRUD、模板引用校验、条件类型参数元数据和实例解析。
- `admin`：报名条件管理页从“注册类型说明”改为“条件实例 CRUD”；活动模板选择条件实例。
- `governance`：新增管理端 API、数据库和权限契约。
- 外部订单商城：继续使用现有受控客户端；本功能不新增外部系统依赖。

## 关键决策与权衡

1. **类型与实例分离**：`ActivityCondition` 仍是代码注册的执行策略，保证参数校验和业务语义在后端；`ActivityConditionInstance` 是租户可管理的数据，保存名称、说明和配置。这样可以创建 `1天内下单`、`7天内下单` 等多个实例而不复制处理器。
2. **实例单独建表**：不把实例混入现有 `yshop_activity_condition` 类型说明表，避免把“租户对类型的说明覆盖”和“可被模板引用的业务配置”混为一体，也便于引用计数和删除校验。
3. **模板保存实例引用，期次保存执行快照**：模板条件项保存 `conditionId`，生成期次时解析当前实例并将 `type/config/name/description/version` 写入期次快照。实例后续修改只影响新生成期次，不回溯历史快照。
4. **删除只检查模板引用**：删除实例前查询当前租户所有模板 JSON 条件配置；不查询期次快照和报名记录，符合已确认的业务规则。删除与模板保存使用事务/行状态校验，避免并发绕过。
5. **启停与引用解耦**：停用实例不自动修改模板；新模板不可选停用实例，已引用模板仍可回显。生成期次和模板保存是否允许使用停用实例统一拒绝，提示重新启用或替换实例，避免产生不可执行快照。
6. **参数表单由类型元数据驱动**：类型 API 返回 `configSchema`；前端只渲染受支持的字段类型，最终以处理器 `validate(config)` 为准，不接受脚本、表达式或任意类名。

## 必要流程

### 查询条件实例

管理端按租户分页查询实例，并关联注册表元数据补充类型名称、类别、版本、可用状态和参数摘要。注册类型不存在的实例显示为不可用，不能被新模板选择。

### 新增/编辑实例

1. 管理端加载已注册类型及其 `configSchema`。
2. 提交实例名称、说明、类型、配置、排序和启用状态。
3. 后端验证名称唯一性、类型存在且可用、配置为 JSON object，并调用处理器 `validate(config)`。
4. 编辑时禁止修改 `conditionType`；更新实例配置不更新已生成期次快照。

### 删除实例

1. 按当前租户和实例 ID 加锁读取实例。
2. 扫描当前租户活动模板的 `condition_config`，判断是否有条件项引用该 ID。
3. 有引用时返回业务错误 `CONDITION_INSTANCE_IN_USE`；无引用时执行逻辑删除。
4. 删除接口重复调用时返回 `CONDITION_INSTANCE_NOT_EXISTS`，不影响其他租户或实例。

### 活动模板保存与期次生成

- 模板条件项提交实例 ID和排序；后端读取实例，将实例的类型与配置解析到模板执行配置中。
- 同一模板不得重复引用同一实例；实例类型相同但实例 ID不同允许同时引用。
- 生成期次时复制实例的执行信息和展示信息到 `condition_snapshot`；报名只读取期次快照，不查询当前实例。

## 风险与控制

- **JSON 扫描删除引用成本**：当前模板条件存储为 JSON，删除校验需要按租户扫描模板。实现先复用现有结构并限制查询范围；后续若数据量达到阈值，再增加模板条件引用表或规范化字段。
- **处理器下线**：实例记录保留但标记不可用；不能新增、编辑为不可用类型或生成新期次。历史期次仍按已冻结处理器版本的快照语义执行，部署下线策略需在发布前确认。
- **停用实例引用**：模板编辑需要显示“已停用”状态，避免管理员误以为实例可继续使用；保存/生成时明确阻断并提供替换路径。
- **租户隔离**：所有实例查询、唯一性校验、引用扫描和删除均显式限定 `tenant_id`。
