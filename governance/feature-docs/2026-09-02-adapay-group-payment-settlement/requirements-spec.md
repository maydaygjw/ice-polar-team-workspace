# AdaPay 拼单多支付单结算规格

## Scope

本功能解决一个业务订单由多个付款人分别使用 AdaPay 支付后，分账确认、订单结算管理和日终对账仍按单支付单处理的问题。

范围包括：

- 每个已支付 AdaPay 支付对象独立完成分账确认。
- 将订单级分账金额可靠拆分到各支付对象，金额合计保持一致。
- 订单结算管理展示订单级汇总及支付单级明细。
- 日终对账按 `payment_id + confirm_id` 核对支付、确认分账和收款主体金额。
- 失败、处理中、重试、回退和退款场景的状态一致性与幂等处理。

不包括：

- 改变现有拼单支付发起、拼单成团或支付回调规则。
- 改变 AdaPay 外部接口语义。
- 历史已成功分账记录的自动重算或自动补账。

## Use Cases

### UC-1：拼单订单完成结算

订单总额 0.40，由两个付款对象各支付 0.20。订单计费结果为商家 0.28、平台 0.12。系统应针对两个 `payment_id` 分别发起 0.20 的确认分账，每个支付对象的主体明细合计为 0.20，最终订单累计分账为 0.40。

### UC-2：单笔普通订单结算

普通订单只有一个支付对象时，现有一笔确认分账行为和管理展示保持兼容。

### UC-3：部分支付对象分账失败

一个订单的部分支付对象成功、部分失败或处理中时，订单不能标记为已结算；系统只能重试未成功的支付对象，不能重复调用已成功的支付对象。

### UC-4：日终对账

对账任务应分别匹配 AdaPay 的 Charge、PaymentConfirm、Div 记录和本地支付/分账子记录，并能定位到订单、支付对象和确认对象。

### UC-5：拼单退款或回退

退款、支付撤销和分账回退必须识别订单下所有支付对象及其分账状态，不能因只读取一条支付或确认记录而误操作。

## Business Rules

1. AdaPay 确认金额以支付对象为边界；单次 `confirm_amt` 不得超过该 `payment_id` 的可确认余额。
2. 一个订单的分账金额必须拆分到所有已支付且需要确认的支付对象；所有子确认金额之和等于订单可分账金额。
3. 主体金额拆分采用确定性规则：按订单主体金额比例分配，最后一个支付对象吸收分、厘舍入差额，确保分配总额精确相等。
4. 每个支付对象的 `div_members` 金额之和必须等于该支付对象本次 `confirm_amt`。
5. 每次 AdaPay 请求中的手续费承担方必须且只能有一个。若原手续费承担主体在当前支付对象上的拆分金额为 0，则按计费顺序转移给当前支付对象中第一个金额大于 0 的其他主体；无可用主体时该子记录不得调用 AdaPay，并进入可诊断失败状态。
6. 已成功的支付对象不可再次确认；处理中对象必须先查询/对账确认最终状态后再决定是否重试。
7. 订单级状态由支付子记录聚合：全部成功/合法回退才算已结算；存在处理中则为处理中；存在失败则至少为失败或部分失败；存在未执行则为待分账。
8. 订单结算管理以订单为主视图，同时提供支付对象级明细、金额、确认号和状态。
9. 日终对账的本地支付金额使用支付记录的实际支付金额；历史普通支付记录没有该字段时才回退使用订单支付金额。
10. 对账不得按订单号合并不同 `payment_id` 的 Charge、PaymentConfirm 或 Div 记录；匹配键至少包含 `payment_id`，分账确认还必须包含 `confirm_id`。
11. 订单完成结算、退款和回退均必须具备幂等保护，重复消息、重复点击和日终重跑不得造成重复分账或重复收入。
12. 历史单支付订单的现有数据和管理页面语义保持兼容；新模型不得修改历史财务快照。

## Frontend Requirements

- 订单结算管理列表继续按订单展示，不因拼单拆成多条订单。
- 订单详情展示订单总金额、已支付总金额、已确认分账金额和整体结算状态。
- 增加支付分账明细区域，展示每个付款对象的脱敏支付标识、支付金额、确认金额、确认号、状态、失败原因和主体分账明细。
- 部分成功、处理中、失败状态必须有清晰区分，禁止把部分成功显示为整体已结算。
- 重试按钮只能作用于可重试的支付子记录；已成功记录不显示重试操作。
- 日终对账详情支持按订单号、`payment_id`、`confirm_id` 和匹配结果定位差异。
- 对账页面明确区分支付金额差异、确认金额差异、主体金额差异、仅账单存在和仅本地存在。

## Edge Cases

- 拼单付款数量为 1 时按普通订单路径验证兼容性。
- 多个支付对象金额不相等时，按实际支付金额拆分并由最后一个对象吸收舍入差额。
- 某支付对象已部分确认或存在历史撤销时，只确认其剩余额度。
- 某主体在一个支付对象上的拆分金额为 0 时，不发送零金额 `div_member`，并执行手续费承担方转移规则。
- 同一收款人以不同业务角色出现时，必须保持角色主体边界，手续费承担方不能因收款人 ID 相同而串移。
- 支付成功回调重复、结算任务重复执行、Redis Pending 重发和人工重试并发时，不得生成重复有效确认。
- 一个子分账成功后另一个子分账失败时，退款/回退不得撤销或重复处理已成功子分账。
- AdaPay 账单延迟出现时，日终对账应记录待匹配，不得把暂时缺失直接当作本地数据错误。
- 历史记录缺少支付对象金额时，普通订单允许兼容回退；拼单历史记录缺少金额时必须进入人工核查。

## Acceptance Criteria

1. 两笔 0.20 支付组成 0.40 订单时，产生两笔独立确认；每笔确认金额为 0.20，主体金额总和与订单计费结果一致。
2. 任一支付对象的分账请求金额不得大于其支付金额减去已确认和已撤销金额。
3. 单笔支付订单的结算、订单管理、对账结果与改造前一致。
4. 当原手续费承担方在某支付对象上的金额为 0 时，该请求仍有且只有一个有效手续费承担方；无可转移主体时不会调用外部接口。
5. 一个子记录失败时，重试不会再次调用已成功的其他子记录。
6. 订单管理能正确展示“全部成功、部分成功、处理中、全部失败、已回退”五类聚合结果及子记录。
7. 日终对账能对两笔 Charge、两笔 PaymentConfirm 和对应 Div 明细分别匹配，且本地支付金额使用实际支付金额而非订单总额。
8. 对账重跑不会重复产生有效本地记录或错误覆盖上一次对账结果。
9. 退款/回退测试覆盖多支付对象中存在成功、失败和处理中组合的情况。
10. 后端单元测试、集成测试和管理端类型检查/构建通过；关键拼单结算链路完成测试环境验收。

## Assumptions

- AdaPay 的确认分账接口必须以单个 `payment_id` 调用，不能用一个请求跨多个支付对象确认。
- 拼单各支付对象的实际金额以 `pay_out_order_no.pay_amount` 为准；普通历史记录允许为空。
- 订单级计费主体金额仍以现有应收应付结果为准，不重新计算业务分账规则。
- 订单结算管理和日终对账属于同一后端支付域，但管理端需要配合展示字段和操作粒度调整。
- 本规格不授权生产数据库手工修复、凭据更换、部署或历史账务补偿；这些动作需单独审批并提供回滚方案。
