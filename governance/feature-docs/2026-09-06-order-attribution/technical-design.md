# 技术设计：订单渠道与推荐人记录

## 模块影响

| 模块 | 变更类型 | 说明 |
|---|---|---|
| `yshop-module-order-api` | 修改 | 扩展统一订单创建 DTO，增加两个可选归因字段 |
| `yshop-module-order-biz` | 修改 | 接收 App 下单字段、校验推荐人、写入订单实体；保持查询响应不变 |
| `yshop-module-site` | 修改 | 家政服务订单构造统一订单 DTO 时透传字段 |
| `yshop-module-device` | 修改 | 设备订单构造统一订单 DTO 时透传字段 |
| `yshop-module-desk` | 修改 | 桌面预约订单构造统一预约 DTO 时透传字段，并复用订单归属校验 |
| `yshop-module-order-biz` admin | 修改 | 管理端订单创建接收字段并复用推荐人校验；新增订单推广分页查询 |

| `governance/CONTRACT` | 实现后更新 | 重新生成后端 OpenAPI 快照 |

## 架构决策

### 1. 归因字段放在统一订单表

将渠道和推荐人保存到 `yshop_store_order`，因为本次范围是所有非积分订单，且这些订单最终共享该订单实体。积分订单使用独立订单模型，不引入跨模块字段。

### 2. 公开参数和内部 DTO 使用同名字段

`AppOrderParam` 是 App 下单入口，`AppStoreOrderDTO` 是业务模块调用统一订单 API 的边界对象。两者使用同名字段，减少转换歧义，确保家政和设备等内部调用不会丢失归因信息。

### 3. 推荐人校验

创建订单时校验推荐人属于当前租户，且不能是下单用户本人。用户没有商圈归属概念，因此不校验推荐人与订单门店的商圈关系：

```text
当前租户上下文
        ↓
推荐人属于当前租户？
        ↓
推荐人 != 下单用户？
        ↓
保存订单归因
```

校验失败在订单落库前终止流程，避免产生无效订单。推荐人字段不作为返佣计算触发器，本次只保存归属事实。

### 4. 归因信息在创建时固化

新订单创建时写入字段；加餐更新已有订单时不覆盖原有值。普通订单更新、退款和履约流程不修改这两个字段，以保持历史归因稳定。

### 5. 仅新增可空列和查询索引

历史订单不做推断回填。新增列允许 `NULL`，保留“无渠道/无推荐人”和空字符串归一化后的明确语义。索引按租户前缀建立，满足后续统计和返佣查询的基本访问路径，同时保持租户隔离。

## 必要流程

### 公开 App 下单

1. 接收 `channelCode`、`referrerUserId`。
2. 对渠道标识执行长度校验；空白值归一为空。
3. 按现有流程确定下单用户和门店。
4. 若存在推荐人，校验租户和非自推荐条件。
5. 在新订单实体中写入两个字段。
6. 继续现有价格、库存、优惠券、支付和履约流程。

### 内部模块下单

```text
家政/设备请求
    ↓ 组装 AppStoreOrderDTO（透传字段）
OrderApi#createAppOrder
    ↓ 转换 AppOrderParam（透传字段）
AppStoreOrderService#createOrder
    ↓ 校验并保存
yshop_store_order
```

内部调用缺少字段时按 `NULL` 处理；不为积分订单增加转换或校验逻辑。

桌面预约订单通过 `OrderApi#addDueOrder` 直接写入统一订单表，因此在写入前复用同一套推荐人校验，并由预约 DTO 透传渠道和推荐人字段。

管理端订单创建通过 `/admin-api/order/store-order/create` 写入统一订单表，同样在落库前复用推荐人校验；积分订单不经过该入口的本次改造。

### 管理端订单推广查询

页面调用 `/admin-api/order/store-order/promotion-page`，查询条件由页面传入，后端固定增加“渠道标识非空或推荐人非空”条件，并沿用现有租户和门店数据权限。查询返回独立推广记录 VO，避免为了页面展示而改变普通订单接口的返回契约。

## 事务、幂等与并发

- 沿用现有订单创建事务边界。
- 推荐人校验和订单写入必须位于同一创建事务内。
- 本次不新增订单幂等键；现有订单幂等和重复下单规则保持不变。
- 订单归因字段只在新建订单或明确允许的统一创建流程中写入，避免并发更新覆盖历史值。

## 风险与权衡

| 风险 | 等级 | 缓解措施 |
|---|---|---|
| 内部 DTO 未同步扩展导致字段丢失 | 中 | 将 API DTO、家政和设备调用方纳入同一契约变更与测试 |
| 订单更新覆盖归因 | 中 | 新增回归测试，检查加餐及普通更新保留原值 |
| 历史订单回填产生错误归因 | 低 | 不回填历史数据，新增列保持可空 |
| 后续返佣查询数据量增长 | 低 | 增加租户前缀索引，后续按实际查询计划优化 |
