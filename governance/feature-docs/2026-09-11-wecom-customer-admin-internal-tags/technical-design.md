# 企业微信客户管理员与统一内部标签技术设计

## 模块影响

- `backend`：在 `yshop-module-mp` 增加客户管理员同步、分页和内部标签管理/关联能力；迁移现有客户群标签数据；更新客户群查询、批量打标和群发筛选。
- `admin`：新增“客户管理员”页面和“标签管理 → 内部标签”页面；现有“客户标签”页面调整菜单归属；客户群页面改用内部标签。
- `miniapp`、`icepolar-dms`：N/A。

## 关键决策

1. **标签源分离**：客户标签继续以企业微信客户标签库为唯一来源；内部标签为本地租户级标签库。两者即使同名也不共用 ID 或关联关系。
2. **内部标签统一模型**：使用一个租户级内部标签表和一个多态关联表，关联目标类型限定为 `CUSTOMER_GROUP`、`CUSTOMER_ADMIN`。业务服务在写入前验证目标属于当前租户，避免多态关联绕过租户隔离。
3. **客户群标签迁移**：创建新内部标签后，以“租户 + 标签名称”合并旧客户群标签；旧群标签及关联表暂不删除，作为迁移回滚和审计依据，代码切换后不再写入旧表。
4. **客户管理员身份**：以“企业微信配置 + userid”作为同步幂等键。同步只保留企业微信当前客户联系权限范围内的成员；已不在范围内的记录标记为非当前范围，不物理删除其历史内部标签关联。
5. **凭证复用**：客户管理员列表继续调用现有客户联系 Secret 的 `externalcontact/get_follow_user_list`；不把全部通讯录成员接口混入本功能。当前该接口主要返回 userid，成员姓名不是本期可靠字段。
6. **成员选择统一**：客户管理员服务提供统一的 simple-list 选项，联系我、客户联系人发送、客户群群发和定时推送复用该选项；客户联系人发送在前端再按该客户的实际跟进成员过滤。
7. **群发兼容**：客户群群发请求的 `tagIds` 改为内部标签 ID；服务端按内部标签关联反查客户群，群发外部接口和发送成员校验保持原有逻辑。

## 必要流程

### 客户管理员同步

`accountId → 当前租户企业微信配置 → CorpID/客户联系 Secret → access_token → get_follow_user_list → upsert(account_id, userid) → 标记不再返回的历史成员 → 返回同步统计`

- 外部列表为空表示当前权限范围为空，不删除历史记录。
- 同步使用事务和唯一键，重复执行不得创建重复成员。
- 成员姓名在没有通讯录同步 Secret 或其他可靠来源时显示 userid；不得用后台系统用户表猜测企业微信身份。

### 成员选择器

`accountId → 客户管理员 simple-list → 前端可搜索多选下拉 → 提交 userid[]/sender`

- “联系我”表单的成员选择直接提交选中的 userid 数组，后端继续按企业微信联系我接口校验。
- 客户群发送成员和定时推送发送成员使用单选下拉；客户联系人发送只展示该联系人 `followUsers` 中存在于客户管理员选项的成员。
- 编辑联系我时，已保存但当前同步列表不存在的 userid 以“历史成员（不可用）”保留展示，提交时由后端决定是否允许继续使用。
- `partyIds`/部门 ID 保持独立字段，不伪装成客户管理员；本期不要求部门下拉。

### 内部标签绑定

`tenantId → 内部标签 → 目标类型/目标 ID → 当前租户对象校验 → 幂等插入/软删除关联`

- 客户群目标需验证 `group_id` 属于当前租户。
- 客户管理员目标需验证 `customer_admin_id` 属于当前租户。
- 删除内部标签先解除关联，再软删除标签；查询默认排除已删除数据。

### 旧数据迁移

`旧客户群标签 → 按 tenant_id + name 合并内部标签 → 旧群关联映射为内部标签关联 → 迁移结果校验 → 新代码读取内部标签`

- 同租户同名旧标签合并为一个内部标签。
- 旧标签跨企业微信配置同名时，所有客户群关联均转入同一个租户级内部标签。
- `mp_wecom_customer_group_schedule.tag_ids` 中保存的旧客户群标签 ID 也必须按旧标签映射表转换为内部标签 ID，保证一次性/定时群发继续使用原筛选语义。
- 迁移脚本必须可重复执行，且不能覆盖管理员在迁移后新建的内部标签或重复创建关联。

## 数据模型增量

- `mp_wecom_customer_admin`：客户管理员同步快照，包含 `tenant_id`、`account_id`、`userid`、当前范围标识、最近同步时间和审计字段；唯一键为租户、企业微信配置、userid、未删除状态。
- `mp_wecom_internal_tag`：租户级内部标签，包含名称、排序、审计字段和软删除字段；唯一键为租户、名称、未删除状态。
- `mp_wecom_internal_tag_rel`：内部标签与客户群/客户管理员关联，包含租户、目标类型、目标 ID、关联时的 account_id、标签 ID 和审计字段；唯一键为租户、目标类型、目标 ID、标签 ID、未删除状态。
- 旧表 `mp_wecom_customer_group_tag`、`mp_wecom_customer_group_tag_rel` 在首期迁移后保留只读，不再作为业务查询来源。
- 定时推送表继续保存内部标签 ID JSON；迁移前必须完成旧标签 ID 到内部标签 ID 的转换。

## 风险与权衡

- 统一关联表使用目标类型和目标 ID，数据库不能用普通外键表达两类目标；必须依赖 Service 层校验和定向清理测试。
- 企业微信客户联系 Secret 的成员列表接口不能稳定提供成员姓名；若必须展示真实姓名，需要另行增加通讯录读取凭证和外部接口契约，不在本期隐式引入。
- 旧客户群标签按名称合并可能改变原先按 account_id 隔离的标签视图；这是租户级共享的直接结果，迁移报告必须列出合并数量。
- 企业微信客户标签页面继续实时调用外部接口；内部标签页面只读本地租户库，两个页面必须明确标识标签来源。
- 同步期间成员从权限范围移除时保留历史记录和标签关联，避免历史筛选和审计数据丢失；“当前范围”筛选默认只显示仍在范围内的成员。
