# 活动管理需求规格

## Scope

### In

- 管理端创建和维护周期性活动模板，并按规则生成独立活动期次。
- 配置活动商圈、活动周期、报名区间、开奖时间和活动状态。
- 配置活动标题、富文本正文、活动主图、活动背景图及其他渠道宣传素材。
- 配置一个或多个活动客户管理员和活动社群标签；社群标签关联的具体微信群由群标签维护，不在活动中单独指定。
- 配置多个奖品及各自数量、图片和领取说明。
- 查询报名记录、中奖记录、计划中奖人数和实际中奖人数。
- 在活动期次上生成可用于投放的微信小程序码，并返回临时图片地址。
- 报名时基于本地数据校验用户是否已添加指定活动管理员，以及是否属于活动社群标签对应的微信群。
- 按计划时间自动开奖，并支持后台查看开奖结果。

### Out

- 第一版不开发小程序页面和小程序交互。
- 第一版不调用企业微信接口，不实时同步客户、标签或群成员。
- 不包含奖品自动发放、物流、核销、优惠券/积分等系统权益。
- 不包含付费报名、权重抽奖、多轮开奖和人工指定中奖人。

### Deferred

- 小程序活动列表、详情、报名、结果展示和背景图实际接入。
- 企业微信数据实时校验与群成员同步。
- 奖品权益自动发放及领奖核销闭环。

## Use Cases

| 角色 | 目标 | 主流程 |
|---|---|---|
| 活动运营人员 | 配置活动 | 创建模板→配置周期/报名/开奖时间→配置内容、管理员、社群和奖品→启用 |
| 活动运营人员 | 管理期次 | 查看期次状态、报名数和中奖数→查看报名/中奖明细→必要时查看开奖结果 |
| 活动运营人员 | 推广期次 | 在指定活动期次上生成小程序码→下载或复制图片地址→投放到其他渠道 |
| C 端用户 | 报名活动 | 在报名区间提交报名→系统校验管理员添加关系和社群归属→报名成功或展示失败原因 |
| 定时任务 | 完成开奖 | 到达期次开奖时间→锁定有效报名→按奖品数量抽取中奖人→生成中奖记录→期次结束 |

## Business Rules

1. 活动模板定义周期规则；每个活动期次保存独立的时间、内容、奖品和校验规则快照。
2. 一期活动至少配置活动商圈、活动周期、报名开始/结束时间、开奖时间、标题、正文、活动主图和奖品。
3. 示例规则“每周五 22:00 截止报名、22:00 开奖”必须支持；报名结束时间不得晚于开奖时间。
4. 活动状态为“未开始、进行中、已结束”，由期次时间和开奖完成情况决定，不允许通过状态值绕过时间约束。
5. 每个用户同一期最多报名一次；报名成功后不可重复占用名额。
6. 报名必须同时满足已添加任一指定活动客户管理员、且在活动所属社群标签对应的微信群本地成员数据中；未配置某项校验时跳过该项。
7. 活动可配置一个或多个客户管理员；用户满足任一管理员关系即可通过管理员校验。
8. 每个奖品数量为正整数；计划中奖人数等于有效奖品数量合计，不能超过有效报名人数。
9. 开奖只处理有效报名记录；同一期开奖必须幂等，重复触发不得重复生成中奖记录或重复消耗奖品数量。
10. 中奖记录保存开奖时的奖品名称、图片、数量规则和领取说明；后续模板或配置变更不得回溯修改历史期次。
11. 开奖完成后期次进入“已结束”，报名和中奖记录只读。
12. 活动管理员和活动数据按当前租户隔离，并遵循部门/商圈数据权限。
13. 活动背景图仅表达活动页面背景用途；宣传素材图独立管理，用于其他渠道投放，不与背景图混用。
14. 小程序码必须绑定具体活动期次，不绑定活动模板；扫码后应能定位到该期活动。
15. 同一期可重复生成小程序码；每次生成均返回新的临时图片地址，不覆盖历史业务记录。
16. 小程序码生成复用系统已有小程序码能力，使用当前租户的小程序配置和登录/租户上下文，不允许指定其他租户配置。
17. 小程序码图片为临时投放素材，预期保留 48 小时；过期后需要重新生成，不作为永久活动素材保存。

## Frontend Requirements

- 后台活动列表展示标题、商圈、期次、报名区间、开奖时间、报名人数、计划/实际中奖人数、状态和操作。
- 后台编辑页分区呈现：基础信息、时间规则、内容素材、客户管理员、社群/群配置、奖品配置。
- 奖品支持动态新增、编辑和删除；提交时显示奖品总数与计划中奖人数。
- 支持查看某一期的报名记录和中奖记录，至少可按用户、状态和奖品筛选，并支持导出。
- 已生成期次后，影响该期历史快照的配置不可直接回溯修改；页面须明确提示影响范围。
- 开奖前展示倒计时或计划时间；开奖后展示实际中奖人数和开奖完成状态。
- 活动期次操作中提供“生成小程序码”；生成成功后支持预览、下载或复制图片地址，并展示临时有效期提示。
- 生成小程序码时使用活动期次标识作为定位参数；模板标识不能单独替代期次标识。
- 小程序页面本期不实现，但 API 契约需预留活动详情、报名资格和结果查询的业务语义。

## Edge Cases

- 报名截止时间与开奖时间相同：截止时刻前允许报名，达到时刻后拒绝报名并进入开奖流程。
- 没有有效报名或有效报名少于奖品总数：按实际有效报名人数开奖，未分配奖品保留为未中奖数量。
- 本地管理员关系或群成员数据缺失：按校验失败处理，不回退为通过。
- 报名请求使用当前登录态的 `yshop_user.id`；系统通过 `mp_wecom_customer_contact.member_id` 获取企微客户联系人的 `external_user_id`。联系人查不到时，开启的管理员或社群校验必须失败；两个校验均关闭时可跳过联系人查询。报名请求可携带推荐人用户 ID 和渠道标识。
- 同一用户满足多个管理员或多个群条件：只生成一条报名记录。
- 管理员、标签、群配置在模板变更或停用后：不影响已生成期次的快照。
- 定时开奖与后台人工触发并发：只允许一个开奖结果生效，另一方返回已完成状态。
- 活动时间跨自然日或跨周：后台必须按完整日期时间校验，不仅比较时分。
- 删除活动或奖品前存在报名/中奖记录：禁止破坏性删除，保留历史可追溯性。
- 期次尚未接入小程序页面时：允许后台生成二维码作为预投放素材，但实际扫码承载页面由后续小程序阶段交付。
- 小程序码生成失败或临时地址失效：不产生“已生成”状态，允许运营重新生成。

## Acceptance Criteria

1. 运营人员可创建每周五活动，并配置报名截止 22:00、开奖 22:00。
2. 系统能为周期规则生成独立期次，期次拥有自己的时间、奖品和校验快照。
3. 未开始和已结束期次不能报名；报名区间内可报名，重复报名被拒绝。
4. 未添加指定活动管理员或不在指定社群标签对应微信群本地数据中的用户不能报名，并获得明确失败原因。
5. 活动可配置多个奖品及数量，系统正确计算计划中奖人数。
6. 到达开奖时间后自动生成不超过有效报名人数的中奖记录，且不超过各奖品配置数量。
7. 重复开奖或并发开奖不会产生重复中奖记录或超发奖品。
8. 后台可查看活动期次、报名记录、中奖记录、计划中奖人数和实际中奖人数。
9. 历史期次的中奖记录和内容快照不因模板后续修改而变化。
10. 不同租户及无权限用户不能读取或操作其他租户/商圈活动数据。
11. 运营人员可在具体活动期次上生成小程序码，二维码定位参数对应期次而非模板。
12. 小程序码生成失败时后台展示失败结果；生成成功时返回可访问的临时图片地址和预期过期时间。

## Assumptions

- “活动周期”一期采用每周规则，首期可支持每周指定星期；更复杂的月度/自定义周期后续扩展。
- “活动主图”用于活动自身展示；“活动宣传图/素材图”作为独立投放素材，可由活动关联但不强制一一对应。
- 本期活动管理员指企业微信客户管理员，具体客户关系使用系统已有本地客户关联数据判断。
- 抽奖采用系统随机抽取有效报名用户；若后续需要权重、人工干预或可复核种子，需要新增规则确认。
- 活动模板停用后不再生成新期次；已经生成的未开始期次是否继续执行，进入设计阶段时按产品选择冻结。
- 小程序码暂使用后续活动详情页的固定页面路径，业务定位参数只携带活动期次；具体页面路径在小程序阶段冻结。
