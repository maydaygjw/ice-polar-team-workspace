# 订单应收应付每日补算契约

## 目标

将本地订单应收应付的计算从订单确认收货/服务完成的请求链路移到每日定时任务。该变更不调整既有计费模板、金额计算、应收应付表结构或 OpenAPI AdaPay 支付回调流程。

## 跨模块 API

- 订单模块 `OrderApi` 提供通用按订单状态查询订单号的内部方法，状态及退款状态集合均使用 `OrderInfoEnum`，并支持可选支付状态和 `id` 游标分页。
- 查询在当前租户上下文执行，并始终排除系统删除记录。计费任务传入 `OrderInfoEnum.STATUS_2`、`paid=1`、`refundStatuses=[REFUND_STATUS_0,REFUND_STATUS_3]`，按订单主键升序分页；退款中（1）和已退款（2）的订单不参与补算，退款已拒绝（3）的订单仍可参与。
- `status=2` 覆盖商城订单确认收货后状态，以及服务订单履约完成后进入待评价状态。

## 任务与幂等

- 支付计费模块 Quartz handler 按租户每日运行并分页扫描候选订单。
- 应收应付主记录已存在且状态不是 `FAILED` 时跳过；不存在时生成，`FAILED` 时允许重试。计算逻辑仍以租户隔离的订单快照和当前有效计费配置为准。
- 每个候选订单的异常单独记录并继续处理后续订单；任务按租户输出扫描、生成、重试、跳过和失败数量。
- OpenAPI AdaPay 继续在支付成功回调中基于创建时快照生成应收应付，不纳入本地商城订单扫描。

## 部署

- 新增 Flyway 迁移注册每日 `orderReceivablePayableDailyJob`，每天 03:00 执行。
- 迁移只添加/更新 `infra_job` 定时任务，不改业务表。
