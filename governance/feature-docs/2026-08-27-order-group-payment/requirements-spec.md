# 拼单支付需求规格

## Scope

### In-scope

- 为租户/门店提供拼单开关配置：租户配置为总开关，门店可覆盖；门店未配置时继承租户配置。
- 用户下单时可选择拼单总人数，人数包含发起人，范围为 2～10 人。
- 发起人必须先支付一份；其他登录用户通过统一拼单页支付剩余一份或多份。
- 同一用户可在一次或多次支付中购买多份；一次选择多份时合并为一笔 AdaPay 支付。
- 按支付份额记录支付进度；全部份额成功后订单进入现有后续流程。
- 支持拼单有效期、超时关闭、发起人主动取消和已支付份额原路退款。
- 在订单中记录拼单状态：`0/NULL` 表示非拼单，`1` 表示拼单中，`2` 表示已拼满。
- 管理后台提供租户级、门店级拼单开关配置；管理员沿用现有订单退款权限和规则。

### Out-of-scope

- 本期不改造小程序用户界面、下单入口、拼单页或分享入口；小程序由后续需求对接。
- 不新增微信、支付宝或其他支付渠道，沿用当前系统 AdaPay 支付。
- 不按商品分类配置拼单资格，资格只由租户和门店开关决定。
- 不新增退款失败的专用状态、重试流程或异常处理规则。
- 不提供单个支付份额的独立退款；发起人用户侧申请按整单处理。

## Use Cases

### 发起人发起拼单

- **角色**：已登录用户。
- **目标**：将一个订单拆成固定份数，与其他用户共同完成支付。
- **主流程**：
  1. 用户在允许拼单的门店下单，并选择总人数。
  2. 系统按订单金额生成对应支付份额，用户必须先支付第一份。
  3. 首份支付成功后，拼单生效并开始倒计时。
  4. 用户打开统一拼单页并分享给其他人。
  5. 所有份额支付成功后，订单进入现有已付款后的流程。

### 参与人支付拼单份额

- **角色**：已登录用户，可以是发起人本人或任意获得拼单页的用户。
- **目标**：支付一份或多份剩余份额。
- **主流程**：
  1. 用户打开拼单页并登录。
  2. 查看剩余份数和每份金额，选择支付份数。
  3. 系统发起一笔合计金额的 AdaPay 支付。
  4. 支付成功后更新该用户已支付份数和订单拼单进度。

### 系统处理未完成拼单

- **角色**：系统。
- **目标**：避免拼单长期占用订单和资金。
- **主流程**：
  1. 从发起人首份支付成功开始计算租户配置的有效期（分钟）。
  2. 截止时间前未拼满时，关闭订单。
  3. 已支付份额全部按原支付路径退回，分享页失效。

### 发起人取消或申请退款

- **角色**：发起人；管理员可按现有权限主动退款。
- **目标**：终止拼单并退回已支付资金。
- **业务结果**：发起人主动取消时，与超时处理一致；拼单完成后的退款按现有订单退款规则判断，用户侧由发起人申请整单退款，所有支付人全部原路退回。

## Business Rules

1. 只有租户开关开启且门店最终配置为开启时，订单才允许拼单；门店配置优先于租户配置。
2. 拼单人数必须包含发起人，最少 2 人，最多 10 人；人数确认并首份支付成功后不可修改。需要修改时，发起人必须先取消原订单。
3. 每份金额按订单金额平均拆分并精确到分；无法整除的尾差放在最后一份；每份金额不得低于 0.1 元。
4. 发起人必须先完成第一份支付，其他份额在首份支付成功后才可被支付。
5. 参与支付者必须登录小程序账号，不允许游客支付；同一账号可以支付多份，也可以在有效期内分多次追加支付。
6. 分享使用一个统一拼单页，任何获得页面的登录用户都可以支付当前剩余份额；份额成功支付后不可重复占用。
7. 多人同时支付剩余份额时，系统不得形成超额支付；成功占用剩余份额的支付有效，未成功占用的请求不得增加已支付份数。
8. 用户选择多份时，一次 AdaPay 支付的金额等于所选份数对应金额之和。
9. 拼单中订单的主订单不进入现有已付款后的履约流程；只有拼单状态变为 `2` 后才继续后续流程。
10. 非拼单订单的拼单状态为 `0` 或 `NULL`；拼单超时/取消后保留 `1`，拼满后即使后续退款仍保留 `2`，订单关闭、退款等结果由现有订单状态表达。
11. 拼单有效期从发起人首份支付成功开始计算，时长取租户的分钟配置；该配置按现有配置能力保存，不增加本功能专用校验。
12. 拼单未完成时发生超时或发起人取消：订单关闭、分享页失效、所有已支付份额原路退回。
13. 拼单完成后的用户侧退款只能由发起人申请，并按整单退款；所有已支付份额分别退回各自原支付人。管理员继续使用现有主动退款权限和规则。
14. 管理后台服务订单详情应展示该订单全部成功的拼单支付明细；非拼单订单或没有成功拼单支付记录时不展示明细表。

## Frontend Requirements

### 管理后台 (`admin`)

- 提供租户级拼单开关配置。
- 提供门店级拼单开关配置，并明确显示“继承租户配置”与门店覆盖状态。
- 配置结果应能反映最终生效状态，供后端判断订单是否允许拼单。
- 本期不新增小程序用户侧页面；管理后台不承担用户拼单和分享流程。
- 订单的拼单状态、支付进度和退款结果沿用后端提供的业务数据及现有订单展示/退款规则。
- 管理后台服务订单详情在存在拼单支付记录时展示每位支付人的支付份数、金额和支付时间。

### 小程序 (`miniapp`)

- 本期不改动，仅记录后续需要对接统一拼单页、登录校验、份数选择、AdaPay 支付、进度展示和分享入口。

## Edge Cases

| 场景 | 处理 |
|---|---|
| 门店未配置开关 | 继承租户配置。 |
| 租户关闭但门店曾开启 | 租户总开关未开启，订单不得拼单。 |
| 首份支付前访问拼单页 | 不允许支付剩余份额；订单沿用现有待支付规则。 |
| 人数确认后修改 | 不允许修改，必须取消原订单后重新下单。 |
| 同一用户多次支付 | 允许，只要订单仍在有效期内且仍有剩余份额。 |
| 多人同时支付最后份额 | 不能超额拼单，未成功占用份额的支付请求不得生效。 |
| 超时后访问分享页 | 分享页失效，不得继续支付。 |
| 发起人主动取消未拼满订单 | 关闭订单并退回全部已支付份额。 |
| 拼满后申请退款 | 由发起人申请整单退款，所有支付人全部原路退回；适用现有退款状态规则。 |
| 退款异常 | 本期不新增特殊处理，沿用现有退款流程。 |

## Acceptance Criteria

1. 租户关闭拼单时，所有门店均不可创建拼单订单；租户开启后，门店覆盖配置按最终生效状态判断。
2. 用户可选择包含发起人在内的 2～10 人；首份支付成功前不能由其他用户支付。
3. 系统按份拆分金额，尾差只出现在最后一份，且每份金额不低于 0.1 元。
4. 登录用户可在统一拼单页支付一份或多份；多份选择只发起一笔合计金额的 AdaPay 支付。
5. 同一用户可在有效期内多次追加支付，支付进度不会重复计数或超过总份数。
6. 拼单未满时订单拼单状态为 `1`，拼满时为 `2`；非拼单订单为 `0/NULL`。
7. 拼满前订单不会进入现有已付款后的履约流程；拼满后正常进入该流程。
8. 有效期从发起人首份支付成功开始；超时后订单关闭、分享失效，并将所有已支付份额原路退回。
9. 发起人主动取消未拼满订单时，结果与超时一致。
10. 发起人对已拼满订单申请退款时，所有已支付份额均退回对应原支付人；管理员仍可按现有权限主动退款。
11. 并发支付剩余份额时，系统不会产生超过总份数的成功支付记录。
12. 未登录用户不能完成拼单支付，游客支付不被接受。

## Assumptions

- 本期只定义后端业务能力和管理端配置，完整用户侧流程待小程序对接后才可端到端使用。
- 订单总金额、商品快照及现有订单履约规则继续沿用当前系统；本需求不改变非拼单订单的状态语义。
- AdaPay、原路退款和现有退款资格判断沿用当前系统能力；本需求仅增加多支付人、多份额的业务归集。
- 拼单退款以整单为业务单位；一名用户购买多份时，其多份资金按该用户原支付流水退回。
- 本功能涉及支付、订单、数据库和跨端 API，后续设计阶段必须先冻结功能级契约，并补充迁移与验证方案。
