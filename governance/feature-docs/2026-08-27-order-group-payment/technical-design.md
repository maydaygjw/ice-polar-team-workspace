# 拼单支付技术设计

## 1. 设计目标

在现有订单、AdaPay 和 `pay_out_order_no` 体系上增加一个订单对应多个支付人的能力。每次支付尝试独立生成 AdaPay 支付号，成功回调先更新支付尝试，再按份数汇总主订单；主订单只有拼满后才进入现有履约流程。

本期只改造 `backend` 和 `admin`，不改造微信支付，也不改造 `miniapp`。

## 2. 关键决策

1. 不新增 `yshop_store_order_group_payment` 表。支付尝试继续存放在现有 `pay_out_order_no` 表中。
2. `outPayNo` 统一格式为 `主订单号-拼单人序号-支付尝试序号`。
3. `outPayNo` 只作为外部支付单号，不作为业务数据源；业务逻辑只读取独立字段，不反解析字符串。
4. 普通订单的拼单人序号固定为 `1`，例如 `订单号-1-1`、`订单号-1-2`。
5. 拼单人序号绑定订单内的支付用户。同一用户后续重试或追加支付时复用该序号；一次支付多份通过 `share_count` 表示。
6. 历史两段式 AdaPay 单号不修改，新字段不回填历史数据；新代码保留旧记录读取兼容路径。

## 3. 数据模型

### 3.1 主订单 `yshop_store_order`

新增字段建议：

| 字段 | 类型 | 说明 |
|---|---|---|
| `group_status` | tinyint | `0/NULL` 非拼单，`1` 拼单中，`2` 已拼满 |
| `group_total_count` | tinyint | 拼单总份数，包含发起人，2～10 |
| `group_paid_count` | tinyint | 已成功支付份数 |
| `group_start_time` | datetime | 发起人首份成功支付时间 |
| `group_expire_time` | datetime | 本订单固定的拼单截止时间 |

普通订单的 `group_status` 保持 `0/NULL`。拼单订单创建后进入 `1`；首份支付成功后设置开始时间和截止时间；全部份数成功后改为 `2`。取消、超时或退款不回退拼单状态。

### 3.2 支付映射 `pay_out_order_no`

新增字段建议：

| 字段 | 类型 | 说明 |
|---|---|---|
| `group_member_no` | int | 订单内拼单人序号；普通订单固定为 `1` |
| `pay_attempt_no` | int | 该拼单人的支付尝试序号，从 `1` 递增 |
| `payer_user_id` | bigint | 实际发起本次支付的登录用户 |
| `share_count` | int | 本次支付的份数 |
| `pay_amount` | decimal(10,2) | 本次支付金额 |
| `refund_status` | tinyint | 该支付记录的退款处理状态，沿用现有退款结果语义 |
| `refund_id` | varchar(128) | AdaPay 退款请求或结果标识 |
| `refund_time` | datetime | 该支付记录退款完成时间 |

历史记录新增字段保持空值，不执行数据迁移。新记录必须写入完整字段。保留现有 `(tenant_id, out_pay_no)` 唯一约束，并增加按 `(tenant_id, order_id, group_member_no, pay_attempt_no)` 查询的索引。

## 4. 支付单号生成

生成前在订单行锁内确定序号：

1. 普通订单使用 `group_member_no=1`。
2. 拼单发起人固定使用 `group_member_no=1`；其他新支付用户在该订单内分配未使用的拼单人序号。
3. 同一订单、同一支付用户继续支付时复用已有 `group_member_no`。
4. `pay_attempt_no` 取该订单、该拼单人的新支付尝试序号。
5. 直接拼接三段字段生成 `outPayNo`，不从 `outPayNo` 解析序号。
6. 插入时由数据库唯一约束兜底，发生冲突则重新获取序号并重试。

示例：

```text
订单 O，普通订单：O-1-1、O-1-2
订单 O，发起人重试：O-1-3
订单 O，第二位用户首次支付：O-2-1
订单 O，第二位用户再次支付：O-2-2
```

## 5. 创建支付与份数占用

创建 AdaPay 支付尝试时，在同一事务中锁定主订单：

1. 检查订单仍为可支付状态、拼单未过期且拼单未满。
2. 计算已成功份数与未关闭支付尝试占用份数。
3. 请求份数不得超过剩余可占用份数。
4. 计算本次支付金额；尾差只归入最后一份。
5. 写入 `pay_out_order_no`，状态为创建中，并生成三段式 `outPayNo`。
6. 调用 AdaPay 创建支付订单。
7. AdaPay 创建失败时只关闭本次支付尝试，不影响其他支付人。

同一用户重新发起支付时，可以关闭该用户自己仍为创建中的旧尝试后重新占用；不能关闭其他用户的创建中尝试。支付尝试超时或主动取消时释放其占用份数。

## 6. AdaPay 回调

AdaPay 回调携带 `outPayNo`，通过 `pay_out_order_no` 精确定位支付尝试：

```text
AdaPay 回调
  → 查询 outPayNo
  → 幂等更新支付尝试为成功
  → 保存 adapay_payment_id 和支付时间
  → 锁定主订单并汇总成功份数
  → 未拼满：保持拼单中
  → 已拼满：只执行一次现有订单支付成功流程
```

同一支付尝试重复回调不得重复增加 `group_paid_count`。支付成功后不得再被普通订单的“单笔支付完成”逻辑重复处理。

主订单现有的单值 `transaction_id` 不作为拼单退款依据；拼单退款和支付对账以 `pay_out_order_no` 的成功记录为准。

## 7. 超时、取消与退款

### 7.1 超时

- 截止时间从发起人首份成功支付时开始。
- 延迟任务只处理仍处于拼单中且已到截止时间的订单。
- 事务锁定主订单后，将订单关闭并使拼单页失效。
- 遍历所有成功支付记录，按各自支付金额逐笔调用 AdaPay 原路退款。
- 退款完成后主订单沿用现有退款状态规则。

### 7.2 发起人取消

未拼满时，只有发起人可取消；处理结果与超时一致。普通用户不能取消或申请该拼单订单退款。

### 7.3 拼满后退款

继续沿用现有可退款状态规则，用户侧只允许发起人申请整单退款。系统按所有成功的 AdaPay 支付记录逐笔退回对应支付人，不按主订单单一支付号退款。

## 8. 配置生效

- 租户参数提供拼单总开关和付款时限分钟数。
- 沿用现有 `infra_tenant_config` 和租户参数管理页面；参数值统一按字符串保存，不新增参数类型或参数表字段。
- `order.group-payment.enabled` 约定值为字符型 `"0"`/`"1"`，`order.group-payment.timeout-minutes` 约定为分钟数字符串，由业务层读取后转换使用。
- 门店支持继承、启用、禁用三态；租户关闭时最终结果始终为禁用。
- 订单创建时判断是否允许选择拼单。
- 发起人首份成功时读取有效分钟数并写入 `group_expire_time`，之后配置变化不影响该订单。

## 9. 模块影响

### Backend

- `order`：下单校验、支付尝试创建、支付成功汇总、拼单超时、取消、退款。
- `pay`：`PayOutOrderNoDO` 字段、AdaPay 单号生成、支付回调和支付记录查询 API。
- `infra`：租户拼单参数读取。
- MQ/Redis 延迟队列：增加拼单截止处理消息，保证重复消息幂等。

### Admin

- 租户参数页面增加拼单开关和付款时限。
- 门店编辑页面增加三态拼单开关和最终生效状态展示。

### Miniapp

N/A：本期不修改。

## 10. 迁移、回滚与风险

- 迁移脚本计划命名为 `backend/sql/upgrade-2026-08-27-order-group-payment.sql`。
- 迁移脚本只新增字段和索引，不修改历史 `outPayNo` 或历史支付记录。
- 新代码通过订单拼单标识区分新流程；旧普通订单继续兼容旧 AdaPay 记录。
- 回滚应用代码前不能删除新增字段；数据库字段保留可兼容已写入的新记录。
- 主要风险是支付回调、超时任务和退款任务并发，需要以主订单行锁、支付记录状态机和幂等条件保证一致性。
