# 技术设计 — 店铺收入报表独立数据源与打款指标

## 模块影响

| 模块 | 变更 | 说明 |
|---|---|---|
| `yshop-module-pay-biz` | 修改 | 报表日汇总投影、同步 API、汇总查询改读本地投影表；明细仍读本地分账事实 |
| `admin/` | 修改 | 增加同步操作和三项汇总字段 |
| 数据库 | 新增 | 新增一张店铺日汇总投影表 |
| 外部系统 | 无变化 | 同步和查询均不调用 AdaPay |

## 关键决策

1. **使用报表投影而非查询时联算**：新增店铺日汇总表保存原有指标和三项新增指标。列表分页只查该表，避免列表请求联查订单、分账和收款人结算事实。
2. **复用现有 pay 模块**：现有报表 Controller、Service、Mapper 已位于 `pay-biz`；同步及投影查询留在该模块，不引入新的跨模块业务依赖。
3. **同步采用同步请求**：用户按单店铺和日期区间发起一次重算。当前只写入按日聚合行，不需要引入后台任务主表、轮询状态 API 或 MQ。前端在请求期间显示加载状态，提交后显示结果。
4. **原子替换目标范围**：使用租户 + 店铺维度的 Redisson 锁串行化同店铺同步；在一个数据库事务中读取本地源数据、计算汇总、删除目标店铺和日期范围内的旧投影并写入新结果。事务提交前旧结果仍可查询，异常时整体回滚。锁须覆盖事务提交。
5. **保留明细的本地事实查询**：现有订单明细接口和弹窗继续读取分账主表、店铺角色明细和订单表；这些均为本地表，不访问远端。实际打款只有收款人结算流水，没有订单关系，不新增伪造的订单明细。
6. **使用现有预计打款日期策略**：注入 `ProfitSharingSettlementDateCalculator`，按与订单结算管理相同的 `T_PLUS_ONE` / `D_PLUS_ONE` 策略和本地工作日日历计算。同步日期范围是预计日期范围，不可直接误用分账日期范围。
7. **打款金额只累加净到账**：源为本地收款人结算活动版本，筛选店铺收款人类型和 `settle_stat=succeeded`，汇总 `net_settle_amount`；不纳入失败/待处理状态、旧采集版本、平台收款人和平台商户主体。
8. **投影不是财务事实**：投影可从源表重建，目标范围替换使用事务内物理删除旧投影后插入新投影；分账、订单和结算流水事实保持不可变。

## 数据来源与聚合流程

来源表均在当前后端数据库：

| 投影指标 | 来源 | 过滤及分组 |
|---|---|---|
| 原有结算订单数、订单金额、店铺收入 | `yshop_adapay_profit_sharing_order`、`yshop_adapay_profit_sharing_order_item`、`yshop_store_order` | 沿用现有报表成功分账去重、`role=2` 店铺明细及订单实付金额口径；按 `sharing_time` 自然日和店铺聚合 |
| 预测打款收入、笔数 | `yshop_adapay_profit_sharing_order`、`yshop_adapay_profit_sharing_order_item`、`yshop_store_order`、`yshop_pay_receivable_payable_order` | 与订单结算管理一致选取订单当前有效分账记录；只取成功且存在 `role=2` 明细的订单；Service 计算预计打款日期后按预计日期和店铺聚合，金额累加店铺角色明细，笔数按订单去重 |
| 打款金额 | `yshop_adapay_profit_recipient_settlement_detail` | `recipient_type=SHOP_RECIPIENT(2)`、成功状态、`is_active_version=1`、未删除；按 `settle_date` 和快照 `shop_id` 汇总 `net_settle_amount` |

一次同步的步骤：

1. 校验日期范围、店铺 ID、租户以及当前用户的店铺数据范围，并获取该店铺同步锁。
2. 在事务内分别按目标范围读取原有结算日汇总、预计打款订单来源和实际打款日汇总。预计打款来源查询需要覆盖能映射到目标预计日期区间的分账日期；边界由现有日期计算器推导，不能固定假设“回看一天”，以覆盖周末和连续节假日。
3. 在 Service 中将预测来源按 `ProfitSharingSettlementDateCalculator` 计算并过滤预计日期；与另外两组按日结果以 `(shopId, businessDate)` 合并，缺失指标补零。只要任一来源有数据，就生成对应店铺日行。
4. 物理删除该租户、店铺、日期闭区间内旧投影，批量写入本次完整结果。没有任何来源的日期不写行，因此可以清理过期值。
5. 提交事务后返回重建行数及无店铺归属的成功打款流水数量。该数量只对可访问全租户店铺的管理员返回实际值；普通店铺用户返回 0，避免暴露其他店铺信息。若任何读取、计算或写入失败，事务回滚，旧投影继续可查；释放店铺锁。

业务日期使用 `Asia/Shanghai` 自然日；同步及列表的日期起止均包含。分账时间条件仍采用半开时间区间 `[startOfDay, dayAfterEnd)`。

## API 与权限变化

API、字段和错误语义见 [`contract-changes.md`](contract-changes.md)。保留现有汇总、明细 URL；汇总响应兼容扩展三项字段；新增同步端点。同步端点复用现有 `pay:profit-sharing-income:query` 权限，不新建权限点。

查询仍检查租户和当前用户可访问店铺范围。同步必须指定单一店铺及起止日期，并执行同样的数据范围检查；租户管理员和超级管理员沿用当前不限制店铺的规则。并发同步锁以租户和店铺为键，锁冲突返回可重试的业务错误，不允许两个同步交错覆盖同店铺投影。

## 数据库迁移、初始化与回滚

- 在 `backend/sql/migrations/` 新增 Flyway migration，按创建时最高版本分配版本号；不新增历史数据事实表字段。
- 新建 `yshop_pay_store_income_report_daily`，字段和索引定义见契约文档。新表声明 InnoDB、`utf8mb4` 和 `utf8mb4_0900_ai_ci`。唯一键为 `(tenant_id, shop_id, report_date)`；查询索引覆盖 `(tenant_id, report_date, shop_id)` 和 `(tenant_id, shop_id, report_date)`。
- 同步按钮及 API 复用 `pay:profit-sharing-income:query`；不新增权限数据，菜单路径不变。理由：该操作只重建可再生报表投影，不修改财务事实，也不触发外部调用；有权限查看报表的用户可刷新报表数据。
- 新投影在首次手工同步前为空。发布/启用后由有权限用户按店铺和历史期间执行同步；不在 Flyway 中做大批财务数据回填，也不调用 AdaPay。
- 回滚时移除同步按钮权限并回退 API/页面；投影表可删除或保留以便重新发布。删除投影不影响源订单、分账或收款人结算事实。不得删除既有业务流水。

## 风险与权衡

| 风险 | 处理 |
|---|---|
| 预计打款日期跨周末或节假日，源分账日期可能早于目标日期 | 用现有计算器确定来源日期回看边界；使用结算日历；覆盖连续非工作日边界验证 |
| 单次同步时间随区间和订单量增长 | SQL 侧聚合原收入及实际打款；预计打款只读取当前有效记录并批量计算；实现时核对执行计划和最大请求耗时，必要时再引入异步任务而不改变汇总 API 语义 |
| 本地结算采集尚未覆盖某日 | 不调用远端补数；该项显示 0。全租户管理员可看到该期间未关联店铺的成功流水数量；财务按现有收款人结算采集流程补齐后再次同步 |
| 切换到独立投影后未同步范围显示为空 | 发布说明需提示先对需要查看的店铺和期间执行同步；重复同步可安全重建 |
| 日历配置或源事实变化后投影过期 | 同步按当前本地源表和当前结算策略重算所选范围；不自动改写未同步日期 |

## 验证要求

- 用数据库 fixture 核对三类来源能按各自日期合并到同一 `(tenant, shop, date)` 行，且金额、笔数符合业务规则。
- 验证重复同步、无源数据清理、事务异常回滚、并发锁、店铺权限及租户隔离。
- 验证预估打款日期的 T+1、D+1、周末和连续节假日映射。
- 验证汇总 API 只查投影表；同步及明细不发起 AdaPay 请求。
- 后端按 pay-biz 模块测试/构建约定验证；管理端执行 `pnpm ts:check` 和 `pnpm build:prod`，并完成同步交互 E2E。
