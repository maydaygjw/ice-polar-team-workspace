# 活动游戏模式技术设计

## 模块影响

- `backend/yshop-module-activity`：活动模式扩展、游戏配置管理、期次游戏快照、用户游戏进度与关卡结算 app-api。
- `admin`：复用现有活动模板管理页面承载游戏配置维护弹窗、游戏模式和逐关奖品编辑，不新增独立菜单页。
- `h5`：活动页游戏入口，改造现有 `/game.html` 跳跃演示接入活动、会话、关卡结算和中奖展示。
- `governance/CONTRACTS.md` 与本功能契约：记录 API、数据库和权限增量。
- `miniapp`：不在本期范围。

## 关键决策

### 游戏目录与运行时

不新增游戏目录表。复用 `yshop_activity_template` 保存游戏配置记录，通过新增记录类型区分“活动模板”和“游戏配置”；管理员手动填写展示名称和启用状态，后端按稳定映射保存 `gameCode`：`企业蓄力跳跃` → `ENTERPRISE_JUMP`。当前使用 H5 企业蓄力跳跃玩法和服务端数字记忆挑战，不上传游戏代码，也不提交关卡脚本或可执行配置。活动模板的 `gameId` 指向同表中的游戏配置记录，期次快照保存内部代码和展示名称，避免名称变更或停用改写历史期次。

历史 `MEMORY`、`SUM`、`ORDER` 配置继续按原有数字挑战规则运行。新建的手动命名配置使用五位数字记忆挑战；共享的会话、报名校验、进度推进、奖品结算放在活动服务。H5 跳跃画布承担操作体验，服务端校验挑战答案，不校验 Canvas 物理过程；如需将跳跃操作本身作为兑奖判定，后续需增加可服务端复核的操作凭据。

  现有接口沿用 `drawMode` 字段，扩展值 `3=GAME`；不重命名为 `activityMode`，避免影响已有模板、期次和客户端契约。新 DTO 可增加 `gameId`、`gameCode`、`gameName`，展示名称仍为“活动模式”。

### 游戏会话和结果判定

每个期次报名记录最多创建一个游戏会话。进度字段和关卡幂等结果 JSON 增加在现有 `yshop_activity_registration` 报名记录中；`start` 重试返回既有进度，进行中的会话继续当前关，失败或完成后返回最终结果，不重新开局。此设计保证重复进入和网络重试不会重置状态，也不新增游戏会话表。开始会话时要求报名开放；会话开始后即使报名关闭，也允许该会话继续到终局，避免中断正在进行的游戏。若业务需要每次抽奖机会对应一局，需另行调整进度和重开规则。

服务端通过锁定报名行串行处理关卡提交，并校验服务端保存的数字挑战答案；不得接受客户端直接传入的“成功”、最高关卡、奖品 ID 或用户 ID 作为结算依据。每关提交包含 `requestId`，已处理请求重放原结果。失败结果会终止当前会话；通过结果必须匹配挑战答案。

### 单奖品结算

关卡 1–3 分别绑定一个期次奖品快照。当前关通过且尚有下一关时只推进进度，不创建中奖记录；当前关失败或第 3 关通过结束游戏时，在本次 `game/submit` 事务中选取最高已通过关卡的奖品并返回中奖结果。失败时该奖品是失败关的上一已通过关奖品；第 1 关失败不生成中奖记录；三关全部通过时选取第 3 关奖品。结算最多写一条现有 `ActivityWinnerDO`，兑奖继续使用现有中奖兑奖服务，中奖通知和后台中奖管理继续使用现有记录。

结算事务内通过期次奖品的原子库存更新校验份数，库存成功后创建中奖记录并增加期次中奖人数。奖品库存不足时游戏仍结束，但不创建中奖记录、不替换为其他关奖品；H5 展示奖品库存已用完的结果。单人限中规则沿用期次快照；若用户已有效中奖，会话照常结束但不创建第二条中奖记录。

## 主流程

1. 活动管理员在现有活动管理页面打开游戏配置入口，手动填写游戏展示名称并设置启用状态；后端按 `企业蓄力跳跃` → `ENTERPRISE_JUMP` 映射保存代码。
2. 管理员创建游戏模式模板，选择启用的游戏，并为三关各选一个活动奖品。服务端校验租户归属、游戏可用及三关配置完整。
3. 生成期次时复制游戏内部代码/名称和逐关奖品快照。期次生命周期仍使用活动报名开关；游戏模式不进入定时开奖或后台统一开奖。
4. 已报名用户在活动开放期间调用 `start`。服务端创建或返回其唯一会话，并返回当前游戏类型、关卡和策略生成的挑战数据。
5. H5 渲染三关跳跃玩法并提交当前关卡结果。服务端验证挑战答案并推进下一关，或结束会话并结算最高已通关关卡奖品。
6. 有中奖记录时复用现有 `/activity/period/my-result`、中奖码、`claimStatus` 和 `POST /activity/period/claim` 兑奖接口；H5 的自动发放奖品展示“立即兑奖”操作，线下兑奖展示企微联系指引。未中奖或无库存时返回终局结果，不调用兑奖规则。

## 契约变化

详见 [contract-changes.md](contract-changes.md)。管理端 UI 及 H5 状态详见 [ui-ux-design.md](ui-ux-design.md)。

模板校验、周期边界计算和开奖入口均须显式支持 `drawMode=3`：游戏模式不要求 `drawTime`，周期推进按报名结束时间计算；自动/手动开奖仅接受模式 1，即时抽奖仅接受模式 2。活动模板查询和游戏配置查询共用模板表时必须按记录类型隔离，活动期次生成只接受活动模板类型。

## 风险与待确认决策

- 跳跃演示的 Canvas 操作不由服务端复核，只有数字挑战答案由服务端校验。若兑奖规则要求验证跳跃操作本身，需要另行设计可服务端复核的关卡凭据。
- 每条报名记录一局是本设计的默认值；需求目前没有定义游戏模式是否消耗 `drawChances` 或是否可重复开局。
- 同一活动奖品能否绑定多个关卡需确认；本设计按允许重复绑定处理，但每局只结算一次最高通过关卡奖品。
- 关卡奖品库存不足时不降级给前一关或其他奖品；该行为需产品确认。
- 首期复用 H5 跳跃演示作为一种游戏需要改造为可服务端验证的流程；若判定机制无法落地，应先缩减首期游戏清单。

## 迁移与回滚

不新增任何业务表。升级脚本新增 `backend/sql/upgrade-2026-10-15-activity-game-mode.sql`，仅向活动模板和报名表增加记录类型、游戏代码/引用及游戏进度字段，并向奖品关系/快照增加关卡编号；回滚删除新增字段和索引。部署回滚前需先停用游戏模式模板及期次。历史模板默认记录类型为活动模板、默认模式保持 1；历史报名的游戏进度为空。
