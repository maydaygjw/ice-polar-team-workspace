# 商圈排名竞价（二期）— Requirements Spec

承接一期 `bidrank-auction`。二期先实现“能查看、能报名、能支付、能结算、能展示”的最小闭环，不追求完整竞价系统。

本期只交付 backend + admin API，不做小程序页面。

## Scope

二期以一个周期实例为单位完成以下流程：

1. 系统生成当前周期实例，记录竞拍开始、结束、尾款截止和生效日期。
2. 商家查看本商圈当前活动和档位。
3. 商家在某个档位、某个门店首次提交出价；后续可在同一档位加价，但不能切换到其他档位。
4. 商家支付预付，再在截止前支付尾款。
5. 结算按最终出价降序、尾款支付完成时间升序取前 `slot_count` 个门店作为中标店。
6. 中标结果通过一期的 `StoreShopSortApi` 写入 `yshop_store_shop_sort`。
7. admin 查看出价单和中标结果。

## 交付边界

- **本期**：周期实例、基础 app-api、首次出价与同档加价、预付/尾款、简单结算、未中标退款、通用排序结果写入、admin 出价单/结果查询。
- **明确不做**：并发锁、重复请求协调、实时最低入围价、价格栈、复杂竞价策略、运营手工干预、退款重试/对账、支付多渠道抽象、小程序页面。
- **后续补充**：在不改变订单和排序契约的前提下，再增加实时竞争展示、价格栈、并发控制和更完整的财务状态机。

## 角色与用例

| 角色 | 用例 |
|------|------|
| 商家（app-api，未来由小程序/H5 调用） | 查看当前活动和档位；为门店报名出价；支付预付和尾款；查看自己的出价单 |
| C 端用户 | 门店列表按有效排序结果展示中标店铺 |
| 平台运营（admin） | 查看出价单；查看周期结算结果 |
| 系统 | 生成周期实例；到期结算；写入排序；发起未中标退款 |

## 简化业务规则

1. 一个周期、一个门店只能有一笔出价单；首次出价选择一个档位，上一笔预付支付成功后，后续只能更新同一 `rank_id`，不能切换档位。
2. 首次出价金额不得低于档位 `start_price`；后续加价必须高于当前出价加 `min_increment`。每次加价更新同一出价单，并写入 `yshop_bid_order_his`。
3. 出价成功后生成预付单；预付成功后才能支付尾款。
4. 每次加价只支付预付差额；尾款金额 = `bid_price - deposit_amount`，超过尾款截止时间不再接受尾款。
5. 结算只处理已付全款的出价单，按 `bid_price` 降序、`final_pay_time` 升序、`id` 升序取前 `slot_count` 个；不足名额时剩余位置空置。
6. 中标出价单置为“已生效”，经 `StoreShopSortApi.upsert` 写入通用排序结果，`sourceCode="bidrank"`，`sourceRecordId=cycleId`。
7. 已付全款但未中标的出价单发起全额退款；退款失败先记录失败，不在本期设计自动重试。
8. 未付预付的出价单在结算时置为“已作废”；已付预付但未付尾款的出价单发起预付退款，退款成功置为“已退款”，失败记录日志并置为“已作废”。
9. 商圈、门店、租户、部门仍按一期规则隔离；排序表由 store 模块负责派生 `dept_id`。
10. 排序展示直接读取 store 模块拥有的通用排序结果，不再使用 `BidRankSortApi` 或 `bid_shop_sort`。

## API 需求

### App API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/app-api/bidrank/auction/current?businessRegionId=` | 当前周期活动和档位 |
| POST | `/app-api/bidrank/bid` | 按 `cycleId + rankId + storeId + price` 首次出价或在同一档位加价，返回本次预付支付参数 |
| POST | `/app-api/bidrank/final-pay` | 按 `bidOrderId` 支付尾款，返回尾款支付参数 |
| GET | `/app-api/bidrank/my-order/page` | 查询当前租户/用户自己的出价单 |

本期不提供档位实时竞争状态、最低入围价和价格栈接口。

### Admin API

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| GET | `/admin-api/bidrank/order/page` | `bidrank:order:query` | 出价单列表 |
| GET | `/admin-api/bidrank/order/result` | `bidrank:order:query` | 周期中标结果 |

## Admin 要求

- 监控页只展示出价单、支付状态、周期状态和结算结果。
- 本期不做实时价格栈、刷新抢位、人工改价和人工改中标结果。
- 菜单挂在一期 `bidrank` 菜单树下，新增权限 `bidrank:order:query`。

## 验收标准

1. 可生成并查询当前周期实例和档位。
2. 商家可为门店选择一个档位出价，并在同一档位继续加价；切换档位的请求被拒绝。
3. 预付成功后可以在截止前支付尾款，截止后被拒绝。
4. 结算按最终出价降序、尾款支付完成时间升序取前 `slot_count` 个，并写入 `StoreShopSortApi`。
5. 未中标全款出价单能发起退款；未付清出价单被作废。
6. admin 可查询出价单和中标结果。
7. 门店列表能读取 `yshop_store_shop_sort` 的有效结果。

## Assumptions

- 只做 backend + admin，不做小程序页面。
- 本期不保证并发出价下的公平性；重复请求和并发冲突以数据库约束/业务错误结束。
- 本期支持同一档位的基础加价，但不实现实时最低入围价、价格栈和并发公平性。
- 支付通过 `pay-api` 的最小下单/退款能力接入，支付渠道继续由 pay 模块现有配置决定，bidrank 不感知渠道。
- 支付通知沿用现有 Redis Stream；仅增加足够区分 `bizType="bidrank"` 的字段，不展开渠道适配重构。
- 排序结果写入使用一期已经落地的 `StoreShopSortApi`，不新增 bidrank 排序接口。
