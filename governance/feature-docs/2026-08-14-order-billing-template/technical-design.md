# 技术设计 — 订单计费模板与应收应付

## 模块影响

| 模块 | 变更 | 职责 |
|---|---|---|
| `yshop-module-pay-api` | 修改 | 新增通用计费、重算和 AdaPay 转换的内部 DTO/API。 |
| `yshop-module-pay-biz` | 修改 | 管理计费项、模板和应收应付；完成模板匹配、金额分配、快照和 AdaPay 适配。 |
| `yshop-module-order-api` | 修改 | 对外提供结算金额快照及受控订单属性读取/校验能力。 |
| `yshop-module-order-biz` | 修改 | 订单确认收货后幂等触发通用计费；固化平台补贴字段；计费失败不回滚订单状态。 |
| `yshop-module-store-api` | 复用/修改 | 提供门店商圈、标签和绑定收款人查询。 |
| `admin` | 修改 | 新增计费项、计费模板、应收应付三个财务页面，替代旧店铺分账计费规则入口。 |
| `backend/sql` | 修改 | 新增配置与应收应付表，扩展订单和 AdaPay 分账表，增加菜单权限。 |

## 设计决策

### 1. 通用计费与支付渠道解耦

应收应付是订单财务事实，不放入 AdaPay 专属表中。所有已支付订单在确认收货时先生成通用应收应付；AdaPay 仅在通用计算成功后，将主体汇总映射为现有分账订单及明细。

这一边界避免微信、支付宝等非 AdaPay 订单依赖 AdaPay 状态机，也为后续其他分账渠道保留统一输入。

### 2. 复用安全的现有表，不强行复用旧规则表

继续复用：

- `yshop_adapay_profit_recipient`：收款主体与 AdaPay Member/结算账户。
- `yshop_adapay_profit_sharing_order`：AdaPay 分账执行主记录。
- `yshop_adapay_profit_sharing_order_item`：AdaPay 实际分账明细。
- 现有门店、商圈、门店标签及门店收款人绑定关系。

`yshop_adapay_profit_sharing_rule` 不继续承载新配置。该表是“店铺 + 固定角色 + 比例总和 100%”模型，新需求是“商圈 + 标签 + 动态计费项 + 不同基数”，复用会导致字段语义污染和历史兼容风险。旧规则不迁移、不再用于新订单，但暂不删表。

### 3. 订单模块拥有金额口径和字段安全边界

Pay 模块不直接拼接订单表 SQL。Order API 返回标准化快照：

- `beforeCouponAmount`
- `discountAmount`
- `afterCouponAmount`
- `platformSubsidyAmount`
- 经校验的订单属性名与金额值

“校验字段”仅允许查询固定的商户订单表，先验证字段标识符格式，再通过数据库元数据或无数据查询验证字段存在且是数值类型。运行时只读取已通过同等校验的字段，禁止传入表名、表达式或 SQL 片段。

### 4. 匹配必须稳定可审计

非默认模板的候选条件为同租户、同商圈、启用中，且标签为空或门店包含该标签。排序固定为：

```text
priority DESC, template_id ASC
```

无候选者时查询本租户启用的全局默认模板。成功记录保存模板 ID 及名称快照，既不依赖后续配置，也不需要独立模板版本表。

### 5. 计算与分配分两步

```text
allocatable = beforeCoupon - discount + platformSubsidy

percentage theoretical = round(base * percentage / 100, 2, HALF_UP)
attribute theoretical  = round(orderAttribute, 2, HALF_UP)
```

模板明细参数按计费项类型条件生效：`ORDER_PERCENTAGE` 必须提供 `baseType` 和 `percentage`；`ORDER_ATTRIBUTE` 不提供这两个参数，直接将计费项绑定的订单属性值作为理论金额输入。管理端隐藏无关控件，服务端按计费项类型拒绝不匹配的参数，避免同一明细同时存在两套金额口径。

1. 先计算所有模板明细的理论金额。
2. 非商家明细按 `sort ASC, line_id ASC` 分配：`actual = min(theoretical, remaining)`。
3. 当 `actual < theoretical` 时记录差异；当前剩余归零后，后续非商家明细的实际金额为 0。
4. 商家主体的最终实际金额等于非商家分配后的剩余。显式商家计费项只作为该金额内的明细归类；若其理论合计超过商家最终金额，同样按明细顺序截断，不增加整单总额。未被显式商家项归类的部分作为“商家剩余”明细。
5. 按最终收款主体汇总，并校验主体汇总合计与可计算金额完全相等。

理论与实际存在差异不是失败，主记录状态为 `SUCCESS_WITH_DIFFERENCE`。只有缺少模板、字段错误、固定收款人失效、可计算金额为负数或总额校验不平时才是 `FAILED`。

### 6. 业务状态与财务计算隔离

确认收货事务只负责将订单变为已收货/待评价。通用计费在独立事务中执行：即使配置或数据异常，也写入 `FAILED` 主记录而不抛出导致订单状态回滚的异常。

以 `(tenant_id, order_id)` 唯一约束保证触发幂等。失败重算锁定主记录，替换失败明细并增加重算次数；成功和成功有差异状态不允许重算。

### 7. AdaPay 作为下游适配器

对 AdaPay 已支付订单：

1. 通用计费成功后读取主体汇总。
2. 校验所有非零主体均有启用且已绑定结算账户的收款人；商家未绑定时保持待配置，不调用 AdaPay。
3. 创建或更新现有 `yshop_adapay_profit_sharing_order`，`calculation_type` 新增“通用计费模板”。
4. 每个主体汇总映射为一条 `yshop_adapay_profit_sharing_order_item`，保存通用主体汇总关联和收款人快照。
5. 模板明细勾选项对应的收款主体汇总为手续费承担方，写入 `fee_bearer=1` 并映射到 AdaPay 明细的 `fee_flag=1`；同一收款人的多条明细先合并再保留一个标记，其余主体为 0。
6. 后续仍使用现有 AdaPay 延迟分账状态机、日终任务、重试和失败回退机制。

旧 `role` 与 `fee_bearer_role` 保留供历史数据展示；新模型以收款人/主体汇总 ID 为路由依据，不再依赖固定四角色枚举。

## 核心流程

### 订单确认收货

```text
订单状态 -> 已收货/待评价
  -> 幂等请求 BillingSettlementApi.calculate(orderId)
      -> 读取订单金额、商圈、标签和属性
      -> 匹配商圈模板 / 全局默认模板
      -> 计算理论金额
      -> 按顺序分配非商家金额
      -> 剩余金额归商家
      -> 写入计费明细 + 主体汇总 + 快照
      -> AdaPay 订单且收款人完整：转换为现有待分账记录
```

### 失败重算

```text
财务点击重算
  -> 校验记录属于当前租户且状态为 FAILED
  -> 加锁并重新匹配当前有效模板
  -> 成功：替换明细/汇总并固化快照
  -> 失败：保留 FAILED，更新错误原因和重算次数
```

## 部署与切换

1. 部署新表、订单补贴字段、API 和管理页面，通用计费开关保持关闭。
2. 财务为每个需要切换的租户配置并启用全局默认模板，完成订单属性校验。
3. 开启通用计费，新确认收货订单不再读取 `yshop_adapay_profit_sharing_rule`。
4. 保留旧规则表和历史 AdaPay 分账数据，不做规则数据迁移。
5. 回滚时关闭通用计费开关并恢复旧计算路径；不删除已生成的通用应收应付数据。

## 风险与控制

| 风险 | 等级 | 控制 |
|---|---|---|
| 金额口径与订单实际字段不一致 | 高 | Order API 统一输出快照；契约测试覆盖券前、券后、优惠和补贴。 |
| 计费项字段形成 SQL 注入 | 高 | 固定订单表、标识符校验、元数据验证，禁止未校验字段进入查询。 |
| 计费失败阻断订单完成 | 高 | 订单状态与计费事务隔离，失败落库并提供重算。 |
| 多标签命中结果不稳定 | 高 | `priority DESC, id ASC` 且固化命中模板快照。 |
| 分配金额超出可计算金额 | 高 | 顺序截断，保存理论/实际差异，最终执行总额平衡校验。 |
| 收款人在配置后失效 | 高 | 模板保存时和订单计算时双重校验；商家缺收款人只阻断 AdaPay。 |
| 新旧计费引擎重复生效 | 高 | 切换开关互斥，通用计费启用后不再读取旧规则。 |
| 历史金额被配置变更污染 | 高 | 成功记录快照化且不可重算，历史 AdaPay 数据不迁移。 |
