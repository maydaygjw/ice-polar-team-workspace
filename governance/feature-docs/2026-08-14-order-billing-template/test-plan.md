# 测试计划 — 订单计费模板与应收应付

## 环境前置

- 本地或测试环境，禁止使用生产和个人数据。
- 至少两个租户，每个租户包含财务角色；平台超管可切换租户。
- 测试租户内准备两个商圈、多个门店、多选门店标签和已启用/已停用收款人。
- 准备 AdaPay 和非 AdaPay 已支付订单，允许进入确认收货状态。
- 订单数据能覆盖券前、优惠、券后、平台补贴、餐盒费和配送费。
- Mock Token 仅在测试环境使用，用户必须拥有对应菜单权限。

## 单元与集成测试

| ID | 场景 | 核心断言 |
|---|---|---|
| UNIT-01 | 比例项按券前计算 | 指定基数 × 比例，单项 HALF_UP 到分。 |
| UNIT-02 | 比例项按券后计算 | 基数为用户实际支付金额，不使用可计算金额。 |
| UNIT-03 | 订单属性项 | 读取已校验数值，负数/空/非数值进入 FAILED。 |
| UNIT-04 | 可计算金额 | `券前 - 优惠 + 平台补贴`，补贴为空按 0。 |
| UNIT-05 | 顺序足额分配 | 非商家项实际=理论，剩余归商家，总额平衡。 |
| UNIT-06 | 顺序不足分配 | 当前项取全部剩余，后续项为 0，主记录为 SUCCESS_WITH_DIFFERENCE。 |
| UNIT-07 | 显式商家计费项 | 明细被保留，与商家剩余合并到一个主体汇总，不超出可计算金额。 |
| UNIT-08 | 多标签模板匹配 | 优先级高者胜出；同优先级选 ID 最小者。 |
| UNIT-09 | 商圈无模板 | 使用本租户全局默认模板。 |
| UNIT-10 | 幂等触发 | 同租户同订单重复触发只有一条主记录。 |
| UNIT-11 | 失败重算 | 仅 FAILED 允许，使用最新模板；成功后不可再重算。 |
| UNIT-12 | AdaPay 转换 | 主体汇总一对一生成分账明细，手续费承担方唯一，金额合计一致。 |

## API 测试

| ID | 场景 | 断言 |
|---|---|---|
| API-01 | 新增比例计费项 | HTTP/通用响应成功，本租户列表可见。 |
| API-02 | 重复计费项名称 | 返回 `BILLING_ITEM_NAME_EXISTS`，无重复数据。 |
| API-03 | 订单字段校验 | 合法金额字段成功；非法标识符、非存在字段、文本字段失败；不返回数据样本。 |
| API-04 | 删除已引用计费项 | 返回 `BILLING_ITEM_IN_USE`，原数据不变。 |
| API-05 | 创建全局默认模板 | 商圈/标签为空，模板和明细原子保存。 |
| API-06 | 创建第二个启用默认模板 | 返回 `BILLING_TEMPLATE_DEFAULT_EXISTS`，并发请求也不能突破唯一性。 |
| API-07 | 模板重复计费项 | 返回 `BILLING_TEMPLATE_ITEM_DUPLICATED`，不部分保存。 |
| API-08 | 模板引用跨租户商圈/标签/收款人 | 请求被拒绝，不泄露他租户名称和详情。 |
| API-09 | 无默认模板的订单计算 | 订单状态成功变更，应收应付为 FAILED，错误为 `BILLING_TEMPLATE_NOT_MATCHED`。 |
| API-10 | 非 AdaPay 订单确认收货 | 生成通用应收应付，不生成 AdaPay 分账记录。 |
| API-11 | AdaPay 订单且收款人完整 | 生成通用记录和唯一待分账记录。 |
| API-12 | AdaPay 订单的商家无收款人 | 通用计算成功，`adapayReady=false`，不调用分账。 |
| API-13 | 重算失败记录 | 权限、租户和状态校验正确，重算次数增加，成功后快照固化。 |
| API-14 | 已成功记录重算 | 返回 `BILLING_RECORD_NOT_RECALCULABLE`，金额和明细不变。 |
| API-15 | 不同租户使用同订单号 | 各自独立生成，查询不串租户。 |
| API-16 | 无菜单权限 | 返回权限不足，不产生配置或重算副作用。 |

## 回归范围

- 用户、管理员和自动确认收货。
- 订单状态、积分、成长值和评价入口，确保计费失败不阻断原流程。
- AdaPay 待分账创建、日终分账、失败重试和虚拟余额回退。
- 历史 AdaPay 分账订单/明细查询与展示。
- 分账收款人创建、启停、门店绑定和租户隔离。
- 门店标签多选维护和商圈数据权限。

## 验证命令

```bash
(cd backend && mvn clean test)
(cd admin && pnpm ts:check && pnpm lint:eslint && pnpm build:prod)
(cd governance/e2e && npm test)
```

若全量后端测试耗时过长，先执行 pay/order/store 相关模块及依赖的定向测试，再在交付前完成全量验证。

## 测试数据清理

- 使用测试租户与带固定前缀的计费项/模板名称。
- 测试后通过管理页/API 停用或删除未被引用配置。
- 已生成的应收应付是订单财务快照，不通过 UI 删除；仅对明确的测试订单按环境清理流程处理。
- 任何数据库清理必须限定测试租户和明确主键，并在 `test-notes.md` 记录。
