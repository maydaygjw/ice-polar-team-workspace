

# Feature: 订单计费模板与应收应付

## Scope

### In Scope

1. 维护租户级计费项，支持“订单比例”和“订单属性”两种计费方式。
2. 维护租户级计费模板，按“商圈 + 可选门店标签 + 优先级”匹配，并提供唯一的租户全局默认模板。
3. 模板明细配置计费项、计费基数或订单属性、比例、收款主体和分配顺序。
4. 订单确认收货时，不区分支付渠道生成通用应收应付记录。
5. 逐项保存理论金额与实际分配金额，再按收款主体汇总；商家取得非商家主体分配后的剩余金额。
6. 应收应付计算失败不阻止订单确认收货；管理员可对失败记录重新计算。
7. AdaPay 作为后续分账执行渠道，消费通用应收应付的主体汇总结果。
8. 管理后台新增计费项管理、计费模板管理和应收应付管理页面。

### Out of Scope

- 退款后的应收应付冲销、分账回退和重新分配。
- 平台补贴的计算和来源；订单系统负责在订单中固化该金额，本功能只读取。
- 商家端或小程序维护计费配置、查看应收应付。
- 新增商户类型基础资料；本期复用现有门店标签。
- 将旧店铺级 AdaPay 分账计费规则自动转换为新模板。

## Use Cases

### UC-1: 财务维护计费项

- 角色：租户管理员、财务人员、平台超管。
- 目标：统一定义可被计费模板复用的费用项。
- 主流程：
  1. 用户新增计费项，填写名称并选择计费方式。
  2. 订单属性类型还需配置订单字段。
  3. 用户点击“校验字段”，系统确认字段存在于商户订单数据且可用于金额计算。
  4. 用户启用计费项，供模板选择。

### UC-2: 财务维护计费模板

- 角色：租户管理员、财务人员、平台超管。
- 目标：为指定商圈及门店标签配置收款分配规则。
- 主流程：
  1. 选择全局默认模板，或选择商圈、可选门店标签和优先级。
  2. 添加计费项；订单比例类型选择券前/券后并填写比例，订单属性类型直接使用计费项中的字段。
  3. 为每个计费项选择固定收款主体或“当前商家”，并设置分配顺序。
  4. 选择支付通道手续费承担主体，默认为平台收款主体。
  5. 保存并启用模板。

### UC-3: 订单确认收货后生成应收应付

- 角色：系统。
- 目标：固化订单在当前计费配置下的费用明细和主体应收。
- 主流程：
  1. 已支付订单进入确认收货状态。
  2. 系统按商圈、门店标签和优先级选择模板；未命中商圈模板时使用租户全局默认模板。
  3. 系统计算可计算金额和各计费项理论金额。
  4. 非商家计费项按分配顺序使用可计算金额，不足时当前项取剩余金额，后续项取 0。
  5. 剩余金额归当前商家；模板中显式归属商家的计费项作为商家金额的明细分类，不增加整单可分配总额。
  6. 系统按收款主体汇总实际分配金额并固化计算快照。

### UC-4: 财务查看与重算

- 角色：租户管理员、财务人员、平台超管。
- 目标：追溯订单计费结果并处理计算失败。
- 主流程：
  1. 用户按订单号、门店、商圈、状态和确认收货时间筛选。
  2. 查看订单金额口径、命中模板、逐项计算过程、主体汇总和差异备注。
  3. 对计算失败的记录点击“重新计算”，按当前最新有效配置重算。

### 业务配置示例

商圈 `NT005`、不选门店标签的模板可配置为：

| 计费项 | 计费方式 | 基数/属性 | 配置 | 收款主体 |
|---|---|---|---:|---|
| 服务费 | 订单比例 | 券前 | 8% | 平台 |
| 餐盒费 | 订单属性 | `box_fee` | 属性金额 | 平台 |
| 用户配送费 | 订单属性 | `delivery_fee` | 属性金额 | 当前商家 |
| 技术服务费 | 订单比例 | 券后 | 2% | 技术平台 |
| 营销渠道费 | 订单比例 | 券后 | 4% | 营销方 |

`box_fee` 和 `delivery_fee` 为业务示例名，实际保存前必须通过商户订单字段校验。表格行顺序即非商家主体的金额分配顺序。

## Business Rules

### 计费项

1. 计费项名称在租户内唯一；同一模板不得重复引用同一计费项。
2. 计费方式只有：
   - 订单比例：由模板明细选择券前或券后基数并配置比例。
   - 订单属性：读取计费项绑定的商户订单金额字段。
3. 订单属性只允许来自商户订单数据，字段必须存在、可读取且为金额数值类型。
4. 被模板引用的计费项不可删除，可停用；停用后不允许新模板引用。

### 模板选择

5. 每个租户最多有一个启用的全局默认模板；默认模板不配置商圈和门店标签。
6. 非默认模板必须选择商圈，门店标签可不选。
7. 候选模板必须与订单同租户、同商圈，且模板标签为空或订单门店包含该标签。
8. 多个候选模板按优先级降序、模板 ID 升序选择；同优先级不随机，保证结果可重现。
9. 商圈内无候选模板时使用租户全局默认模板；全局默认模板不存在或已停用时计算失败。
10. 模板配置支付通道手续费承担主体，默认平台；仅在后续分账渠道需要时使用。

### 金额口径与分配

11. 券前金额：优惠券和折扣使用前的订单金额。
12. 券后金额：用户实际支付金额。
13. 可计算金额 = 券前金额 - 优惠金额 + 平台补贴金额。平台补贴由订单系统固化，无补贴时为 0。
14. 券前和券后是订单比例的仅有可选基数；可计算金额只用作整单实际分配上限和商家剩余金额的计算基础。
15. 比例允许 0% 至 100%；订单属性金额不得为负数。
16. 每个计费项独立按四舍五入保留到分。
17. 非商家计费项按模板顺序分配：实际金额 = `min(理论金额, 当前剩余可计算金额)`。
18. 金额不足时，当前项可部分分配，后续项为 0；保存理论金额、实际金额和“订单可计算余额不足”备注。
19. 非商家主体分配后的全部剩余金额归当前商家；商家金额可为 0，不得为负。
20. 同一收款主体的多个计费项在主体汇总中合并；计费明细仍逐项保留。
21. 主体实际分配合计必须等于可计算金额。

### 应收应付与历史数据

22. 每个最终收款主体保存一条主体汇总：对平台清算资金是应付，对收款主体是应收，不生成用户侧记录。
23. “当前商家”运行时解析为订单门店绑定的收款人；未绑定时仍生成商家应收，但暂不可执行 AdaPay 分账。
24. 非商家主体必须关联启用中的分账收款人；模板保存和订单计算时均校验。
25. 计算成功的记录不可重算，并固化订单金额、命中模板、计费项和收款主体快照。
26. 只有计算失败记录允许重算；重算使用当前最新有效模板。
27. 模板修改只影响尚未成功生成应收应付的订单，不改变历史成功记录。
28. 订单确认收货重复触发时不得重复生成应收应付。
29. 金额被截断且有差异时，状态为“成功但有差异”，可继续用于分账，不允许人工重算。
30. 计费失败不回滚订单确认收货，也不允许进入后续分账。

## Frontend Requirements

| 页面 | 能力 |
|---|---|
| 计费项管理 | 列表、搜索、新增、编辑、启停、删除、订单字段校验。 |
| 计费模板管理 | 列表、新增、编辑、启停；维护商圈、标签、优先级、手续费承担主体和可排序计费明细。 |
| 应收应付管理 | 分页、筛选、计算状态、差异/失败原因、明细弹窗、失败记录重算。 |

- 三个页面均位于“财务管理”。
- 商圈、门店标签和收款主体使用现有后台数据源。
- 超管可切换租户；租户管理员和财务人员只能访问本租户数据。
- 商家管理员和 C 端不新增入口。

## Edge Cases

- 门店同时命中多个标签模板：按优先级降序、模板 ID 升序选择。
- 订单没有门店标签：可命中同商圈的无标签模板，否则回退到全局默认模板。
- 订单属性不存在、值为空、非金额或为负数：计算失败并保存明确原因。
- 平台补贴为空：按 0 计算；券前金额或优惠金额缺失时计算失败。
- 可计算金额为 0：各主体实际金额均为 0，有非零理论金额时标记差异。
- 可计算金额小于 0：计算失败。
- 固定收款人在订单确认收货前被停用：计算失败，恢复或更换后可重算。
- 商家没有绑定收款人：应收应付计算成功，AdaPay 执行保持待配置。
- 失败记录重算时原模板已停用：重新执行完整匹配流程。
- 订单已有成功记录：重复确认或重算请求不改变任何金额。

## Acceptance Criteria

- [ ] 财务可维护租户内唯一命名的计费项，订单属性可被校验且不能越出商户订单数据。
- [ ] 财务可配置全局默认模板和商圈/标签模板，同一计费项在同一模板中不可重复。
- [ ] 模板按优先级降序、ID 升序稳定匹配，未命中时使用本租户全局默认模板。
- [ ] 已支付订单确认收货时，所有支付渠道均幂等生成应收应付。
- [ ] 可计算金额严格按“券前 - 优惠 + 平台补贴”计算，比例项只能选择券前或券后基数。
- [ ] 各计费项独立四舍五入到分，非商家项按顺序分配，不足时当前项取剩余、后续项取 0。
- [ ] 计费明细保留理论和实际金额，同一收款主体汇总合并，汇总合计等于可计算金额。
- [ ] 商家取得非商家分配后的全部剩余金额，未绑定收款人不影响应收应付生成。
- [ ] 金额不足产生“成功但有差异”状态和明确备注，仍可进入后续分账。
- [ ] 配置或数据错误产生“计算失败”记录但不阻止确认收货，修复后可使用当前有效配置重算。
- [ ] 成功记录固化模板、金额、计费项和收款主体快照，不受后续配置修改影响且不可重算。
- [ ] 租户数据隔离、菜单权限和超管租户切换符合现有治理规则。
- [ ] AdaPay 可从通用主体汇总生成现有分账订单明细，且收款人不完整时不执行分账。
- [ ] 旧店铺级分账计费规则不迁移、不再用于新订单，历史分账订单和明细保持不变。

## Assumptions

1. 订单系统能在确认收货前提供券前金额、优惠金额、券后金额和平台补贴金额快照。
2. 订单与门店、商圈的关系在计算时可可靠获取。
3. 现有门店标签为多选，因此使用优先级和稳定 ID 规则解决多模板命中。
4. “平台、技术平台、营销方”等非商家主体均通过现有“分账收款人管理”维护。
5. 本期不修改退款行为，也不对已生成的应收应付执行退款冲销。
