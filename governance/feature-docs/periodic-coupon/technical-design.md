# 技术设计 — 普通券与周期券（重新实现）

## 模块影响

| 模块 | 变更 | 说明 |
|---|---|---|
| `yshop-module-coupon-api` | 修改 | 新增券类型枚举及错误语义 |
| `yshop-module-coupon-biz` | 修改 | 商圈校验、发放窗口和周期领取校验、店铺范围匹配、重复领取、状态查询 |
| `backend/sql` | 修改 | 优惠券类型、发放起止时间和用户券有效期快照字段 |
| `admin/` | 修改 | 后台优惠券表单和列表展示 |

## 关键决策

1. 新增 `coupon_kind` 区分普通券和周期券，避免与现有 `coupon_type`（满减/折扣）混淆。
2. 新增 `issue_start_time`、`issue_end_time` 表示周期券的发放窗口。它们只负责判断“当前是否允许领取”。
3. 新增 `issue_cycle_days` 表示周期长度，必须为正整数。周期桶以 `issue_start_time` 为起点，按自然日每 `issue_cycle_days` 天切分；发放窗口末尾的不足完整周期部分归入最后一个周期。
4. 新增必填 `business_region_id`，一张优惠券只归属一个商圈；新增店铺范围字段，与现有商品范围字段分离：`shop_scope_type` 表示不限制、指定或排除，`shop_scope_values` 保存店铺 ID 集合。
5. 周期券固定使用 `expiration_type=2`（领取后有效期），并要求 `expiration_day > 0`。领取成功时将该关系的 `receive_time` 和模板 `expiration_day` 转换为关系表中的 `taking_effect_time`、`expiration_time` 并持久化；`taking_effect_time`、`expiration_time` 不用于发放窗口，也不承载发放时间。
6. 普通券继续保留现有固定时间、领取后天数和无限制时间选项；周期券不能选择普通券的其他有效期类型。
7. 所有券类型在发放时都生成有效期快照：
   - 固定时间：关系字段复制券模板的 `taking_effect_time`、`expiration_time`。
   - 领取后天数：关系字段分别写入 `receive_time` 和 `receive_time + expiration_day`。
   - 无限期：关系字段写入领取后的生效时间，`expiration_time` 为空。
8. 周期券在发放窗口内复用现有领券流程，并根据 `receive_time` 判断当前周期是否已经领取；同一用户同一周期重复领取失败，跨周期可再次领取。每次成功领券都新增一条关系并写入有效期快照。
9. 周期领取校验不新增 `period_date` 等周期字段或周期唯一索引；使用现有领取关系的 `receive_time` 查询当前周期记录，并通过现有事务/用户-券维度锁避免并发重复领取。
10. `getReceivedCount(couponId, uid)` 继续统计累计领取数量；配置了 `limitNumber` 时按累计次数限制，不按周期重置。周期内一次领取限制独立于累计上限。
11. 商圈和店铺范围校验：`business_region_id` 必须属于当前租户且通过数据权限校验；当前店铺必须属于该商圈后，才继续执行店铺范围判断。
12. 店铺适用性判断统一使用店铺范围字段：
    - `shop_scope_type=1`：不过滤所选商圈内的店铺，商圈内所有店铺适用。
    - `shop_scope_type=2`：当前店铺 ID 必须在 `shop_scope_values` 中，且属于所选商圈。
    - `shop_scope_type=3`：当前店铺 ID 不得在 `shop_scope_values` 中，且属于所选商圈。
13. 领券列表、用户券可用性、购物车优惠券计算和核销前校验必须使用同一套商圈和店铺范围判断，不能只在后台表单限制。
14. 每条领取关系通过现有 `is_used`、`receive_time`、`usage_time` 以及新增的有效期快照字段独立表达一张用户券；核销一条关系不会复用、重置或影响其他关系。
15. 用户券列表、购物车可用券和过期判断统一使用关系表的 `taking_effect_time`、`expiration_time`，不再通过模板 `expiration_day` 动态计算。
16. 周期券不新增定时任务；用户在页面领取时即时校验发放窗口、周期领取资格、商圈和店铺范围，避免预生成无主用户券。
17. 周期券固定 `get_type=0`，不生成兑换码，统一走页面领取接口。

## 兼容与风险

- 新字段默认普通券；历史数据和未升级客户端继续按普通券工作。
- 旧客户端创建周期券时若未传新字段，后端按普通券处理；后台新表单负责完整配置。
- 周期券的库存仍从优惠券 `number` 扣减；库存耗尽后发放窗口内也不可领取。
- 保留 `issue_cycle_days`；旧方案中的 `period_date` 和周期唯一索引不纳入本次重新实现。
- 领取关系仅增加用户券有效期快照字段，不改变领取、核销和多次领取关系逻辑。
- 旧单店铺数据继续按原 `shop_id` 语义兼容；新配置使用店铺范围字段表达全店铺、包含和排除模式。
- 历史优惠券的商圈按门店归属回填；无法从旧 `shop_id` 推导的记录使用当前租户默认商圈并记录迁移结果，不能保留空商圈。
