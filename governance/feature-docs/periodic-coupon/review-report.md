# Review Report — 普通券与周期券（重新实现方案）

## 结论

原审查结论因需求变更失效。本次仅完成重新实现方案的文档修订，代码尚未重新实现，暂不进入交付审查。

## 审查项

- 重新实现必须将 `couponKind` 与现有满减/折扣字段 `couponType` 分离，历史数据默认按普通券处理。
- 周期券使用独立的 `issueStartTime`/`issueEndTime` 作为发放窗口，并使用 `issueCycleDays` 切分领取周期。
- 同一用户同一周期只能成功领取一次，跨周期可以再次领取；不得增加 `periodDate`、周期唯一索引等周期字段，但需要在关系记录保存该张用户券的有效期快照。
- 用户券查询和有效性判断必须使用关系记录的 `takingEffectTime`/`expirationTime`，不能参与发放窗口判断或依赖模板 `expirationDay` 动态计算。
- 周期券只能使用 `expirationType=2` 和正数 `expirationDay`；管理端限制不能替代后端校验。
- 店铺范围必须支持不限制、指定多店铺和排除多店铺；领券、可用券查询和核销前校验必须保持一致，并执行租户/数据权限隔离。
- 优惠券必须绑定一个有效商圈；店铺范围只能选择该商圈下的店铺，商圈和店铺归属必须执行租户/数据权限校验。
- 周期券后端强制 `getType=0`，不生成兑换码，统一进入页面领取。
- 数据库升级脚本实现时需包含回滚语句，且不得修改基线初始化 SQL。

## 残余风险

1. 周期券库存沿用现有优惠券的全局 `number`，不会按发放窗口自动补充。
2. 周期券不支持兑换码入口；如未来需要扫码领取周期券，需要单独设计周期码语义。
3. 重新实现尚未执行真实数据库接口集成测试，领取关系有效期快照和迁移脚本需在测试库验证后再上线。
4. OpenAPI 静态快照尚未重新生成。
