# Review Report — 普通券与周期券

## 结论

通过实现审查，可进入交付前收尾。实现覆盖普通券/周期券配置、周期窗口校验、周期内领取限制、管理端配置和数据库迁移；没有加入已取消的前台展示开关。

## 审查项

- `couponKind` 与现有满减/折扣字段 `couponType` 分离，历史数据默认按普通券处理。
- 周期券由后端强制使用 `expirationType=2`，并固定每个发放周期每人限领 1 张，不能只依赖前端限制。
- 领取记录保存 `periodDate`，并用 `(coupon_id, uid, period_date)` 唯一索引防止同周期重复记录；领取入口使用事务，保存失败可回滚库存扣减。
- 周期券的领取窗口复用 `takingEffectTime`/`expirationTime`，周期桶按起始日期和 `issueCycleDays` 计算。
- 周期券后端强制 `getType=0`，不生成兑换码，统一进入页面领取。
- 数据库升级脚本包含回滚语句，未修改基线初始化 SQL。

## 残余风险

1. 周期券库存沿用现有优惠券的全局 `number`，不会按周期自动补充；如果业务需要“每天每店/每人固定配额”，应另行设计周期库存。
2. 周期券不支持兑换码入口；如未来需要扫码领取周期券，需要单独设计周期码语义。
3. 未执行真实数据库接口集成测试，迁移脚本需在测试库验证后再上线。
4. OpenAPI 静态快照尚未重生成。
