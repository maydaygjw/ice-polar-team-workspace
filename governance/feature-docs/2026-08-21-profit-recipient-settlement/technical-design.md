# 技术设计 — 分账收款人结算

## 模块影响

| 模块 | 变更 | 说明 |
|---|---|---|
| `yshop-module-pay-biz` | 新增 | 结算明细事实、采集任务、定时采集、汇总/明细查询和手工重拉接口 |
| `yshop-module-store-biz` | 修改 | 绑定/解绑分账收款人时写入不可变历史关系，并保存结算账户快照 |
| `yshop-module-pay-api` | 使用 | 复用现有收款人/支付领域能力；不新增跨模块业务 API |
| `admin/` | 新增 | 财务菜单、双 Tab 报表、采集状态和单日重拉交互 |
| `backend/sql` | 新增 | 4 张业务表的 DDL，以及菜单/权限初始化和回滚 |
| 外部依赖 | 升级/确认 | 使用已发布的 `pay-java-adapay 2.14.14-SNAPSHOT` 结算明细封装 |

## 关键决策

1. **本地事实优先**：AdaPay `SettleAccount.detail` 是到账事实来源；采集后保存本地，页面不实时访问外部系统。
2. **每日增量 + 单日重拉**：自动任务只处理前一日；手工重拉只接受单日，二者共用采集、幂等和错误处理逻辑。
3. **金额保留三列**：保存 `settle_amt`、`settle_fee_amt` 和 `settle_amt - settle_fee_amt`，汇总净到账金额使用第三列，不使用分账订单明细金额。
4. **收款人历史关系独立保存**：当前 `yshop_store_shop.profit_sharing_recipient_id` 只能表达当前状态，不能支撑历史查询；绑定事件需产生关系快照，旧结算账户不能因更换账户而丢失。
5. **双 Tab 隔离维度**：店铺 Tab 仅关联店铺级收款人及历史店铺关系；平台 Tab 仅关联平台级收款人，并按角色筛选。平台到账不按店铺拆分。
6. **采集任务可部分成功**：按收款人独立执行并记录结果；单项失败可重试，成功收款人的结果可发布，失败收款人继续使用最近一次成功活动版本。
7. **状态与到账分离**：所有 AdaPay 状态保留；只有 `succeeded` 产生成功到账汇总，采集任务状态单独表达外部拉取是否完整。
8. **不新增订单关联**：AdaPay 结算明细无订单号，报表明细展示结算账户到账记录，不伪造订单级归属。

## 流程

```text
每日调度 / 手工指定日期
        ↓
创建采集任务并锁定 tenant + settle_date
        ↓
读取当前及历史收款人账户快照
        ↓
逐收款人调用 querySettleDetail
        ↓
校验响应并按外部明细幂等写入本地事实
        ↓
更新收款人级结果和任务汇总
        ↓
管理端只读本地事实，按 Tab/周期/关系过滤汇总
```

## 查询实现边界

- 明细和汇总均使用 MyBatis-Plus DSL 查询本地结算事实；Mapper 不维护跨表 `EXISTS`、`UNION`、聚合和 XML 查询，历史绑定关系与当前状态由 Service 基于本地收款人/绑定历史快照判断。
- 日/周/月汇总在 Service 层完成分组、金额合计和分页。这样关系状态过滤与汇总使用同一套本地快照口径，避免 Mapper 中重复维护复杂 SQL；结算明细数据量增长后再单独评估预聚合方案。

## 数据模型增量

本需求明确涉及 DDL，新增以下 4 张表，字段级定义见 `contract-changes.md` 的“数据结构内容”：

- `yshop_adapay_profit_recipient_settlement_task`
- `yshop_adapay_profit_recipient_settlement_task_recipient`
- `yshop_adapay_profit_recipient_binding_history`
- `yshop_adapay_profit_recipient_settlement_detail`

现有 `yshop_adapay_profit_recipient`、`yshop_store_shop` 不新增业务字段；当前绑定字段继续服务于当前态，不作为历史关系的唯一来源。菜单和权限只做 `system_menu`、`system_role_menu` 数据初始化，不新增权限表。

### 结算明细事实

保存租户、收款人、Member、结算账户及名称/角色快照，避免当前收款人被禁用或删除后历史消失；保存 AdaPay 原始字段和计算后的净到账金额。每次采集生成批次号，事实记录保留采集版本并标记活动版本；同一收款人和结算日的完整成功响应在事务内切换活动版本，失败响应不改变活动版本。查询索引围绕租户、结算日期、收款人类型、角色、店铺和采集状态建立。

### 收款人绑定历史

关系记录保存：收款人 ID、Member ID、结算账户 ID、店铺 ID/名称、商圈 ID/名称、生效时间、失效时间和当前关系标记。解绑和换绑只关闭旧关系并新增关系，不修改旧记录。

### 采集任务

任务记录保存租户、目标结算日、触发来源、执行状态、开始/结束时间、收款人数、成功/失败数、明细数和错误摘要。相同租户和日期只能存在一个运行中任务。

## 幂等与失败处理

- 外部明细使用稳定组合键或内容指纹去重，重新拉取采用更新/插入，不重复累计。
- 每个收款人的响应按“完整成功”发布；空列表也是完整成功，表示该收款人该日活动明细替换为空。
- 重新拉取失败时保留最近一次成功事实，并将任务标记为失败或部分失败。
- 收款人缺少历史 Member/结算账户快照时，任务记录明确失败原因，不使用当前账户猜测历史数据。
- AdaPay 返回未知状态时保存原始状态并标记异常，不能默认为成功。

## 权限与安全

- 采集任务只在服务端执行，AdaPay 密钥不出现在管理端。
- 查询和重拉权限分开。
- 所有查询带租户条件；店铺 Tab 复用现有店铺范围校验。
- 卡号只保存/展示 AdaPay 返回的脱敏值，不返回完整银行卡号。

## 风险与权衡

| 风险 | 处理 |
|---|---|
| 平台到账无法拆到店铺 | 平台 Tab 不提供店铺维度，保留平台角色维度 |
| 历史关系无法完全回溯 | 上线前回填可推断关系；无法确定的日期标记关系不完整 |
| 外部接口逐收款人调用量较大 | 单日任务分收款人执行、记录失败并支持重拉；不在页面实时调用 |
| AdaPay 明细无唯一 ID | 采用账户、日期、类型、金额、手续费和状态等稳定字段组合/指纹去重，需以真实响应验证 |
| SDK SNAPSHOT 变更 | 锁定可用构建版本并在后端构建验证中检查方法签名 |

## 回滚与兼容

- 新表和菜单权限由独立升级脚本创建，提供逆序回滚语句。
- 删除报表菜单不会删除已采集的财务事实和历史绑定数据；数据回滚需单独审批。
- 不修改现有「店铺收入报表」、分账订单状态机和 C 端支付流程。
