# 活动推荐阶梯奖励技术设计

## 模块影响

- `backend/yshop-module-activity`：活动模板阶梯配置、期次阶梯快照、首次参加身份判定、期次推荐计数、奖励记录、自助兑奖与后台查询。
- `admin`：现有模板向导增加最后一步“推荐奖励”；原推荐抽奖/游戏机会设置保持不变；期次记录增加推荐奖励查询视图。
- `h5`：活动详情展示阶梯；当前用户结果展示该期计数和奖励记录；复用现有用户端兑奖交互。
- `governance/CONTRACTS.md` 与本目录契约：记录跨仓库 API、数据及权限变更。
- `miniapp`：不在本期范围。

## 关键决策

### 两套推荐机制保持隔离

继续保留模板字段 `inviteRegistrationChance` 及现有报名后增加当期抽奖/游戏机会的逻辑。新阶梯奖品采用独立模板配置、期次快照、进度和奖励记录；开关、计数和库存不互相影响。旧机会仍写入推荐人的 `drawChances`，新奖励不增加 `drawChances`。

### 阶梯配置和期次奖品快照分表保存

新增 `yshop_activity_template_referral_tier` 保存模板阶梯；每行关联奖品库 `prize_id`，并保存类型（`NEWCOMER` / `ORDINARY`）、人数门槛和独立推荐奖励份数。按租户、模板、类型、门槛建立唯一键。

期次生成时复制至 `yshop_activity_period_referral_tier`，并冻结奖品名称、图片、兑奖说明、规则类型、规则参数及版本。`reward_quantity` 和 `issued_quantity` 只控制推荐奖励库存，不读取或更新 `yshop_activity_period_prize.quantity/winner_quantity`。每条配置一档一个奖品，排序按门槛值。

不把推荐奖品塞入 `yshop_activity_period_prize`，也不把奖励记录写入 `yshop_activity_winner`。后者同时驱动中奖公示、通知、开奖数量和兑奖，混用会污染中奖统计并影响开奖库存。推荐奖励单独查询和管理，但通过现有用户端兑奖路由完成领取。

### 首次参加标记解决跨期新人唯一性

仅查询已有报名记录无法可靠解决不同期次同时首次报名的竞争条件。新增 `yshop_activity_user_template_participation`，以 `(tenant_id, template_id, user_id)` 唯一，保存首次成功报名的期次、报名记录、推荐人及时间。报名事务中插入该行；插入成功表示本次是模板范围内首次参加，之后的期次都只能按普通推荐计数。若首次报名无推荐人，后续带推荐关系的报名也不能补算新人。

数据库升级时，以保留的成功报名记录按报名时间和记录 ID 选出每个模板/用户的首次参加记录回填该表。并发首次报名由唯一键决定唯一的首次记录，避免一个用户在两个期次都算新人。

### 期次/推荐人计数行串行更新

新增 `yshop_activity_period_referral_progress`，按 `(tenant_id, period_id, referrer_user_id)` 唯一，保存 `ordinary_count` 和 `newcomer_count`。新增 `yshop_activity_referral_reward` 保存每次达档产生的待兑奖奖励，并对 `(tenant_id, period_id, referrer_user_id, period_tier_id)` 建唯一约束。

推荐报名进入现有 `ActivityRegistrationServiceImpl.createForUser` 事务：先完成报名资格校验及报名插入，再按当前期次检查推荐人是否已有有效报名；若满足条件，插入首次参加标记（如适用），锁定/创建期次推荐进度行，更新普通计数和新人计数，检查所有新达到的阶梯，按独立数量原子预占并写奖励记录。报名、计数与奖励记录同事务提交，失败整体回滚。现有 `rewardReferrer` 抽奖/游戏机会路径单独保留，不能复用阶梯计数。

同一邀请报名在期次内由现有 `(tenant_id, period_id, user_id)` 唯一约束去重；同一个被推荐人跨期再次报名可再次贡献普通人数。新人只能由首次参加记录贡献一次。达到 5 人并一次越过 3 人和 5 人门槛时，事务内生成两个档位各一条奖励。

### 奖励记录与规则执行

奖品规则只在用户兑奖时执行。奖励记录保存领取方、期次、档位、奖品展示快照、兑奖码、兑奖状态和时间；规则参数从不可变的期次阶梯快照读取。推荐线下兑奖码使用 `REC` 前缀，与现有中奖码 `ACT` 前缀分开，在各自记录表中加租户级唯一索引。

用户端沿用 `/app-api/activity/period/claim`，保留原 `winnerId` 参数并增加可选 `referralRewardId`；请求必须且只能包含其中一个。后端按对应记录表锁行、验证当前用户归属、租户和状态，再执行该记录对应的期次快照规则。中奖记录逻辑保持原样；推荐奖励使用同一规则注册表和兑奖状态语义，但独立的记录表和处理分支。线上规则失败保持待兑奖并允许重试；处理中记录拒绝并发重复执行；线下规则沿用现有客服指引，不自动核销。

### 库存耗尽不回滚推荐报名

达档后按期次阶梯行原子执行 `issued_quantity < reward_quantity` 检查。库存足够时更新已发数量并写奖励记录；库存耗尽时不生成超量记录，保留已更新的推荐计数。开奖库存及抽奖算法不变。库存耗尽的档位在 H5 标示“本期已发完”。

## 主流程

### 模板保存及期次生成

1. 管理端保存 `referralRewards` 列表；后端校验租户奖品、启用状态、规则参数、正整数数量、同类型门槛唯一且递增。
2. 创建/更新模板阶梯与当前奖品库关联；继续独立保存 `inviteRegistrationChance`。
3. 生成期次时复制阶梯配置及完整奖品规则快照。后续模板或奖品库变化只影响新期次。

### 报名与阶梯触发

1. 报名服务沿用当前期次、资格和唯一性校验；推荐人不存在、本人自荐、未成功报名当前期次或状态无效时不触发任何奖励。
2. 报名插入成功后，先执行并保留既有 `inviteRegistrationChance` 机会发放逻辑。
3. 新阶梯逻辑单独锁定该期次/推荐人进度；普通人数加 1。仅当新建模板首次参加记录成功且本次报名有同期期有效推荐人时，新人数量加 1。
4. 读取该期次新人/普通阶梯快照，对比更新前后计数，逐一发放本次新达到的门槛；独立奖品数量耗尽则跳过奖励记录，不回退人数和既有抽奖/游戏机会。

### 用户查看和兑奖

1. 活动详情/最近期次详情公开返回该期阶梯、奖品展示信息和人数门槛，不返回推荐奖励剩余库存。
2. 登录用户调用 `my-result` 获取该期自己的新人/普通计数、阶梯进度及推荐奖励记录；返回内容仅限当前用户。
3. 用户对其中一个待兑奖奖励调用现有 `/claim?referralRewardId={id}`。服务端以登录态用户 ID 为准，不信任请求中的用户 ID。

## 风险与迁移

- 历史报名回填决定既有会员是否属于新人；迁移仅回填首次参加索引，不修改报名或开奖业务数据。报名被删除且已物理清理的历史记录无法参与回填。
- 期次和推荐人进度行需在报名事务中锁定；奖励记录唯一键及期次库存原子更新共同保证并发报名不重复发放或超发。
- 该功能与旧机会开关同时启用时会分别触发抽奖/游戏次数和阶梯奖品；管理端和 H5 必须清楚展示两种奖励的区别。
- 推荐库存耗尽时仍保留人数进度。具体 UI 展示“本期已发完”，不提供库存恢复或事后补发流程。
- 新增表含兑奖及新人首次参加历史。发布后如需回滚，应先停用新阶梯配置并使用前向迁移保留数据；仅在尚未产生奖励记录的环境中允许删除新增表。
