# AdaPay 对账单管理需求规格

## Scope

### In-scope

- 在管理后台提供独立的“对账单管理”能力，按当前租户管理 AdaPay 日终标准账单。
- 财务或管理员手动选择历史日期下载账单；本版本不提供每日自动下载。
- 每次成功下载从 AdaPay 获得包含 `Charge`、`PaymentConfirm`、`Div` 三个 CSV 的标准账单 ZIP。
- 将原始 ZIP 保存到主 OSS；每次成功下载形成一个 ZIP 历史版本。
- 解压 ZIP 后按 CSV 表头将三类明细解析并独立持久化，支持分页表格展示原始账单数据。
- 按天展示每个日期是否已经存在成功下载记录。
- 支持对已有成功日期重新拉取；重新拉取后，解析明细删除重建，ZIP 历史版本全部保留。
- Charge 支持按支付ID、商户订单号筛选；PaymentConfirm 支持按商户支付ID筛选；Div 支持按商户支付ID、MemberId（CSV 字段“分账用户”）筛选。
- 明细关联本地商家订单：Charge 通过账单支付ID与订单 `transactionId` 关联，并展示商家名称；PaymentConfirm、Div 通过账单商户支付ID关联 Charge，再获取商家名称。
- 支持查看和下载某天已成功归档的 ZIP 历史版本。

### Out-of-scope

- 不解析或处理 `Refund`、`RefundDiv` 等账单文件。
- 不下载微信、支付宝等其他支付渠道账单。
- 不将 CSV 数据与本地支付、分账记录进行对账或状态核验；仅按明确关联规则补充商家名称，不改变账单原始字段。
- 不执行金额核对、状态核对、差异判定或业务对账。
- 不改变现有“日终对账记录”模块的数据和行为。
- 不单独保存三个 CSV 文件到 OSS；CSV 仅作为 ZIP 内容读取，解析后写入数据库。
- 不提供解析明细历史版本查询；旧解析明细在新版本成功入库后被替换，历史解析数据以对应 ZIP 为准。

### Deferred

- 每日自动下载和失败自动重试。
- 明细数据导出。
- 账单文件清理和保留期限策略。
- 明细排序和统计；除本需求明确列出的字段外的其他筛选。

## Use Cases

### UC-1：手动下载某天的原始账单

- **角色**：当前租户的财务或管理员。
- **目标**：下载指定历史日期的 AdaPay 标准账单，并完成原始 ZIP 归档与三类明细入库。
- **主流程**：用户选择日期并发起下载；系统确认该日期不是未来日期且当前租户没有同一日期的运行中任务；系统从 AdaPay 获取标准账单 ZIP；成功保存 ZIP 后解压并解析 `Charge`、`PaymentConfirm`、`Div`；替换该日期旧解析明细；记录本次下载状态和归档信息。

### UC-2：按天查看账单明细

- **角色**：财务或管理员。
- **目标**：查看某日期已成功下载的三类账单原始数据。
- **主流程**：用户在日历选择日期，查看下载状态和汇总信息；系统展示最新成功版本的 `Charge`、`PaymentConfirm`、`Div` 三个分页表格；用户切换明细类型浏览数据。

### UC-3：按账单字段筛选明细并查看商家名称

- **角色**：财务或管理员。
- **目标**：按各账单类型支持的业务标识快速定位明细，并查看关联商家名称。
- **主流程**：用户在 Charge 输入支付ID或商户订单号，在 PaymentConfirm 输入商户支付ID，在 Div 输入商户支付ID或 MemberId；系统按字段精确匹配并分页返回。对于可关联的明细，页面补充展示商家名称；关联不到时仍展示账单原始记录，商家名称为空。

### UC-3a：按 MemberId 查看 Div 分账流水

- **角色**：财务或管理员。
- **目标**：快速定位某收款人 MemberId 在某日期的分账流水。
- **主流程**：用户选择日期后进入 Div 明细，输入 MemberId；系统只返回“分账用户”与该值一致的数据。

### UC-4：重新拉取某天

- **角色**：财务或管理员。
- **目标**：更新某天已经下载的解析明细，同时保留重新拉取前的 ZIP。
- **主流程**：用户确认重新拉取；系统生成新的 ZIP 版本；新 ZIP 成功解析入库后成为该日期最新展示版本；旧 ZIP 继续保留在归档列表中。

### UC-5：下载历史 ZIP

- **角色**：财务或管理员。
- **目标**：获取某日期任意一次成功下载时的原始账单。
- **主流程**：用户查看该日期归档版本列表，选择对应版本下载 ZIP。

## Business Rules

1. 所有账单数据和操作记录均属于当前登录租户，不得跨租户查询或覆盖。
2. 日期必须是历史日期，不允许选择未来日期；默认建议日期为昨天。
3. 同一租户、同一日期同时只允许一个下载任务执行。
4. 下载任务在以下阶段之一失败时，不能删除或替换原有解析明细：AdaPay 下载失败、ZIP 不完整、任一目标 CSV 缺失、CSV 解析失败或明细入库失败。
5. 只有 ZIP 保存成功、三个目标 CSV 全部解析成功且明细替换成功后，本次下载才标记为成功。
6. 成功下载必须保存 ZIP 原始字节及摘要信息；每次成功下载形成新的 ZIP 版本。
7. `Charge`、`PaymentConfirm`、`Div` 分别解析为三类独立明细数据；解析字段由设计阶段按样本表头定义。
8. CSV 中以 `#` 开头的说明、汇总和导出信息不写入明细；表头后的数据行按原顺序写入，并保留其在 CSV 数据区中的原始行号。
9. 解析只按 CSV 结构拆分字段，不转换交易状态、日期或金额含义；页面展示原始字段值。
10. 页面展示的明细永远来自该租户、该日期最近一次成功下载版本。
11. 文件存在但没有业务数据时视为合法结果，该文件对应明细数量为 0。
12. 任一目标文件缺失时，整个下载失败，不允许展示部分更新的日期数据。
13. 筛选字段按账单类型隔离：Charge 的支付ID、商户订单号；PaymentConfirm 的商户支付ID；Div 的商户支付ID、MemberId（“分账用户”）。均采用精确匹配，空筛选值不增加条件。
14. Charge 以账单“支付ID”匹配本地订单 `transactionId`，将 `shopId`、`shopName` 作为冗余快照在导入时写入明细表；PaymentConfirm、Div 以账单“商户支付ID”关联 Charge 后继承。分页查询直接读取冗余字段，不实时关联订单表。
14a. 关联只用于展示门店信息，不过滤账单行、不改变原始值，也不执行金额或状态核对。未匹配时门店字段为空。
15. ZIP 历史版本只追加、不覆盖、不删除；本版本不设置自动清理期限。
16. 下载、重新拉取、查询明细和下载 ZIP 都必须受独立的管理后台权限控制。

## Frontend Requirements

- 页面提供月份日历，展示当前月每天的下载状态；日期状态应区分“已成功下载”“下载失败”“下载中”和“未下载”。
- 日历点击某一天后，加载该日期最新成功下载的三类明细；无成功下载时展示空状态和重新下载入口。
- 日期下载区域提供日期选择器和下载按钮；重新拉取已成功日期前必须二次确认。
- 三类明细使用页签切换，并分别展示文件行数、最新成功下载时间和 ZIP 版本号。
- 每个明细页签使用数据库分页表格；列数较多时允许横向滚动，数据值不得截断或自动改写。
- 每个页签提供对应筛选：Charge（支付ID、商户订单号）、PaymentConfirm（商户支付ID）、Div（商户支付ID、MemberId）；筛选后回到第一页并显示命中行数。
- 表格展示商家ID、商家名称列；内容来自导入时冗余的门店快照，未匹配时显示 `—`。
- 下载任务进行中提供明确状态；下载失败时展示原因并允许再次发起。
- 页面提供当前日期 ZIP 的下载入口，并支持展开历史 ZIP 版本列表进行下载。

## Edge Cases

- 选择未来日期：不允许发起下载。
- 同日并发重新拉取：只允许一个任务执行，另一个请求返回“任务进行中”。
- AdaPay 返回空 ZIP、非 ZIP 内容或 ZIP 中缺少 `Charge_`、`PaymentConfirm_`、`Div_` 任一文件：本次下载失败。
- CSV 表头为空、数据列数异常或字段无法按表头对齐：本次下载失败。
- 某文件只有注释和表头、没有数据行：该文件按 0 行成功处理，不要求整个下载失败。
- 某个 CSV 数据行存在多余尾部空列：必须保留原始行的全部字段和顺序。
- 某日期曾成功下载，但最新重拉失败：日历仍显示该日期已下载，明细继续展示上一次成功版本。
- 用户连续重拉同一天并全部成功：页面展示最后一次成功版本的解析数据，归档列表包含全部 ZIP 版本。
- MemberId 前后包含空白：按精确业务值处理，不返回不匹配的数据。
- 当前租户未配置 AdaPay 支付信息：下载任务失败，并提示先完成支付配置。

## Acceptance Criteria

1. 用户可为当前租户选择一个历史日期并手动下载 AdaPay 标准账单。
2. 成功下载后，原始 ZIP 被保存到主 OSS，并能在该日期归档列表中看到本次版本。
3. `Charge`、`PaymentConfirm`、`Div` 三类 CSV 均解析入库，页面可分别分页查看原始字段值。
4. 页面不展示或计算业务对账结果；账单仅按约定关联键补充商家名称，不核对金额、状态或支付结果。
5. 各账单类型支持对应筛选字段精确匹配，筛选与分页结果正确；商家名称按支付ID/商户支付ID关联规则正确补充。
6. 某日重新拉取成功后，页面解析明细来自新 ZIP，旧 ZIP 仍可从历史版本下载。
7. 下载或解析任一步失败时，不会删除或替换已有解析明细，日历仍以上次成功状态展示。
8. 日历能正确区分已成功、失败、下载中和未下载的日期。
9. 同一天不允许并发下载；并发请求不会生成两个正在执行的任务。
10. 不同租户之间不能看到、下载或覆盖彼此的账单和明细。
11. 三类目标文件之一缺失、CSV 结构异常或租户未配置 AdaPay 时，页面给出明确失败原因。
12. 有权限的财务或管理员可以执行查询、下载、重新拉取和 ZIP 下载操作，无权限用户不能访问对应能力。

## Assumptions

- “历史日期”指不晚于昨天的自然日期，账单日期按 `Asia/Shanghai` 解释。
- “MemberId”对应 Div CSV 的“分账用户”字段；Charge 和 PaymentConfirm 当前没有 MemberId 字段。
- 不做业务对账判定；按指定关联键关联商家订单，仅补充商家名称。Charge 的支付ID对应订单 `transactionId`；PaymentConfirm、Div 的商户支付ID对应同版本 Charge 的支付ID，再经 `transactionId` 取得订单 `shopName`。
- 三个 CSV 不单独保存为 OSS 文件，用户确认仅保留 ZIP 历史版本。
- 当前版本无 ZIP 清理期限，所有成功 ZIP 版本长期保留。
