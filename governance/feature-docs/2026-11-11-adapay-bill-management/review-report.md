# Review 报告 — AdaPay 对账单管理

## 结论

未发现阻塞交付的代码缺陷。实现符合需求规格和已冻结契约：只归档 ZIP，解析三类 CSV 入库，成功重拉时原子替换明细，失败保留旧数据，Div 支持 MemberId 精确筛选，页面提供日历和分页原始明细。

## 已核对项

- 所有查询和写入均带当前租户条件；控制器不接受客户端租户 ID。
- 同日下载使用 Redis 锁、活动键唯一约束和超时回收，避免并发生成两个活动任务。
- 远端下载、ZIP 校验、CSV 解析、OSS 上传均不在明细事务内；明细替换和任务成功更新在同一事务。
- 解析或 OSS 前失败不会删除旧明细；明细事务失败会回滚，旧明细继续可查询。
- ZIP 历史版本只追加不覆盖；失败任务保留已上传 ZIP 地址供追踪，但不进入成功版本列表。
- Charge、Confirm、Div 三表使用租户、账单日期和原始行号唯一键，重拉前物理删除，避免逻辑删除行与唯一键冲突。
- 原始固定字段按字符串保存，页面同时返回 `rawLine` 和 `extraFields`，不做金额、日期或状态语义转换。
- Div 的 MemberId 映射到 `member_id` 并建立日期维度索引，接口采用精确等值筛选。
- 前端日历优先展示下载中，再展示成功、失败和未下载；今天及未来日期不可选择。
- 生产构建和新增单测通过。

## 残余风险

- 真实 AdaPay 返回结构只按样本表头实现，未做线上响应验证。若远端新增、删除或重命名必需字段，任务会失败并保留旧明细。
- 真实主 OSS 的上传和回读未验证。OSS 故障时任务失败，需要用户手工重拉，没有自动重试。
- ZIP 下载和解析在单个异步请求内完成，没有独立大小上限和流式解压。对超大账单需要考虑内存上限。
- Flyway migration 未在真实数据库执行，菜单动态 ID、套餐 `menu_ids` 更新和四张表 DDL 仍需在目标环境验证。
- 未执行登录态页面 E2E，日历、分页、MemberId 筛选和 ZIP 下载需要联调确认。

## 建议

在测试租户完成一次真实下载，至少覆盖：正常 ZIP、缺少目标 CSV、解析失败保留旧明细、同日重复提交、Div MemberId 筛选、ZIP 历史下载和租户隔离。
