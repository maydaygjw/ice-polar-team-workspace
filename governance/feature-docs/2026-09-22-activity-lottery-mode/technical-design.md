# 活动抽奖模式技术设计

## 1. 设计目标

在现有“报名后统一开奖”模式之外，增加“报名后即时抽奖”模式。两种模式由活动模板配置，并在生成期次时冻结到期次数据。

本期只改变中奖产生时机，不改变报名条件、抽奖次数来源、兑奖、中奖通知和中奖公示的既有业务边界。

## 2. 模块影响

- `backend/yshop-module-activity`：增加抽奖模式和概率快照；新增用户端即时抽奖服务、抽奖尝试幂等记录、并发库存控制；调整期次生成、抽奖次数增加、状态计算和定时开奖扫描。
- `admin`：活动模板增加模式选择和奖品概率配置；期次管理按模式展示可用操作；抽奖模式不展示开奖时间和手动开奖操作。
- `miniapp`：本期明确不修改代码、不接入新接口；后续客户端迭代再调用新增 app-api。
- `h5`：本期不修改页面，仅保留接口契约供后续客户端接入。
- 外部系统：无新增外部依赖。奖品规则仍复用现有活动奖品库和 `ActivityDrawRule` 注册机制。

## 3. 核心决策

### 3.1 模式枚举和兼容

使用稳定枚举值：

| 值 | 名称 | 说明 |
|---|---|---|
| `DRAW` | 开奖 | 现有模式；到开奖时间由任务或后台手动统一开奖 |
| `LOTTERY` | 抽奖 | 报名后在报名时间窗口内逐次即时抽奖 |

模板默认值为 `DRAW`。已有模板和已有期次不回写、不重算，保证历史链路继续使用统一开奖语义。

模板、期次和期次快照都保存模式：期次表保存模式用于定时扫描和后台操作判断，快照保存模式用于历史业务读取。

### 3.2 开奖时间

- `DRAW` 模式：开奖时间必填，必须满足报名结束时间不晚于开奖时间。
- `LOTTERY` 模式：开奖时间为空；仅校验报名开始时间早于报名结束时间。
- `LOTTERY` 模式不进入定时开奖扫描，不能调用后台统一开奖接口。
- 期次状态在 `LOTTERY` 模式下由报名窗口和废弃状态决定；即时抽奖完成不会将期次置为 `ENDED`。

### 3.3 概率模型

概率属于活动模板奖品关联，而不是奖品库本身，因为同一个奖品可以在不同活动中使用不同概率。

- 单个奖品概率使用百分比，范围 `0.00` 到 `100.00`，精确到两位小数。
- `LOTTERY` 模式下每个奖品必须配置概率。
- 所有奖品概率之和允许小于或等于 `100.00`；差额是未中奖概率。
- `DRAW` 模式不依赖概率，概率字段可为空并保持现有统一开奖规则。
- 生成期次时将概率复制到 `yshop_activity_period_prize`，期次生成后不再读取模板实时配置。

抽奖使用固定百分比区间：按奖品配置顺序建立累计区间，生成 `0.00–100.00` 的随机值命中奖品；落入未配置区间时未中奖。奖品库存耗尽时不重新归一化，也不改投其他奖品，直接返回未中奖。

### 3.4 抽奖机会与 singleWinner

- 报名成功仍获得 1 次抽奖机会。
- 后台增加次数、邀请成功增加次数和用户端增加次数沿用现有规则；`LOTTERY` 模式以报名结束时间作为“抽奖机会仍可增加”的截止点。
- 每次即时抽奖成功处理一次 `drawChancesUsed` 增量。
- `singleWinner=true` 且用户已经中奖时，仍执行一次概率判断并消耗一次机会，但强制返回未中奖，不生成第二条中奖记录。
- 抽奖次数不足、未报名、已过报名窗口、期次废弃等属于业务错误，不消耗次数。

### 3.5 幂等和并发

客户端必须为每次抽奖生成 `requestId`。服务端以“租户 + 期次 + 用户 + requestId”唯一约束保存抽奖尝试。

即时抽奖事务：

1. 校验当前登录用户、租户、期次模式、报名窗口和有效报名记录。
2. 先按唯一键查找已有抽奖尝试；已存在时直接返回保存的结果。
3. 以条件更新方式消耗一次抽奖机会：`draw_chances_used < draw_chances`。
4. 按期次奖品快照进行概率判断。
5. 命中奖品时锁定奖品行，校验 `winner_quantity < quantity`；库存已满则本次未中奖。
6. 中奖时写入现有中奖记录并增加奖品已中奖数量、期次实际中奖数；未中奖时不写中奖记录。
7. 保存抽奖尝试结果，事务提交后返回。

抽奖尝试记录负责保存未中奖结果和幂等响应；中奖记录仍是兑奖、通知、公示的事实来源。并发抽奖使用数据库条件更新和行锁，不允许超发奖品或重复消耗同一机会。

### 3.6 统一开奖兼容

- `ActivityDrawJob` 继续扫描 `DRAW` 模式期次；查询条件增加 `draw_mode = DRAW`。
- `ActivityPeriodService.draw` 对 `LOTTERY` 模式直接返回业务错误，防止后台或旧调用方绕过即时流程。
- `DRAW` 模式的抽奖机会仍按现有统一开奖逻辑在开奖完成时一次性标记为已使用。
- `LOTTERY` 模式不设置 `drawBatchNo`、`drawTimeActual` 作为期次统一开奖字段；每次中奖记录使用本次抽奖尝试生成的批次号用于审计。

## 4. 数据设计

### 4.1 既有表字段

新增字段，全部带租户隔离和历史兼容：

| 表 | 字段 | 类型 | 说明 |
|---|---|---|---|
| `yshop_activity_template` | `draw_mode` | `TINYINT NOT NULL DEFAULT 1` | `1` 开奖，`2` 抽奖 |
| `yshop_activity_template_prize` | `probability` | `DECIMAL(5,2) NULL` | 抽奖模式奖品概率百分比 |
| `yshop_activity_period` | `draw_mode` | `TINYINT NOT NULL DEFAULT 1` | 期次模式快照，供扫描和状态判断 |
| `yshop_activity_period_snapshot` | `draw_mode` | `TINYINT NOT NULL DEFAULT 1` | 内容/规则快照中的模式 |
| `yshop_activity_period_prize` | `probability` | `DECIMAL(5,2) NULL` | 期次奖品概率快照 |

已有数据统一回填为 `1`。`draw_time` 在模板和期次表改为可空；只允许 `LOTTERY` 模式为空，`DRAW` 模式仍由服务校验必填。

### 4.2 抽奖尝试表

新增 `yshop_activity_draw_attempt`：

| 字段 | 说明 |
|---|---|
| `id` | 抽奖尝试 ID |
| `tenant_id` | 租户 ID |
| `period_id` | 活动期次 ID |
| `registration_id` | 报名记录 ID |
| `user_id` | 当前会员 ID |
| `request_id` | 客户端幂等请求号 |
| `result` | `1` 中奖，`2` 未中奖 |
| `period_prize_id` | 中奖的期次奖品 ID，可空 |
| `winner_id` | 中奖记录 ID，可空 |
| `probability_snapshot` | 本次使用的概率审计快照，可选 JSON |
| `draw_batch_no` | 本次抽奖批次号 |
| `draw_time` | 抽奖时间 |
| 通用审计字段 | 创建、更新、逻辑删除 |

唯一键：`uk_tenant_period_user_request (tenant_id, period_id, user_id, request_id, deleted)`；查询索引覆盖期次、用户、时间和结果。抽奖尝试只保存抽奖结果，不承担兑奖状态。

### 4.3 迁移与回滚

使用 `backend/sql/upgrade-2026-09-22-activity-lottery-mode.sql`：

- 增加字段、索引和抽奖尝试表。
- 对已有模板、期次和快照回填 `draw_mode=1`。
- 不修改 `sql/yixiang-drink.sql`，不删除历史字段和历史记录。
- 回滚先删除抽奖尝试表和新增索引，再删除新增字段；回滚前必须确认没有依赖新字段的代码版本。

## 5. 服务分层和调用流程

### 5.1 模板保存

1. 校验模式、报名时间和开奖时间的条件组合。
2. 校验奖品引用、数量和租户归属。
3. `LOTTERY` 模式校验每个奖品概率非空且在范围内，累计概率不超过 `100.00`。
4. 保存模式和模板奖品概率；不把概率写入奖品库。

### 5.2 期次生成

1. 从模板读取模式和时间配置。
2. `DRAW` 模式生成开奖时间；`LOTTERY` 模式的期次开奖时间为空。
3. 复制模式到期次和期次快照。
4. 复制数量、奖品规则快照和概率到期次奖品。
5. 任一快照校验失败时整体回滚，不产生不完整期次。

### 5.3 报名与即时抽奖

报名接口仍只负责报名，不自动抽奖；调用方在报名成功后使用返回的期次 ID 发起即时抽奖。这样可以区分“报名成功”和“抽奖结果”，并支持剩余次数多次抽奖。

即时抽奖服务建议放在 `ActivityRegistrationService` 的业务边界内，复用当前用户报名查询、租户校验和中奖记录写入能力；概率选择和尝试记录使用独立的 `ActivityLotteryService`，避免把统一开奖批处理逻辑改造成混合流程。

### 5.4 结果读取

`my-result` 继续返回总次数、已使用次数、剩余次数和中奖记录。抽奖接口返回本次结果；不把全部抽奖尝试记录暴露给客户端。后台报名/中奖列表可按现有记录查看中奖事实，后续如需分析未中奖次数再增加专用查询。

## 6. 安全、租户和可观测性

- 用户 ID、租户 ID、报名 ID 均从登录态或服务端查询获得，不信任请求体中的身份字段。
- 所有新增查询和写入显式带 `tenant_id`；期次、报名、奖品和中奖记录同时校验数据权限。
- `requestId` 只作为幂等键，不作为用户身份或随机种子。
- 随机数使用服务端安全随机源，不使用客户端随机值。
- 日志记录租户、期次、用户、抽奖尝试 ID、结果和耗时；不记录完整手机号、openid、企业微信 ID 或奖品规则敏感参数。
- 中奖写入、库存更新、次数消耗和尝试记录必须在同一事务内完成；既有中奖外部发放语义不在本期扩展。

## 7. 风险与未纳入范围

- 高并发下同一奖品库存锁会形成热点；先使用数据库行锁和短事务，达到性能瓶颈后再评估 Redis 预扣库存，但不在本期引入新的库存事实来源。
- 概率是理论概率，不承诺有限样本下的实际比例；后台应展示概率合计和未中奖概率。
- 不增加人工指定中奖、权重概率、多轮抽奖、动态调概率或概率审计后台。
- 不改变已有兑奖、企业微信通知、线下兑奖码和公示规则。
