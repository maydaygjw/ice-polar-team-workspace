# 需求规格：订单每日序号

## Scope

### In

- 为商城订单增加订单序号字段。
- 订单序号按门店和自然日生成，每个门店每天从 `1` 开始递增。
- 新订单创建成功后，订单序号随订单返回给管理端和 C 端订单查询接口。
- 订单序号与现有业务订单号、取餐号相互独立。

### Out

- 不修改现有订单号生成规则。
- 不修改已有取餐号 `numberId` 的含义或历史值。
- 不增加管理端或小程序页面入口；本期仅扩展接口数据。
- 不为历史订单强制回填序号。

## Use Cases

### UC-1：创建普通订单

- 角色：C 端用户、服务端代下单调用方。
- 目标：创建订单时获得当前门店当天的下一个订单序号。
- 主流程：订单创建成功后，序号为当天该门店已分配序号中的下一个值，并出现在订单详情/列表数据中。

### UC-2：并发创建订单

- 角色：多个同时下单的用户。
- 目标：每个订单得到唯一且不重复的序号。
- 主流程：并发请求完成后，序号不重复；同一天后续序号继续递增。

## Business Rules

1. 序号作用域为“租户 + 门店 + 自然日”；自然日按后端运行环境的本地日期计算。
2. 当天第一个成功创建的订单序号为 `1`，后续成功创建订单依次为 `2、3...`。
3. 订单创建事务回滚时，本次序号分配也回滚，不保留孤立序号。
4. 订单序号一旦写入订单不可修改；取消、退款、删除订单不重新占用序号。
5. 历史订单的订单序号允许为空，不根据历史订单号或取餐号推算。
6. 每个订单只分配一次序号；加餐更新已有订单不产生新序号。
7. 订单号、订单序号、取餐号是三个不同字段，调用方不得用其中一个替代另一个。

## Frontend Requirements

- 管理端订单详情、列表和导出接口响应包含 `orderSequence`（历史数据为空）。
- C 端订单详情和列表接口响应包含 `orderSequence`（历史数据为空）。
- 本期不新增筛选、排序、编辑或单独展示入口；现有客户端必须继续按 `orderId` 完成支付、退款、打印和设备流程。

## Edge Cases

- 跨自然日创建订单：新日期的首个订单序号重新为 `1`。
- 并发创建落在日期边界：按服务端计算出的自然日分别计数，不允许跨日复用。
- 订单创建失败或事务回滚：订单和对应序号计数更新均不生效。
- 历史订单没有序号：接口返回 `null`，不影响既有订单操作。
- 同一订单加餐：保持原订单序号不变。

## Acceptance Criteria

- [ ] 新订单响应和后续详情/列表响应包含 `orderSequence`。
- [ ] 同一门店同一天创建的首个、第二个订单分别得到 `1`、`2`；不同门店同日分别从 `1` 开始。
- [ ] 新的一天首个订单序号重新为 `1`。
- [ ] 并发创建订单不会产生重复序号。
- [ ] 订单创建回滚后不留下可见的孤立序号。
- [ ] 订单号和取餐号的现有值与行为不改变。
- [ ] 历史订单序号为空时，详情、列表和导出仍正常工作。

## Assumptions

- 序号按现有订单的 `shopId` 分组；门店属于当前租户，计数表同时保留 `tenant_id` 以维持租户隔离。
- “每天”使用后端应用服务器本地时区的自然日；本期不新增租户级时区配置。
