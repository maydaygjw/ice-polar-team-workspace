# 评审报告：订单每日序号

## Review Scope

- 需求、契约、数据库升级脚本与后端实现的一致性。
- 多租户/门店隔离、并发递增、事务回滚、只读字段和历史数据兼容。
- 普通订单、管理端订单、C 端订单和预约订单创建路径。

## Findings

### No blocking issues found

- 计数表以 `tenant_id + shop_id + sequence_date` 唯一约束分组；`INSERT ... ON DUPLICATE KEY UPDATE` 在事务中递增，随后锁定读取当前值。
- 普通 C 端订单、管理端订单和预约订单均在写入订单前分配序号；订单创建方法处于事务中，失败时计数更新随事务回滚。
- `orderSequence` 未放入新增/编辑共用基础请求 VO，仅加入响应 DTO/VO 和导出 VO，客户端不能通过请求覆盖生成值。
- 订单字段允许为空，历史订单不会被回填；加餐路径不重新分配序号。
- 序号服务通过租户上下文取得租户编号，并使用订单 `shopId` 分组；计数表和订单数据均遵循现有租户边界。

## Residual Risks

- 未用真实数据库验证高并发、跨日边界和回滚；上线前应在目标 MySQL 版本执行升级脚本并完成集成验证。
- 当前“每天”的定义是后端运行环境本地日期，作用域是门店；若业务需要租户时区计数，需要先更新契约。
- 完整依赖测试存在既有 pay-biz 基线失败，当前只能确认编译和新增单元测试通过。

## Conclusion

实现与已冻结需求和契约一致，无发现本次改动引入的阻塞问题；鉴于数据库集成测试和完整基线测试仍有缺口，结论为有条件通过，进入人工验收/上线前验证。
