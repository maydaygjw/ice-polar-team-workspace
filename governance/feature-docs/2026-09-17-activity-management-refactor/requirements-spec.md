# 活动管理重构需求规格

## Scope

### In

- 将“活动管理”整理为父菜单，下设模板管理、期次管理、报名管理、中奖管理四个独立子模块。
- 将现有活动模板、期次、报名、中奖相关页面和操作迁移到对应模块，保持已有业务能力可用。
- 新增“报名条件管理”能力，内置两个企业微信报名条件：已添加指定活动客户管理员、属于指定社群。
- 报名条件只支持 AND 组合；模板可选择并配置多个条件，所有启用条件均通过后才可报名。
- 报名条件支持开发者扩展：新增条件类型可以通过统一条件接口接入，并被管理端发现和配置。
- 条件实现可以调用已登记的内部或外部查询接口获取用户业务数据，例如查询用户当天是否下单；外部接口地址和凭据不由租户或客户端传入。
- 期次生成时冻结活动内容和报名条件；报名校验使用期次快照。
- 用户端返回当前期次的条件展示和校验结果，前端不再写死报名条件文案。

### Out

- 不支持运行时上传脚本、表达式或插件包。
- 不支持 OR、嵌套条件组、条件优先级或条件短路配置。
- 不新增订单金额、会员等级、邀请人数等非企微条件；仅保留扩展接口。
- 本次不交付“用户已下单”条件本身，但方案必须支持其后续接入。
- 不改变抽奖算法、奖品模型、开奖流程和 H5 认证方式。

## Use Cases

- 管理员在模板管理中选择并配置报名条件，保存活动模板。
- 管理员在条件管理中查看内置条件，并控制租户是否可选用某个条件。
- 管理员在期次管理中生成期次、控制报名、开奖和查看该期次关联结果。
- 管理员在报名管理中分页查询、导出、删除报名记录或增加抽奖次数。
- 管理员在中奖管理中分页查询和导出中奖记录。
- 用户访问活动详情时看到本期报名条件，报名时由后端按期次快照统一校验。
- 开发者实现新的条件处理器并注册新的条件类型后，管理端可以展示该条件并在模板中配置。

## Business Rules

- 活动菜单为父菜单；四个业务子菜单拥有独立路由、页面入口和权限码。
- “中奖管理”是独立模块，不再仅作为期次或报名页面的隐藏操作入口；期次和报名页面可保留带筛选条件的跳转。
- 条件类型必须有稳定的类型标识、名称、配置定义和校验结果说明。
- 模板保存条件配置；生成期次时复制条件类型、配置和展示信息到期次快照。
- 报名只读取期次快照，不读取可变的模板条件配置。
- 所有启用条件必须通过；任一条件失败即报名失败。
- 未启用条件不参与报名校验，也不应展示为用户必须满足的条件。
- 企业微信管理员条件沿用现有联系人关联和“命中任一指定管理员”的语义。
- 企业微信社群条件沿用现有本地群成员数据和“命中任一配置标签下群成员”的语义。
- 条件校验结果需保存到报名记录，至少区分各条件是否通过；历史结果不可因条件配置变化而改变。
- 租户停用条件后，不影响已生成期次；新模板不可再选择该条件。
- 未注册、未启用或配置非法的条件类型不得保存为可报名模板配置。
- 所有活动数据和条件配置遵循租户隔离；需要部门/商圈范围时继续执行现有数据权限。

## Frontend Requirements

- 活动管理父菜单下显示四个子菜单：模板管理、期次管理、报名管理、中奖管理。
- 条件管理作为活动管理下的独立配置入口；展示条件名称、类型、状态、说明和可配置字段。
- 模板表单使用条件选择器；选择条件后显示其配置项，支持排序，不能选择已停用条件。
- 期次、报名、中奖页面保持现有查询、操作、导出能力，并迁移到新路由和权限。
- 用户端活动详情根据后端条件列表渲染名称、说明和状态；加载、未报名、已报名、校验失败状态均可表达。
- 用户端不展示内部配置 JSON，不暴露企业微信 UserID、标签 ID 或租户信息。

## Edge Cases

- 模板已有历史期次时，修改条件只影响后续生成期次，不影响历史期次。
- 条件被停用后仍被旧模板引用时，禁止生成新期次并给出明确原因；已有期次继续可报名并按快照校验。
- 条件配置缺失、类型未知、配置格式错误时，模板保存或期次生成失败，不允许产生半配置期次。
- 没有配置任何条件时，按“无额外条件”处理；报名仍受报名时间、报名开关和重复报名约束。
- 单个条件服务查询失败时，报名失败且不产生报名记录；不得降级放行。
- 外部查询超时、限流、认证失败或返回数据不完整时，条件判定失败；不得把外部异常当作通过。
- 条件调用外部接口时使用服务端解析的当前用户身份、租户和业务时区，客户端不得传入待查询用户或日期范围覆盖真实上下文。
- 条件扩展实现未注册或重复注册时，应用启动失败或明确拒绝加载，不能静默覆盖。
- 旧活动模板只有两个 Boolean 条件字段时，迁移后应转换为等价条件配置。

## Acceptance Criteria

- 活动菜单结构和四个子模块入口符合规划，原有模板、期次、报名、中奖操作均可完成。
- 条件管理可展示并管理两个内置企微条件，模板可选择和配置它们。
- 配置两个条件时，任一条件失败都不能报名；两个条件均通过才能报名。
- 期次生成后修改模板条件，不改变该期次的报名校验规则。
- 新增一个条件处理器并注册后，条件管理和模板条件选择能够识别该类型，无需修改报名主流程分支。
- 条件配置错误、条件停用、条件查询异常均有明确错误反馈且不产生报名记录。
- 用户端条件展示与后端配置一致，不再出现固定的虚假订单条件文案。
- 租户隔离、数据权限、权限码和历史报名校验结果保持正确。
- 后端定向测试、管理端类型检查/构建、H5 类型检查/构建和必要 API/E2E 测试结果记录在 test-notes.md。

## Assumptions

- 条件管理的启停为租户级能力；平台内置条件由代码提供，租户只能启用或停用，不能编辑条件执行逻辑。
- 条件配置由模板保存，条件管理不直接绑定具体活动。
- 条件失败原因由后端返回面向用户的安全文案；内部异常和企微标识不返回客户端。
- 本次重构同时修正当前实现未校验报名起止时间的问题，报名必须满足期次时间窗口和人工报名开关。
