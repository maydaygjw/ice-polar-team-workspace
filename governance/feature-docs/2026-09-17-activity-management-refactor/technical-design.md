# 活动管理重构技术设计

## 模块影响

- `backend/yshop-module-activity`：新增条件注册、条件配置、条件快照和统一报名评估编排；重整管理端权限与菜单数据。
- `admin/`：拆分活动管理路由和页面模块，新增条件管理页面，模板表单改为条件驱动。
- `h5/`：基于用户端条件列表展示报名资格，不再使用固定演示数据和固定条件文案。
- `governance/CONTRACTS.md` 与功能契约：同步菜单、权限、API、DB 和兼容迁移规则。
- 不影响 `miniapp/`、`icepolar-dms/`、MQ topic 和外部系统版本。

## 关键决策与权衡

1. **四个业务模块独立呈现**：模板、期次、报名、中奖分别拥有菜单和页面权限；跨页面跳转通过查询参数保留上下文。中奖不再隐藏在期次详情中，但保留快捷入口。
2. **条件采用策略注册而非脚本执行**：定义本模块的条件处理器接口，由 Spring Bean 注册表按 `type` 发现实现。这样新增条件不需要修改报名主流程，同时避免表达式/脚本的注入和越权风险。
3. **配置与执行分离**：条件描述和配置由模板保存；条件处理器负责校验配置和执行；统一编排器只负责 AND 聚合、错误收集和结果落库。
4. **条件快照是事实来源**：模板生成期次时复制完整条件配置和展示快照；报名、用户端展示均读取期次快照，修复模板变更影响历史期次的问题。
5. **租户启停使用活动模块配置**：内置条件代码随版本发布，租户级启停记录只控制可选性和新期次生成，不删除代码注册，也不影响旧期次。

## 条件扩展机制

条件处理器提供以下中性职责：

- 返回稳定 `type`、显示名称、说明、配置 schema 和版本。
- 校验模板配置是否合法，并在保存/生成阶段拒绝未知字段或非法值。
- 接收当前用户、租户、期次和条件配置组成的本模块上下文。
- 可通过本模块提供的受控查询端口访问已登记的内部/外部业务数据源；处理器不得读取 URL、Token 或凭据配置，也不得直接接受客户端传入的用户身份。
- 返回通过标识、面向用户的失败原因和可审计的安全结果摘要。

注册表启动时收集所有处理器，校验 type 唯一性。报名服务按快照中的 type 查找处理器，依次执行并聚合为 AND；任一失败即停止后续业务写入，但建议保留已执行结果用于日志/诊断。处理器不得直接修改报名或开奖数据。

首期处理器：

- `WECOM_ADMIN_FOLLOWED`：配置活动客户管理员列表，命中任一管理员关联关系即通过。
- `WECOM_GROUP_MEMBER`：配置社群标签列表，命中任一标签关联群的本地成员即通过。

后续“用户已下单”条件可实现为独立处理器，例如 `ORDER_PLACED_TODAY`。处理器从上下文取得 `userId`、`tenantId` 和租户业务时区，将“今天”转换为明确的起止时间，再调用已登记的订单查询客户端判断是否存在符合状态的订单。管理端只配置业务参数，不配置外部 URL、请求头或凭据。

外部查询必须有固定连接配置、连接/读取超时、有限重试和脱敏 DEBUG 日志。超时、限流、认证失败、非 2xx 或响应无法解析统一作为条件失败，并记录内部诊断原因。可按“租户 + 用户 + 期次 + 条件版本”做短时只读缓存，但缓存不能跨租户；只有条件评估结果摘要写入报名记录，不保存外部完整响应。

处理器依赖继续通过 `mp-api`，不直接依赖 `mp-biz` 或调用企微 HTTP API。

## 数据与迁移策略

- 模板新增条件配置集合，保留旧 Boolean 字段作为兼容读取来源；迁移脚本将旧字段转换成两个等价条件配置。
- 期次快照新增条件配置和条件展示快照；生成期次时写入处理器版本，确保后续处理器语义升级可识别兼容性。
- 报名记录新增结构化条件结果快照，保留现有管理员/群校验结果字段作为兼容展示字段；新流程以结构化结果为准。
- 新增租户级条件启停配置，默认启用两个内置条件，历史期次不受影响。
- 所有新表/字段包含租户、审计和逻辑删除字段，查询带租户与数据范围约束。
- SQL 使用 `backend/sql/upgrade-2026-09-17-activity-management-refactor.sql`，必须包含限定范围回滚说明；不得修改基线 SQL。

## 必要流程

### 模板保存

管理端读取可用条件元数据 → 选择条件并填写配置 → 后端校验条件类型、启停状态和配置 → 保存模板条件集合。

### 期次生成

读取模板条件 → 校验当前条件仍可用 → 复制内容、奖品和条件配置/元数据/处理器版本 → 生成不可变期次快照。任一条件不可用时整体失败。

### 用户报名

读取期次和快照 → 校验租户、时间窗口、报名开关和重复报名 → 获取当前用户身份上下文 → 按快照条件顺序执行 → AND 聚合 → 保存条件结果快照和兼容布尔结果 → 创建报名记录。

## 风险与控制

- 处理器语义升级可能改变历史期次结果；通过处理器版本和快照配置识别，必要时保留旧处理器实现。
- 内置条件停用与历史模板引用可能产生操作困惑；UI 明确影响范围，生成新期次前强校验。
- 菜单迁移可能造成旧角色失去权限；迁移脚本按旧权限码映射到新父子菜单，并保留权限码兼容。
- 用户端展示条件失败原因存在信息泄露风险；只返回业务文案，不返回企微标识、数据库 ID 或内部异常。
