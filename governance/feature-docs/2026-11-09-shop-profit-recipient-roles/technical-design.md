# 技术设计

## 模块影响

| 模块 | 影响 |
|---|---|
| `yshop-module-store-biz` | 管理店铺主/非主收款人绑定；校验租户、店铺权限和收款人类型；通过现有 pay-api 写入关系历史。 |
| `yshop-module-pay-api` / `pay-biz` | 扩展内部绑定历史写入 API，区分用途和记录标记；订单结算状态同步按店铺与完整 Member ID 解析收款人；应收应付生成继续快照主收款人。 |
| `yshop-module-order-biz` | 无预期代码变更；继续提供现有订单支付信息查询。 |
| `admin/` | 店铺编辑维护主收款人和非主收款人；订单结算管理继续使用既有同步操作。 |
| 小程序、DMS | 无变更。 |

## 关键决策

### 主收款人保持唯一权威来源

继续使用 `yshop_store_shop.profit_sharing_recipient_id` 保存店铺主收款人，并保留现有 `profit_sharing_enabled` 语义。`ProfitRecipientApi.listByShop(shopId)` 继续只返回主收款人，不扩展为所有店铺收款人，以免计费和分账调用误把次级收款人作为出账目标。

订单分账计算、AdaPay 分账请求、失败重试和应收应付生成都沿用主收款人读取路径。应收应付在生成时固化该主收款人 ID；后续主/非主关系变更不回算历史应收应付或分账明细。

### 用现有绑定历史表达次级关系和状态

扩展 `yshop_adapay_profit_recipient_binding_history`，增加绑定用途和“有效/无效”记录标记。历史表继续保存收款人、Member ID、结算账户及店铺快照，并以 `valid_from` / `valid_to` 保留版本。

- `binding_purpose` 区分 `PRIMARY` 和 `RECONCILIATION`。
- `mark_status` 表示非主关系的 `VALID` / `INVALID` 标记；它与 `relation_status`（当前关系/已结束）是不同概念。
- 既有历史数据回填为 `PRIMARY`、`VALID`，保持现有主绑定的含义。
- 标记变化时关闭旧版本并新增版本；解绑时关闭当前关系。历史版本保留，不物理删除。
- 主绑定的历史写入只关闭该店铺的 `PRIMARY` 关系，不再关闭同店铺的 `RECONCILIATION` 关系。
- 收款人全局禁用时，不应因次级关系的记录标记而清除其店铺映射；次级绑定仍可用于订单结算匹配。主收款人的出账校验仍沿用现有启用状态要求。

该方案不新增第二个含义重叠的当前绑定表，并复用结算收款人采集已有的关系快照和有效期查询能力。

### 结算同步按店铺和 Member ID 匹配

保留现有订单结算管理“同步分账状态”接口和 AdaPay 查询流程。`ProfitSharingOrderServiceImpl` 导入远端确认明细时，将每个 `div_members[].member_id` 与订单所属店铺的主绑定及非主绑定历史匹配：

1. 以当前租户、订单 `shopId` 和完整 Member ID 查询关系历史；不使用脱敏 ID 做匹配。
2. `mark_status` 为有效或无效的非主关系均参与匹配；关系快照如有多版本，按收款人 ID 去重。
3. 仅有一个本地收款人 ID 时，远端明细关联该收款人并保存既有结算明细；无匹配或匹配到多个不同收款人时保留未映射语义，不能任意归属。
4. 对已有本地分账记录，同步仍只更新远端状态、手续费和既有本地明细的 `feeFlag`。支付时固化的本地收款人和金额不被远端同步改写。

当前 `resolveImportedRecipient` 仅以 `ProfitRecipientDO.shopId` 判断店铺归属；实现时应改为按绑定历史中的店铺关系解析，使非主收款人和曾经绑定过的收款人都可被匹配。Member ID 仅在本地查询和服务端处理中使用；响应按现有规则脱敏。

订单结算管理同步仍只查询 AdaPay 已有支付确认，不创建或重试分账。AdaPay Div/确认数据未提供来源渠道字段，因此不能据此断言异常分账来自哪个渠道，也不能控制 AdaPay 控制台或独立外部系统。

### 应收应付快照保持主收款人

`BillingSettlementServiceImpl` 当前通过 `ProfitRecipientApi.listByShop()` 获取店铺收款人。该方法保留主收款人语义，商家主体、`recipientId` 和结算快照继续只记录主收款人。不得将次级绑定并入 `listByShop()` 或模板收款人候选列表。

## 关键流程

### 管理绑定

管理端提交店铺主收款人、分账启用状态及非主收款人列表。店铺服务校验店铺权限和租户后更新主字段，并调用 pay-api 记录非主绑定快照。整组绑定在单次服务事务中完成；非主记录状态变更只影响标记版本，不影响匹配资格。

### 订单结算状态同步

管理员触发既有订单同步操作 → pay-biz 查询远端支付确认 → 汇总 `div_members` → 以订单所属店铺和 Member ID 解析本地收款人 → 更新远端结算状态和费旗标 → 对未映射/多重匹配明细保留未映射标识供核查。

### 应收应付生成

订单计费读取主收款人 → 生成商家主体和明细快照 → 固化主 `recipientId`。次级关系不参与计费、主体汇总或分账金额计算。

## 事务、幂等与兼容

- 店铺主/非主绑定写入复用现有 `store:shop:update` 权限和服务端校验；状态同步复用 `order:settlement:query`。
- 新的批量绑定写入以 `(tenant_id, shop_id, recipient_id, binding_purpose)` 幂等处理；重复 ID 拒绝或归一化，不产生重复有效关系。
- pay-api 只提供内部绑定历史写入能力，store-biz 不依赖 pay-biz；pay-biz 不读取 store-biz 数据库表。
- 既有 `bind-profit-recipient` 继续可用并只操作主收款人。新增配置接口用于一次提交主收款人与非主列表，避免新管理页出现两套写入语义。
- 不改写支付时订单明细、已完成的应收应付快照和历史对账结果。

## 风险与处理

| 风险 | 处理 |
|---|---|
| 次级收款人混入分账候选，造成资金发错 | `listByShop` 继续只返回主收款人；服务端出账入口不读取次级绑定。 |
| 旧历史写入会关闭同店铺全部关系 | 绑定历史按 `binding_purpose` 分别关闭；主收款人替换不得关闭次级关系。 |
| 远端 Member ID 未映射或同店铺出现多条本地收款人 | 精确匹配完整 ID；多重映射不猜测，结算明细标记未映射/待核查。 |
| 外部渠道来源不可识别 | 只显示 AdaPay 返回的状态和已知收款人归属，不推断渠道来源或承诺外部拦截。 |
| 应收应付重算覆盖历史主收款人 | 应收应付主体快照采用生成时主收款人；仅既有失败重试规则允许重算的记录按原幂等政策处理。 |
