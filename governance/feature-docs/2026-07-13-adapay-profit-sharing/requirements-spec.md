## Feature: Adapay 分账结算

### Scope

**In Scope**

1. 分账收款人管理（平台级 + 店铺级）。平台级收款人支持分账角色（平台/配送方/销售方）；店铺级收款人无需角色，默认归属于指定店铺。
2. 创建分账收款人时向 Adapay 同步创建个人/企业 Member，`member_id` 按规则编码：`m_{租户Id}_{memberType}_{IdCard}_{storeId|0 for 平台}`。同店铺同身份证号生成相同 `member_id`。
3. 创建分账收款人时向 Adapay 同步绑定结算账户（银行卡），绑定成功后方可入库。结算账户支持通过“更换结算账户”方式修改；编辑基础信息时不要求重新填写银行卡。结算账户信息须包含 Adapay 自定义四位省市编码 `prov_code` 与 `area_code`。
4. 店铺可绑定一个本店铺级的分账收款人，并启用/禁用分账。
5. Adapay 支付时采用延迟分账模式（`pay_mode=delay`）。
7. 店铺级分账计费规则：一个店铺对应一套规则，按角色（平台/店铺/配送方/销售方）拆分为多条记录；每条记录配置分账比例与是否承担手续费。
8. 支付/创建分账记录时，若店铺存在完整有效计费规则，按规则计算各方分账金额与手续费承担方，并将每个角色固化到分账明细记录；否则 fallback 到现有 `commission_rate` 逻辑，同样以平台、店铺两条明细记录固化。
9. 每日自动执行结算 Job，对当天达到可结算状态的订单确认并分账。
10. 分账订单查询与失败重试；分账失败时自动回退到现有虚拟余额结算。
11. 走 Adapay 支付且店铺启用分账的订单，在分账成功或回退到虚拟余额结算后，订单状态更新为待评价。
12. 支付时校验分账收款人配置，缺失时拒绝支付。

**Out of Scope**

- 非 Adapay 支付渠道的分账（微信、支付宝）。
- 退款触发分账回退的完整实现。
- Adapay Member 修改/查询/注销的独立管理功能。
- 已绑定银行卡完整卡号的明文展示。

**Deferred**

- 分账结算记录导出。

### Use Cases

**UC-1: 平台管理员创建分账收款人**

- 角色：平台管理员（超管/财务）
- 目标：为平台或某个门店创建可向 Adapay 接收分账资金的收款人。
- 主流程：
  1. 管理员进入分账收款人管理页面。
  2. 选择收款人类型（平台级/店铺级）。平台级需选择分账角色（平台/配送方/销售方）；店铺级无需角色。
  3. 填写收款人名称、Member 类型（个人/企业）、实名/企业信息。
  4. 填写企业 Member 信息。上传 zip 附件（含三证合一证件照、法人身份证正面照、法人身份证反面照、开户银行许可证照），中文文件名使用 UTF-8 URLEncode 编码；上传法人身份证正反面后，系统自动 OCR 识别并回填法人姓名、身份证号、身份证有效期。填写统一社会信用代码、有效期、经营范围、法人手机号、企业地址、Adapay 省市编码等必填信息。
5. 填写结算银行卡信息。银行选择器默认加载主要银行（`is_primary=1`），非主要银行通过关键字远程搜索（后端模糊匹配银行名称/编码）后选择，带出银行编码。开户省份、开户城市通过后端级联下拉选择，使用 Adapay 自定义四位编码。
  5. 提交后，后台同步向 Adapay 创建 Member 并绑定结算账户；成功后保存到本地。
- 业务规则：
  - 同一租户同一分账角色最多只能有一个启用中的平台级收款人。
  - `member_id` 编码规则天然保证同店铺同身份证号不可重复创建。
  - 若 Adapay Member 创建或结算账户绑定失败，本地不保存该收款人。
  - 删除收款人时须同步删除 Adapay 结算账户；Adapay 删除失败则本地删除失败。
  - 企业 Member 附件须为 zip 压缩包，内含三证合一证件照、法人身份证正面照、法人身份证反面照、开户银行许可证照，中文文件名使用 UTF-8 URLEncode 编码；单包最大 9MB。
  - 法人身份证正反面支持 OCR 自动识别并回填姓名、身份证号、有效期；识别失败时允许手动填写。
  - 结算账户开户省份、城市使用 Adapay 自定义四位编码，由后端提供级联数据；创建/更换结算账户时必填。

**UC-2: 门店管理员为店铺启用分账**

- 角色：门店管理员/运营
- 目标：让指定店铺在 Adapay 支付时参与延迟分账。
- 主流程：
  1. 管理员进入店铺编辑页。
  2. 从绑定该店铺的店铺级分账收款人列表中选择一个已启用的收款人。
  3. 打开分账启用开关并保存。
- 业务规则：
  - 启用分账时，必须已经选择了有效收款人。
  - 只能选择绑定该店铺的店铺级收款人，不可跨店选择。
  - 解绑后，店铺不再参与分账。

**UC-2A: 财务编辑分账收款人并更换结算账户**

- 角色：平台管理员（超管/财务）
- 目标：维护收款人基础信息或更换其收款银行卡。
- 主流程：
  1. 管理员进入分账收款人管理页面并打开编辑弹窗。
  2. 修改收款人名称、启用状态等允许编辑的信息。
  3. 选择更换结算账户后，填写完整的新银行卡信息、开户省份、开户城市并提交。
  4. 后台同步更新 Adapay 结算账户绑定；成功后新账户生效。
- 业务规则：
  - 未选择更换结算账户时，保存基础信息不得要求填写银行卡信息。
  - 更换结算账户时，必须提交完整的新银行卡信息、开户省份和开户城市。
  - 更换结算账户失败时，原结算账户保持有效，基础信息不得被部分保存成不一致状态。

**UC-3: 平台/财务为店铺配置分账计费规则**

- 角色：平台管理员/财务
- 目标：为店铺设定各角色分账比例与手续费承担方。
- 主流程：
  1. 管理员进入店铺分账计费规则配置页面。
  2. 选择目标店铺。
  3. 按角色（平台/店铺/配送方/销售方）逐条添加/编辑记录，填写分账比例、启用/禁用该角色并标记是否承担手续费。
  4. 保存后规则生效。
- 业务规则：
  - 一个店铺对应一套规则；同一角色在同一店铺下只有一条生效记录。
  - 角色不必全部启用；启用角色的分账比例之和必须等于 100%。
  - 手续费承担方必须是已启用的计费角色之一，且只有一方承担。
  - 禁用某角色时，该角色不得是手续费承担方。
  - 规则保存后，历史已创建的分账记录金额不受影响。

**UC-4: 用户使用 Adapay 支付并挂起分账**

- 角色：C 端用户（小程序/H5）
- 目标：完成订单支付。
- 主流程：
  1. 用户下单并选择 Adapay 支付。
  2. 系统校验店铺分账配置完整（平台与店铺收款人均有效）。
  3. 支付请求采用延迟分账模式，用户完成付款。
  4. 支付成功后，系统创建一条待分账记录，并将各角色分账金额、收款人、手续费承担方固化到分账明细表；无有效规则时 fallback 到 `commission_rate` 逻辑，按平台、店铺两条明细固化。
- 业务规则：
  - 若店铺启用分账但缺少有效平台/店铺收款人，或计费规则不完整，支付被拒绝并提示配置缺失。
  - 分账金额在创建记录时固化，不受后续 `commission_rate` 或计费规则变更影响。

**UC-5: 系统按店铺计费规则计算分账金额**

- 角色：系统
- 目标：在创建分账记录或分账确认前，确定各方应收金额与手续费承担方。
- 主流程：
  1. 系统读取店铺当前生效的计费规则。
  2. 若规则完整有效（至少启用一个角色，启用角色比例之和为 100%，且各启用角色已配置有效收款人），按各角色比例计算金额，并标记手续费承担方。
  3. 若规则缺失或不完整，fallback 到现有 `commission_rate` 逻辑：生成平台、店铺两条分账明细（平台 = commission_amount，店铺 = pay_price - commission_amount）。
- 业务规则：
  - 计算结果必须保证各方金额之和等于订单实付金额。
  - 手续费承担方在调用 Adapay 分账确认时反映到对应角色的 `fee_flag` 上。

**UC-6: 日终自动执行分账结算**

- 角色：系统
- 目标：对当天达到可结算状态的订单进行确认并分账，并更新订单状态。
- 主流程：
  1. 系统在每日固定时间触发结算。
  2. 查询当天订单状态为待收货或退款拒绝的订单。
  3. 逐笔确认订单并向 Adapay 执行分账确认。
  4. 分账成功则将分账记录更新为成功状态，并将订单状态更新为待评价。
  5. 分账失败则标记为可分账失败状态，自动回退到现有虚拟余额结算，并将订单状态更新为待评价。
- 业务规则：
  - 同一订单不会被重复分账。
  - 分账失败支持管理后台手动重试。
  - 订单状态仅在 Adapay 分账成功或已回退到虚拟余额结算后更新为待评价。

**UC-7: 财务查询分账订单并处理失败分账**

- 角色：财务/运营
- 目标：掌握分账执行情况，修复失败分账。
- 主流程：
  1. 财务进入分账结算记录页面。
  2. 按订单号、店铺、状态、时间等条件查询分账记录。
  3. 对失败且未回退的分账记录发起手动重试。
- 业务规则：
  - 仅失败状态且未回退的记录可重试。
  - 分账操作日志需记录请求/响应数据以便排查。

### Frontend Requirements

**管理后台**

| 页面 | 功能 |
|------|------|
| 分账收款人管理 | 新增/编辑/删除/分页列表/搜索。 |
| 分账收款人表单 | 新增/编辑弹窗；支持个人/企业两种 Member 类型；创建时填写结算账户（含开户省份/城市），编辑时可选择更换结算账户。 |
| 分账结算记录 | 只读列表/搜索/失败重试。 |
| 店铺分账配置 | 选择分账收款人 + 启用开关。 |
| 店铺分账计费规则 | 按角色配置分账比例与手续费承担方；支持启用/禁用与编辑。 |

**菜单**

- 分账收款人管理、分账结算记录、店铺分账计费规则三个页面在管理后台的门店管理模块下可访问。

**小程序端**

无变更。分账流程对 C 端用户完全透明。

### Edge Cases

- 企业 Member 创建须按 Adapay `/v1/corp_members` 要求提供完整字段：`name`、`social_credit_code`、`social_credit_code_expires`、`business_scope`、`legal_person`、`legal_cert_id`、`legal_cert_id_expires`、`legal_mp`、`address`、`prov_code`、`area_code`、zip 附件等。
- 法人身份证正反面上传后，系统自动 OCR 识别并回填 `legal_person`、`legal_cert_id`、`legal_cert_id_expires`；识别失败时允许手动填写。
- 企业 Member 附件须为 zip 包，内含三证合一证件照、法人身份证正面照、法人身份证反面照、开户银行许可证照，中文文件名使用 UTF-8 URLEncode 编码；单包最大 9MB。
- 结算账户开户省份、开户城市使用 Adapay 自定义四位编码，由后端级联接口提供；创建/更换结算账户时必填，未更换时不强制填写。
- 店铺启用分账但缺少有效收款人，或计费规则不完整（启用角色比例和 ≠100%、无唯一承担方、承担方未启用、收款人缺失/禁用）时，应拒绝支付并给出明确提示；无任何有效规则时 fallback 到现有 `commission_rate` 逻辑。
- 手续费承担方必须是已启用的计费角色之一；承担方在调用 Adapay 分账确认时反映到对应角色的 `fee_flag` 上。
- 无论计费规则模式还是 `commission_rate` fallback 模式，创建分账记录时都必须写入分账明细表；新增角色只需扩展角色枚举，无需修改分账订单主表结构。
- 分账完成（Adapay 分账成功或自动回退到虚拟余额结算）后，走 Adapay 分账的订单应进入待评价状态；分账未完成不得进入待评价状态。
- 银行选择器默认仅加载主要银行（约数十条），避免全量加载 ~5,260 条银行数据导致表单打开卡顿。非主要银行通过关键字远程搜索获取。

### Acceptance Criteria

- [ ] 创建/更换分账收款人结算账户时填写并校验开户省份、开户城市；Adapay 接口不再因 `prov_code` 缺失报错。
- [ ] 未选择更换结算账户时，不强制填写省市编码。
- [ ] 企业 Member 创建时按 Adapay `/v1/corp_members` 要求提供完整字段与 zip 附件。
- [ ] 法人身份证正反面支持 OCR 识别并自动回填姓名、身份证号、有效期。
- [ ] 走 Adapay 分账的订单在分账成功或自动回退到虚拟余额结算后，订单状态变为待评价。
- [ ] 店铺存在完整有效计费规则（至少一个启用角色，启用角色比例和=100%，有唯一启用承担方且已配置有效收款人）时，按规则计算各方分账金额与手续费承担方，并写入分账明细表；无有效规则或规则不完整时 fallback 到现有 `commission_rate` 逻辑，同样以平台、店铺两条明细写入。
- [ ] 分账订单主表不包含角色相关字段；新增角色时无需修改主表结构，仅需扩展角色枚举并确保存在对应收款人。
