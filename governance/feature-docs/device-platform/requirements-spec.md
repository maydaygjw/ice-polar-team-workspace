# 需求规格 — 通用设备平台与制冰机迁移

## Scope

### In-scope

- 将 `device` 重构为通用设备平台，由 `device-core` 定义设备通用规范。
- 设备规范至少包含设备号、设备类型、租户归属、生命周期状态、连接状态和可用/占用状态。
- 在 `device-core` 暂时定义通用设备操作订单，用于记录设备操作申请、执行和结果。
- 新增 `device-ice` 能力模块，将现有制冰机状态查询、指令下发和设备订单迁移到新架构。
- 保持现有制冰机外部 API、DMS/MQTT 通信边界和已有业务行为兼容。
- 为后续设备能力扩展预留清晰的 API、适配器和状态边界，但本期不实现其他能力。

### Out-of-scope

- 本期不新增其他设备类型的业务能力。
- 本期不改造 DMS 内部 MQTT 主题、硬件协议、固件或设备网关。
- 本期不新增设备与门店之间的独立绑定/解绑概念和接口；继续沿用当前已有归属关系。
- 本期不改变商城订单的支付、库存、佣金、退款和财务语义。
- 本期不实现管理后台页面改造。

### Deferred

- 通用设备批量导入、批量迁移和设备生命周期后台操作。
- 设备能力插件市场、能力动态注册和跨租户设备共享。
- 通用设备操作订单是否最终迁移到 `order` 模块。

## Use Cases

### 系统管理员 - 管理通用设备

- 系统可以登记设备号和设备类型，并记录设备所属租户和当前状态。
- 系统可以查询设备的连接状态、可用状态和最近一次通信时间。
- 设备规范不应包含制冰机专属字段或命令含义。

### 制冰机用户 - 使用迁移后的制冰能力

- 用户可以按原有方式查询制冰机状态。
- 用户可以按原有方式下发制冰机指令。
- 用户可以创建并查询制冰机设备操作订单，结果与迁移前一致。

### 系统 - 执行通用设备订单

- 设备能力可以创建通用设备操作订单，记录设备、操作类型、发起人、业务关联号和执行结果。
- 制冰机能力可以在通用订单上扩展冰量规格和设备执行信息。
- 通用订单失败或取消时，不得错误修改商城订单状态。

## Business Rules

- 设备连接状态和可用/占用状态是两个独立维度；设备可以同时在线且占用。
- 连接状态至少支持 `ONLINE`、`OFFLINE`、`UNKNOWN`。
- 可用状态至少支持 `IDLE`、`OCCUPIED`、`MAINTENANCE`、`DISABLED`。
- 通用设备订单只表达设备操作履约，不等同于商城支付订单。
- 所有新增设备和设备订单数据必须按租户隔离；需要门店范围时沿用现有数据权限。
- 迁移后旧制冰机 API 的路径、入参和结果语义保持兼容。
- DMS/MQTT 仍由后端设备模块间接调用，小程序不得直接连接 DMS。

## Frontend Requirements

N/A：本期只完成 backend 设备核心和制冰机迁移，不修改管理后台和小程序页面；现有小程序调用的制冰机接口必须保持兼容。

## Edge Cases

- 设备在线但正在执行互斥操作时，新的互斥设备订单必须被拒绝或进入明确的排队状态。
- 设备离线时，不能把可用状态错误改成空闲；恢复上线后再由设备状态同步更新。
- 重复查询、重复指令请求和重复设备回调不得创建重复设备订单或重复执行不可幂等操作。
- 历史制冰机设备记录只有旧 `imei` 时，迁移后仍必须可以查询和操作。
- 旧设备订单和新通用设备订单并存期间，查询结果不得重复展示同一业务订单。
- 设备租户变更、设备停用和历史订单关系不在本期开放为独立绑定操作。

## Acceptance Criteria

- [ ] `device-core` 明确定义设备号、设备类型、状态和通用设备订单规范。
- [ ] 连接状态与可用/占用状态可以独立表达。
- [ ] `device-ice` 承接现有制冰机状态、指令和设备订单能力。
- [ ] 现有制冰机 API 和 DMS/MQTT 调用链路回归通过。
- [ ] 通用核心不包含制冰机专属枚举、命令路径和产品规格字段。
- [ ] 通用设备订单可以记录设备操作生命周期，并与商城订单保持边界。
- [ ] 新旧设备数据迁移期间不丢失历史设备和订单信息。
- [ ] 全部新增查询满足租户隔离和既有数据权限要求。

## Assumptions

- “通用设备订单”本期先归属 `device-core`；只有未来需要独立支付、退款或财务结算时，才重新评估迁移到 `order`。
- 当前设备与业务主体的归属关系继续沿用现有字段和服务，不新增独立绑定表或 bind/unbind API。
- 本期只迁移制冰机，不实现其他设备能力。
