# 技术设计：活动模板中奖策略

## 模块影响

- `backend/yshop-module-activity`：模板策略字段校验/读写、期次快照、统一开奖加权抽样、即时抽奖赔率计算及单元测试。
- `backend/yshop-module-member-api`：复用现有 `MemberUserApi.getUserStages(Collection<Long>)`；不新增接口或依赖。
- `admin`：活动模板在开奖/抽奖模式下增加策略选项，创建、编辑、详情和复制均保留策略值。
- `governance`：新增本功能契约和功能文档索引。

## 关键决策

1. 模板与期次快照各增加 `winning_strategy`，代码值由策略接口实现提供：`FAIR`、`PREFER_NEW_USERS`、`PREFER_AT_RISK_AND_LOW_FREQUENCY`、`RETENTION_REACTIVATION_TIERS`。字段默认 `FAIR`，保证老模板、老期次及旧请求兼容。
2. 新增 `ActivityWinningStrategy` 接口：`code()`、`name()`、`weightFor(String userStage)`。每套策略作为 Spring Bean 实现；`ActivityWinningStrategyRegistry` 收集 Bean 并按稳定代码解析，重复代码或缺少公平策略会导致启动失败。新增策略仅需增加实现，不修改开奖服务的策略类型分支。模板保存拒绝未知代码，历史空值及运行时未知快照值回退 `FAIR`。
3. 期次生成时将模板策略代码复制到 `yshop_activity_period_snapshot`。抽奖和统一开奖只读取期次快照，模板后续编辑不回写既有期次。
4. 画像阶段通过活动模块已有 `MemberUserApi` 批量读取。画像阶段缺失或不在目标集合时策略返回权重 1.0；画像 API 查询异常回滚当前抽奖事务，避免配置的倾斜策略静默退化。
5. 统一开奖保留现有按奖品顺序和奖品数量分配的流程。公平策略继续使用原有等概率洗牌；偏向策略为每个报名抽奖机会建立权重项，以权重不放回抽取，每名用户的每次机会权重相同。开启 `singleWinner` 后，该用户剩余机会不再进入后续抽取。
6. 即时抽奖将每个奖品与“未中奖”视为结果项。策略接口返回的阶段权重用于重新归一化所有奖品概率，维持奖品之间的相对概率。`P` 为原中奖概率总和，`W` 为画像权重，新中奖概率为 `P×W / (100−P + P×W)`；各奖品按原概率占比获得新概率。公平策略沿用原概率。
7. 画像阶段由服务端根据当前会员 ID 查询，客户端不能提交用户阶段或权重。现有查询按登录租户隔离，不增加权限。
8. `RETENTION_REACTIVATION_TIERS` 实现递减分层：`at_risk=3.0`、`low_frequency=2.0`、`new=1.2`、`mid_frequency=0.7`、`high_frequency=0.3`，未画像/未知阶段及未列明的 `churned` 保持 `1.0`。权重是初始业务假设，建议用公平策略随机留出组验证增量毛利和 30 天复购后再调整。

## 必要流程

- 模板保存：通过策略注册表校验 draw mode 与策略代码，未提供策略时按 `FAIR` 保存；游戏模式隐藏该字段且固定保存为 `FAIR`。
- 期次创建：读取模板策略并写入期次快照。
- 统一开奖：锁定期次、批量读取有效报名人阶段、按策略构造票权并依序分配奖品，沿用既有状态更新、中奖记录及次数消耗。
- 即时抽奖：先进行已有请求幂等检查；新请求读取期次快照策略和当前会员阶段，调整抽奖概率后执行原有次数、库存、单人中奖和中奖记录逻辑。

## 迁移与回滚

- 新增单个 Flyway 迁移，在模板表和期次快照表增加非空 `winning_strategy VARCHAR(64) NOT NULL DEFAULT 'FAIR'` 字段。已有数据由默认值填充。
- 应用回滚可使用旧版本读取数据库；保留新增字段和已选策略值，不执行 drop column。若要彻底移除字段，须先确认所有应用版本已不再使用且接受策略值丢失，再单独安排向前迁移。

## 风险

- 画像仅保留当前值，统一开奖使用执行时的最新画像阶段；策略本身使用期次生成时的快照值。
- 加权随机是概率提升，不提供确定性名额；少量样本下实际获奖人数可能与期望比例不同。
- 即时抽奖原概率总和不足 100% 时，调整中奖和未中奖的比例仍保留未中奖结果，不把总概率补到 100%。
