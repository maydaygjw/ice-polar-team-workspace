# 技术设计：企业微信群临时二维码

## 模块影响

- `backend`：客户群管理接口按租户、企业微信账号和群在 Redis 中复用临时配置；重复请求延长缓存和 Redis 延迟清理任务。消费者按消息携带的租户及企业微信账号信息删除配置。
- `admin`：客户群操作栏入口、二维码弹窗及下载。
- 数据库：无变更。`config_id` 仅存在于创建请求响应和 Redis 延迟消息中。

## 关键决策

- 使用企业微信客户群进群方式 API 创建二维码，绑定单个现有 `chat_id`。
- 创建接口返回 `config_id` 后，调用获取进群方式接口读取 `qr_code`，并在服务端下载图片后以 data URL 返回管理端，支持可靠预览和下载。
- 清理时长为 1 小时，从企业微信成功创建配置的时间开始计时。
- 群二维码配置 ID 只存于 Redis，缓存 TTL 为 1 小时；复用时返回原配置二维码并刷新 TTL、投递新的延迟清理计划。清理消息使用唯一代次 ID，消费者在群级分布式锁内校验代次，忽略已经续期配置的旧消息。
- 消息至少携带 `tenantId`、`accountId`、`configId`、创建时间和重试次数。消费者切换到消息租户上下文后查找账号凭证；消息体不含 Secret 或 access token。
- 复用 message 模块的延迟监听器契约；将通用 `DelayedQueueListener` 接口置于 message-api，使 mp-biz 可实现监听器而不依赖 message-biz。
- 后端先成功创建企业微信配置，再投递延迟消息。若消息投递失败，立即尝试删除新配置；如立即删除也失败，记录配置 ID 和关联信息并进入重试/告警处理，避免孤儿配置。
- 现有延迟监听器在 `take()` 后才调用消费者，失败不会自动放回原消息。新消费者自行捕获失败并用指数退避延迟重新投递，间隔上限为 60 分钟；持续失败时保留任务并持续记录告警日志，不能只依赖 `whenExceptionFinally()`。
- 企业微信删除按配置 ID 执行。配置已不存在按成功处理，保证重复消费幂等。

## 外部接口

- 创建：企业微信 `POST /cgi-bin/externalcontact/groupchat/add_join_way`，请求绑定一个 `chat_id`，返回 `config_id`。
- 删除：企业微信 `POST /cgi-bin/externalcontact/groupchat/del_join_way`，请求携带 `config_id`。
- 管理端新增后端接口：`POST /admin-api/mp/wecom-customer-group/qrcode?id={groupId}`，响应包含二维码地址及失效时间。
- 权限：复用 `mp:wecom-customer-group:query`，不新增权限码。

## 异常与可观测性

- 记录创建、清理成功、重试和最终失败事件，日志标注租户、企业微信账号、群和配置 ID；禁止记录 Secret、access token。
- 创建配置成功但响应字段缺失时按失败处理并尽可能执行补偿删除。
- 清理失败后按指数退避持续重试，间隔上限为 60 分钟；队列重试写入失败时记录 ERROR 日志。

## 回滚

无数据库迁移。回滚前停止创建入口和新消息生产；已入队清理消息的消费者需保留到队列清空，或执行运维清理，避免遗留企业微信进群配置。
