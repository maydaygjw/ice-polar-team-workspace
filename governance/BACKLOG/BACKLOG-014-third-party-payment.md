## Problem / Need

部分业务订单由外部系统创建和管理，但支付由本平台承接。外部系统希望发起支付并及时知道结果，不希望自行接入和维护各支付渠道。

当前外部系统尚无可供其安全使用的业务支付能力，也缺少稳定获知支付最终结果的方式。业务人员需要在两个系统之间人工核对订单和支付状态。

## Context (Optional)

已有第三方客户端认证能力。初步业务方向是由平台统一处理支付，外部系统提交支付请求后可获取支付进展，并在支付状态变化时获知结果。具体接入方式和支付场景需在需求评审阶段确认。

## 初步方案（待评审）

### API 边界与认证

- 第三方业务 API 使用独立前缀 `/open-api/v1`，与 `/app-api`、`/admin-api` 平级。第三方客户端凭证不代表会员或管理员身份，不直接复用现有会员下单/支付接口。
- 业务 API 使用 `client_credentials` Bearer token，并在每个路由显式校验 scope。建议 scope 为 `payment:create`、`payment:read`、`payment:close`。
- 当前 token 接口 `POST /admin-api/system/oauth2/token` 继续兼容；可增加 `POST /open-api/oauth2/token` 作为面向外部集成的入口，避免现有客户端必须同时迁移。
- 客户端凭证映射到所属租户和可用支付配置。业务请求不得自行指定 `tenantId`、商户密钥或任意支付通知地址；支付配置由服务端按客户端绑定关系选择。

### 支付单接口

| 用途 | 方法与路径 | 建议权限 |
|---|---|---|
| 创建支付单 | `POST /open-api/v1/payments` | `payment:create` |
| 查询支付单 | `GET /open-api/v1/payments/{paymentId}` | `payment:read` |
| 按外部单号查询 | `GET /open-api/v1/payments/by-client-order/{clientOrderNo}` | `payment:read` |
| 关闭未支付单 | `POST /open-api/v1/payments/{paymentId}/close` | `payment:close` |

创建请求建议包含：

```json
{
  "clientOrderNo": "外部系统内唯一的业务订单号",
  "amount": 12800,
  "currency": "CNY",
  "subject": "订单标题",
  "paymentChannel": "H5"
}
```

`amount` 使用最小货币单位（人民币分）的整数；`clientOrderNo` 在同一客户端范围内唯一。支付渠道只允许使用该客户端/租户已启用的渠道，未传时可按租户默认配置选择。

创建成功后返回平台 `paymentId`、外部订单号、支付状态、过期时间，以及可选的 `checkoutUrl` 或二维码数据。由于第三方不想自行接入支付渠道，建议由平台提供托管收银页；用户在托管页完成支付，第三方系统无需保存支付渠道密钥或生成渠道签名。

### 幂等与状态处理

- 创建请求必须支持 `Idempotency-Key`；相同客户端、幂等键和请求内容重试时返回原支付单，不重复创建或扣款。
- 同一客户端的 `clientOrderNo` 应具备唯一约束；相同订单号但金额或订单内容不一致时返回明确冲突错误。
- 支付状态至少区分待支付、支付中、成功、失败、已关闭和已退款。订单状态以平台验签后的支付渠道通知及后端查单结果为准，不以浏览器跳转或客户端上报为准。
- 金额、币种、客户端所属租户和支付单关系在创建后保持不可被普通重试请求覆盖。

### 支付结果通知

- 支付终态通过 Webhook 通知第三方，事件类型至少包含 `payment.succeeded`、`payment.failed`、`payment.closed` 和 `payment.refunded`。
- Webhook 地址由管理员在客户端配置中维护，不允许每次创建支付单时提交任意 URL。每个客户端使用独立通知签名密钥。
- 通知包含唯一 `eventId`、事件类型、平台支付单号、外部订单号、最终状态、金额、币种和发生时间；使用 HMAC-SHA256 对时间戳和请求体签名。
- Webhook 采用至少一次投递，失败按退避策略重试；接收方按 `eventId` 幂等处理并返回 2xx 确认。提供支付状态查询接口作为通知丢失时的补偿方式。
- 不向第三方开放内部 RocketMQ 或 Redis 消息通道。

### 需要评审确认

- 托管收银页支持的渠道和客户端场景（H5、扫码等）。
- 外部订单金额、退款、部分退款和支付关闭的业务边界。
- Webhook 的重试时长、签名密钥轮换方式、限流和对账需求。
- 租户与第三方客户端的绑定、客户端停用后的存量支付单处理规则。

## Acceptance Criteria (Optional)

- [ ] 外部系统可以为其业务订单发起支付，并能确认支付请求对应的订单。
- [ ] 支付成功、失败或关闭后，外部系统可以及时获知最终状态。
- [ ] 重复提交同一业务订单不会造成重复支付。
- [ ] 支付信息和结果按所属业务方隔离，外部系统不能查看其他业务方的订单。
- [ ] 外部系统无需直接接入各支付渠道或保管支付渠道密钥。
- [ ] 客户端只能使用明确授予的支付 scope；无权限或跨租户查询会被拒绝。
- [ ] Webhook 有签名校验、失败重试和重复事件处理规则。
