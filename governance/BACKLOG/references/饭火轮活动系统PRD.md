# 饭火轮活动系统 PRD

> 文档版本：V1.0  
> 文档状态：需求基线  
> 适用范围：饭火轮小程序、活动后台、企业微信群池、微信客服兑奖链路

## 1. 背景与产品定位

饭火轮需要承载霸王餐、红包、新店试吃、优惠活动等多种校园运营活动。活动具有短期性，福利群具有长期性，微信客服则更适合承担兑奖、售后和异常处理，不宜成为所有活动流量的强制入口。

本方案将饭火轮小程序定义为：

- Activity Router：统一承接外部、内部活动入口，识别活动和来源，并根据用户状态决定下一步动作。
- Identity Hub：以 `fhl_user_id` 为主身份，逐步关联小程序用户、企微客户、微信客服客户等身份。

将微信客服定义为 Service Hub：

- 霸王餐兑奖
- 订单售后与退款问题
- 活动异常处理
- 人工客服接入

核心模型为：

```text
Activity → GroupPool → Group
User → GroupPoolMembership
User(fhl_user_id) → 多种外部 identity
```

## 2. 产品目标

### 2.1 业务目标

1. 让所有活动入口尽量直接进入饭火轮小程序原生活动页。
2. 通过 `activityId`、`source` 记录活动和渠道来源，支持完整转化分析。
3. 多个活动复用同一校区的长期福利群池，避免重复建群和重复拉群。
4. 不因潜在兑奖需求，强制所有参与用户提前绑定微信客服。
5. 中奖后通过微信客服完成身份识别、订单收集、截图审核和退款。
6. 建立可复用的身份绑定能力，为后续会员、优惠券、售后等场景提供基础。

### 2.2 用户目标

- 用户能快速理解活动规则和参与条件。
- 已在福利群的用户不被重复引导进群。
- 未入群用户能进入当前可用群，而不是过期或已满的群。
- 用户中奖后无需重复解释背景，客服能识别其活动和订单。
- 退款过程透明，用户能看到审核和退款状态。

### 2.3 非目标

V1 不包含以下能力：

- 不要求每个用户参加活动前绑定微信客服。
- 不把活动直接绑定到某个具体微信群。
- 不为每个活动单独创建微信群。
- 不以 H5 作为主要活动承载页面。
- 不在 V1 实现全链路精确判断“用户是否已加入微信群”（如果企微侧暂未提供可靠数据）。
- 不在 V1 实现复杂的自动中奖判定或自动审核替代人工。
- 不建设完整 CRM、会员等级或营销自动化平台。

## 3. 角色与职责

| 角色 | 主要职责 |
|---|---|
| 普通用户 | 查看活动、下单、加入福利群、参与群内开奖、提交兑奖材料 |
| 运营人员 | 创建活动、配置规则、绑定群池、配置来源和活动时间、查看数据 |
| 客服人员 | 接待中奖用户、引导绑定身份、收集订单及截图、处理异常 |
| 审核人员 | 审核中奖截图、订单资格和退款金额 |
| 财务/管理员 | 处理退款账户、退款失败、风控和审计 |
| 系统 | 识别用户、计算下单状态、选择群、生成绑定令牌、记录埋点和状态 |

## 4. 总体方案

### 4.1 入口原则

外部和内部入口均尽量直接打开小程序原生活动页：

```text
线下海报 / 朋友圈 / 微信群 / 小程序 Banner / 分享卡片
                         ↓
饭火轮小程序活动页
       activityId + source + 可选 campaignId
```

建议使用小程序码、短链或小程序分享卡片承载入口，而不是普通 H5。

### 4.2 活动与群池

Activity 只关联 `GroupPool`，不直接保存具体群链接：

```text
Activity 101
    ↓
GroupPool：怀院长期福利群池
    ↓
当前可用群：怀院福利 37 群
```

当 37 群满员或失效时，运营只需切换群池的当前承接群为 38 群，历史活动入口无需修改。

### 4.3 客服定位

用户参加活动不强制绑定微信客服。活动页只根据活动规则、用户下单状态和群池成员状态决定 CTA。

用户中奖后进入微信客服兑奖。首次使用客服且尚未建立身份映射时，客服生成一次性 `bind_token`，通过小程序跳转完成：

```text
微信客服 external_userid
          ↓ bind_token
饭火轮小程序 wx.login()
          ↓
饭火轮后台识别 fhl_user_id
          ↓
建立 Identity Binding
```

## 5. 核心流程

### 5.1 外部入口到活动页

1. 用户扫描活动小程序码或点击活动链接。
2. 小程序打开统一活动页，并解析 `activityId`、`source`、`campaignId`。
3. 系统完成小程序登录，识别或创建 `fhl_user_id`。
4. 系统记录活动访问和来源埋点。
5. 页面加载活动内容、资格条件、用户下单状态和群池状态。

### 5.2 活动页 CTA 决策

```text
打开活动页
    ↓
活动是否有效？ ── 否 → 展示活动已结束/未开始
    ↓ 是
用户是否满足下单条件？
    ├─ 否 → 【去下单】+展示规则
    └─ 是
      ↓
用户是否已在对应 GroupPool？
    ├─ 是 → 【查看福利群/已加入】
    └─ 否 → 【加入福利群】→ 当前可用群
```

如果 V1 暂时无法可靠取得群成员状态，则降级为展示【加入福利群】或【查看福利群】；不得将微信客服绑定状态误认为群成员状态。

### 5.3 加入福利群

1. 系统根据活动关联的 `group_pool_id` 获取当前有效群。
2. 校验群是否有效、是否达到容量、是否在有效期内。
3. 展示企微群二维码/活码或群入口。
4. 记录群引导展示、复制/打开、加入确认等事件。
5. 用户返回活动页后，刷新群池成员状态（如可获取）。

### 5.4 群内开奖与兑奖

```text
用户完成下单
    ↓
加入校区长期福利群
    ↓
群内进行霸王餐红包开奖
    ↓
中奖用户点击兑奖入口
    ↓
进入微信客服
    ↓
查询/绑定饭火轮身份
    ↓
提交订单信息与中奖截图
    ↓
人工审核
    ↓
审核通过 → 系统自动退款
```

### 5.5 微信客服身份绑定

绑定要求：

- `bind_token` 使用安全随机值，建议不少于 256 bit 熵。
- 默认有效期 10 分钟。
- 一次性使用，绑定成功后立即失效。
- 不在小程序参数中直接暴露 `external_userid`。
- 绑定前后记录操作日志，支持审计和异常追踪。

客服侧流程：

1. 接收微信客服用户身份和上下文。
2. 查询是否已存在 `weChatKf` 到 `fhl_user_id` 的映射。
3. 已绑定：直接查询活动、订单和兑奖状态。
4. 未绑定：生成 `bind_token`，发送饭火轮小程序卡片。
5. 用户完成小程序登录后提交令牌。
6. 后台校验令牌、身份和有效期，建立绑定。
7. 返回客服继续兑奖。

## 6. 页面需求

### 6.1 活动页

页面模块：

1. 活动封面、标题、活动状态。
2. 活动时间、参与条件、开奖时间、奖励说明。
3. 用户状态卡片：
   - 今日是否有符合条件的订单
   - 是否已满足参与资格
   - 是否已加入对应福利群
   - 是否已兑奖（中奖后）
4. 主 CTA：根据状态动态展示。
5. 活动规则和注意事项。
6. 群入口说明及群有效性提示。
7. 客服入口：仅用于兑奖、售后或异常，不作为普通参加活动的强制步骤。

CTA 文案示例：

| 状态 | 主 CTA | 辅助提示 |
|---|---|---|
| 活动未开始 | 暂未开始 | 展示开始时间 |
| 活动已结束 | 活动已结束 | 可推荐其他活动 |
| 未下单 | 去下单 | 今天下一单即可参与 |
| 已下单、未入群 | 加入福利群 | 今晚在群内开奖 |
| 已入群 | 查看福利群 | 无需重复加入 |
| 已中奖 | 去兑奖 | 进入客服提交材料 |
| 已提交审核 | 查看兑奖进度 | 展示审核状态 |
| 已退款 | 查看退款结果 | 展示退款金额和时间 |

### 6.2 兑奖引导页/客服落地页

V1 可采用客服消息 + 小程序页面组合实现。页面需展示：

- 当前活动名称
- 中奖状态或待核验状态
- 用户身份绑定状态
- 需要提交的材料
- 订单选择或订单号输入
- 中奖红包/中奖截图上传
- 提交后的审核进度

### 6.3 结果页

至少支持以下状态：

- 提交成功
- 审核中
- 审核通过，退款处理中
- 退款成功
- 审核驳回，展示原因和补充材料入口
- 退款失败，展示联系客服入口

## 7. 后台配置需求

### 7.1 活动管理

字段建议：

- 活动名称、活动类型、活动描述
- 封面图、规则文案、活动标签
- 开始时间、结束时间、开奖时间
- 适用校区/门店
- 下单资格规则
- 奖励规则及最高退款金额
- 关联 `group_pool_id`
- 状态：草稿、待发布、进行中、已结束、已下线
- 活动码/活动链接
- 来源参数白名单

能力要求：创建、编辑、复制、发布、下线、预览、查看访问和转化数据。

### 7.2 群池管理

字段建议：

- 群池名称
- 校区/区域
- 群池用途和说明
- 当前承接群
- 群列表及优先级
- 群二维码/活码
- 容量、有效期、状态
- 群满员阈值

系统需支持群的启用、停用、切换、容量预警和失效处理。

### 7.3 兑奖管理

- 中奖记录查询
- 订单和截图查看
- 审核通过/驳回
- 驳回原因模板
- 退款金额确认
- 退款任务和失败重试
- 操作人、操作时间、审计记录

### 7.4 身份管理

- 查看 `fhl_user_id` 及关联 identity
- 查看绑定来源和绑定时间
- 查看绑定状态
- 异常解绑/换绑（仅管理员，需二次确认和审计）
- 查看疑似一人多号、同订单多次兑奖等风险标记

## 8. 数据模型建议

### 8.1 User

| 字段 | 说明 |
|---|---|
| `id` | `fhl_user_id`，饭火轮主用户 ID |
| `status` | 正常、冻结、注销 |
| `campus_id` | 常用校区，可为空 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

### 8.2 Identity

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `fhl_user_id` | 关联饭火轮用户 |
| `identity_type` | `mini_program`、`wecom_customer`、`wechat_kf` |
| `provider` | 微信/企业微信等 |
| `external_id` | 外部身份标识，需加密或脱敏存储 |
| `status` | active、revoked |
| `bound_at` | 绑定时间 |
| `last_seen_at` | 最近识别时间 |

约束：同一 `identity_type + provider + external_id` 至多绑定一个有效 `fhl_user_id`。

### 8.3 Activity

| 字段 | 说明 |
|---|---|
| `id` / `activity_code` | 活动标识 |
| `type` | 霸王餐、红包、试吃等 |
| `title` / `content` | 展示内容 |
| `start_at` / `end_at` | 活动时间 |
| `draw_at` | 开奖时间 |
| `eligibility_rule` | 下单资格规则 JSON |
| `reward_rule` | 奖励规则 JSON |
| `group_pool_id` | 关联长期群池 |
| `status` | 活动状态 |

### 8.4 GroupPool / Group

`GroupPool` 表示校区长期福利群池；`Group` 表示池内具体微信群。

关键字段：

- GroupPool：`id`、`name`、`campus_id`、`status`
- Group：`id`、`group_pool_id`、`name`、`join_url`/`qr_code`、`capacity`、`member_count`、`priority`、`status`、`valid_until`

### 8.5 GroupPoolMembership

| 字段 | 说明 |
|---|---|
| `fhl_user_id` | 饭火轮用户 |
| `group_pool_id` | 群池 |
| `group_id` | 实际加入的群，可为空 |
| `status` | unknown、invited、joined、left、blocked |
| `source_activity_id` | 首次由哪个活动引导 |
| `joined_at` | 加入时间 |
| `last_verified_at` | 最近验证时间 |

### 8.6 ActivityParticipation

记录用户是否参与活动、是否满足资格、是否中奖和是否兑奖：

- `activity_id`
- `fhl_user_id`
- `source`
- `order_qualified`
- `group_status`
- `participation_status`
- `winner_status`
- `redeem_status`
- `created_at` / `updated_at`

### 8.7 BindToken

- `token_hash`：仅存哈希，不存明文
- `fhl_user_id`：绑定成功后写入
- `wechat_kf_external_id`
- `purpose`
- `expires_at`
- `used_at`
- `created_at`

### 8.8 Redemption / Refund

记录兑奖和退款全过程：

- 活动、用户、中奖信息
- 订单号/订单 ID
- 中奖截图及文件元数据
- 申请退款金额、审核金额
- 审核状态、审核意见、审核人
- 退款状态、退款单号、失败原因
- 全部状态变更日志

## 9. 接口建议

以下为逻辑接口，实际路径可按现有服务规范调整。

### 9.1 活动与用户状态

```http
GET /api/activities/{activityId}
GET /api/activities/{activityId}/context
```

`context` 返回：活动状态、用户下单资格、群池状态、用户群成员状态、CTA 建议和兑奖状态。

### 9.2 活动访问与参与

```http
POST /api/activities/{activityId}/visits
POST /api/activities/{activityId}/participation
```

请求中包含 `source`、`campaignId`、设备/会话信息和当前 `fhl_user_id`。

### 9.3 群池

```http
GET /api/group-pools/{groupPoolId}/current-group
GET /api/group-pools/{groupPoolId}/membership
POST /api/group-pools/{groupPoolId}/join-intent
```

### 9.4 身份绑定

```http
POST /api/identity/bind-tokens
POST /api/identity/bind
GET /api/identity/me
```

生成令牌时由服务端根据客服上下文写入 `wechat_kf_external_id`；小程序端只提交令牌和登录凭证，不提交客服外部身份。

### 9.5 兑奖与退款

```http
POST /api/redemptions
POST /api/redemptions/{id}/materials
GET /api/redemptions/{id}
POST /api/redemptions/{id}/review
POST /api/refunds/{id}/execute
```

所有写接口要求幂等键，避免重复提交和重复退款。

## 10. 状态机

### 10.1 活动状态

```text
草稿 → 待发布 → 进行中 → 已结束
                  └──────→ 已下线
```

### 10.2 群状态

```text
待启用 → 可用 → 接近满员 → 已满/不可用 → 已归档
```

### 10.3 兑奖状态

```text
未申请
  ↓
已提交 → 审核中
             ├─ 驳回 → 待补充 → 审核中
             └─ 通过 → 退款处理中 → 退款成功
                                      └→ 退款失败 → 人工处理
```

## 11. 风控与安全

1. 活动入口参数只允许传递 `activityId`、`source` 等非敏感标识，不暴露客服 `external_userid`。
2. `bind_token` 使用哈希存储、短期有效、一次性消费，并限制尝试次数。
3. 身份绑定必须校验小程序登录态，禁止仅凭 URL 参数绑定。
4. 同一订单、同一中奖资格只能成功兑奖一次。
5. 同一用户、设备、手机号、支付账户等维度设置频率和异常检测。
6. 退款金额不得超过订单实付金额和活动配置上限。
7. 截图和订单材料限制文件类型、大小和数量，必要时做病毒扫描和敏感信息保护。
8. 审核、退款、解绑、换绑等操作保留不可篡改审计日志。
9. 群二维码和活码失效时，后台及时下线并切换备用群。
10. 对恶意刷活动、批量注册、重复中奖、截图篡改设置风险标记和人工复核。

## 12. 埋点与指标

### 12.1 核心埋点

- `activity_exposure`
- `activity_visit`
- `activity_cta_view`
- `activity_cta_click`
- `order_qualification_view`
- `group_join_guide_view`
- `group_join_guide_click`
- `group_membership_verified`
- `kf_entry_click`
- `bind_token_created`
- `identity_bind_success`
- `redemption_submit`
- `redemption_review_result`
- `refund_success`
- `refund_failure`

### 12.2 核心指标

| 指标 | 口径 |
|---|---|
| 活动页到达率 | 活动入口点击后成功打开活动页的用户数 / 入口点击数 |
| 活动 CTA 点击率 | 点击主 CTA 用户数 / 活动页 UV |
| 下单转化率 | 活动后产生符合条件订单用户数 / 活动页 UV |
| 入群转化率 | 成功加入群池用户数 / 入群引导用户数 |
| 重复入群率 | 已在群池仍被重复引导或重复加入的比例 |
| 兑奖提交率 | 中奖用户提交兑奖材料的比例 |
| 审核通过率 | 审核通过记录 / 完成审核记录 |
| 自动退款成功率 | 自动退款成功记录 / 进入退款处理记录 |
| 退款时效 | 从提交审核到退款成功的中位时长 |
| 退群/屏蔽率 | 活动或运营消息后退群、屏蔽行为比例 |

活动分析至少支持按 `activityId`、`source`、校区、时间、群池拆分。

## 13. V1 / V2 范围

### 13.1 V1 必做

1. 通用小程序原生活动页。
2. `activityId + source` 活动入口和归因记录。
3. 活动后台配置、发布和下线。
4. Activity → GroupPool → Group 数据模型。
5. 用户下单资格查询。
6. 当前有效群展示和入群引导。
7. 群内霸王餐开奖，中奖后人工客服承接。
8. 兑奖记录、订单/截图上传、人工审核。
9. 审核通过后的自动退款。
10. 基础风控、幂等和审计日志。
11. `fhl_user_id` 主身份和基础 Identity 模型。

### 13.2 V1 可降级项

- 如果暂时无法准确同步企微群成员状态，活动页展示通用“查看/加入福利群”入口。
- 如果微信客服自动识别尚未接通，中奖用户可由客服人工查询和创建兑奖记录。
- 如果退款通道尚未具备自动化条件，可先由审核人员触发财务退款，并保留同一退款状态模型。

### 13.3 V2 规划

1. 小程序与企微客户、微信客服身份的完整自动绑定。
2. 精确的 GroupPool 成员状态同步和“已在群”判断。
3. 微信客服自动识别活动、用户、订单和历史兑奖记录。
4. 客服侧自动收集订单号、截图并引导补充材料。
5. 订单候选列表和自动资格校验。
6. 截图 OCR、反作弊模型和风险分层审核。
7. 多群自动分流、容量预测和智能切群。
8. 活动模板、A/B 测试和自动化运营编排。
9. 会员、优惠券、售后等场景复用统一身份中心。

## 14. 验收标准

### 活动入口与页面

- 不同活动可通过不同小程序码/链接打开同一套活动页，并正确识别 `activityId`。
- `source` 能被记录并在后台按来源查询。
- 活动未开始、进行中、已结束状态展示正确。
- 页面能根据用户是否有符合条件的订单展示不同 CTA。
- 活动失效、群失效、接口异常时有明确兜底文案，不出现死链。

### 群池

- Activity 不保存具体群链接，只关联 GroupPool。
- 切换当前承接群后，历史活动无需修改即可指向新群。
- 已知用户已在群池时，不重复引导加入同一群池。
- 群满员或失效时不会继续展示不可用入口。

### 身份与客服

- 参加活动不要求用户提前进入微信客服或绑定客服身份。
- 客服首次兑奖时可生成一次性绑定令牌。
- 令牌过期、重复使用、篡改时均绑定失败且有可解释提示。
- 绑定成功后，客服身份可查询对应 `fhl_user_id` 的活动、订单和兑奖信息。
- 不允许通过前端传入的客服外部 ID 直接完成绑定。

### 兑奖与退款

- 用户可提交订单信息和中奖截图。
- 审核人员可查看材料、通过或驳回，并填写原因。
- 审核通过后系统只创建一次退款任务。
- 退款成功、失败和重试状态可查询，失败可转人工处理。
- 同一中奖资格无法重复退款。

### 数据与运营

- 运营可创建、复制、发布、下线活动。
- 运营可管理群池和当前承接群。
- 核心埋点能形成从活动访问到下单、入群、兑奖、退款的链路。
- 所有关键管理操作有操作人和时间记录。

## 15. 待确认事项

以下事项不影响整体架构，但在开发前需要确认：

1. 订单资格的具体规则：按校区、门店、时间窗口、商品范围还是订单金额判断。
2. 企业微信群入口采用群二维码、群活码还是其他企微能力。
3. V1 是否能获取可靠的群成员状态；若不能，采用降级展示策略。
4. 退款渠道及其幂等、回调和失败重试能力。
5. 中奖截图的存储周期、访问权限和合规要求。
6. 微信客服消息能力、客服账号归属及小程序卡片跳转配置。
7. 活动是否允许跨校区参与，以及用户默认校区的确定方式。
8. 霸王餐红包中奖结果由人工录入、群机器人同步，还是由第三方红包系统回传。

## 16. 结论

饭火轮活动系统采用“活动短期化、群池长期化、客服服务化、身份统一化”的设计：

```text
活动入口 → 饭火轮小程序活动页
活动资格 → 饭火轮订单系统
长期触达 → 校区福利群池
群内开奖 → 霸王餐红包
中奖兑奖 → 微信客服
用户主身份 → fhl_user_id
```

该方案降低活动参与门槛，避免每个活动重复建群，也为后续客服自动化、订单识别和统一会员体系保留扩展空间。
