## Problem / Need

当前商品展示主要依赖固定排序、分类和销量，无法充分利用用户的历史下单偏好、当前用餐场景和近期行为。

用户在商品较多时难以快速找到适合自己的商品，商家也缺少提升复购、发现新品和合理分发促销商品的能力。

需要建设轻量级的个性化推荐能力，使系统能够：

- 结合用户历史订单和行为，理解用户长期及近期偏好；
- 根据时间、店铺、场景和预算推荐更合适的商品；
- 兼顾复购商品、热门商品和新商品，避免推荐内容过于单一；
- 对新用户和新商品提供可用的推荐结果；
- 记录推荐曝光、点击和下单反馈，持续改善推荐效果。

## Context

- 推荐范围以当前用户可购买的商品为准，不应推荐无库存、已下架、商家未营业或无法配送的商品。
- 用户的购买行为比单次浏览或曝光更能代表长期偏好；近期行为应对当前推荐产生更大影响。
- 推荐结果需要能够说明推荐原因，并避免在短时间内重复展示同一商品。
- 推荐系统不应改变商品价格、库存、营业状态、配送范围或优惠适用规则。

## Proposed Solution Direction

采用“SQL 候选召回 + LLM 离线画像/标签/重排 + 在线确定性排序”的轻量方案，不在本地训练协同过滤、矩阵分解或深度学习推荐模型。LLM 不参与实时推荐请求。

### 推荐链路职责划分

推荐链路明确拆分为四个阶段：

```text
候选召回 → 离线初排 → 离线 LLM 重排 → 在线业务过滤
```

| 阶段 | 职责 | 个性化 | LLM | 结果规模 |
|---|---|---:|---:|---:|
| 候选召回 | 从全局热门、站点/店铺、时段、新品和促销等来源找商品 | 否 | 否 | 100–500 |
| 离线初排 | 使用确定性规则按用户偏好和业务信号缩小范围 | 是 | 否 | 30–50 |
| 离线 LLM 重排 | 进行语义匹配、多样性组合、推荐角色和理由生成 | 是 | 是 | 10–20 |
| 在线业务过滤 | 过滤实时不可售、无库存、未营业和不可配送商品 | 是 | 否 | 最终结果 |

候选召回阶段只负责基于公共业务条件尽量不漏掉潜在商品，不使用用户个人历史、偏好或价格习惯进行个性化筛选，也不追求最终排序准确性。离线初排由 SQL/Java 完成，再结合用户画像和场景信号从 100–500 个候选缩小到 30–50 个。

离线 LLM 重排只接收初排后的少量候选，输出 10–20 个预生成结果。在线请求不调用 LLM，只读取用户和场景对应的离线推荐列表并执行业务过滤；结果不足时使用热门、复购和规则排序补充。

### 用户画像分层与 ROI

不为所有用户持续维护完整的 LLM 画像。针对长尾用户，画像维护成本可能高于个性化收益，采用分层策略：

| 用户层级 | 判断 | 推荐方式 |
|---|---|---|
| 新用户 | 无订单或只有少量行为 | 冷启动、站点热门、当前时段和群体推荐 |
| 普通用户 | 有少量订单但活跃度较低 | SQL 轻量统计和群体画像 |
| 活跃用户 | 近期持续下单或有明显复购 | 维护轻量个性化画像 |
| 高价值/高潜用户 | 频繁下单、复购明显、客单价较高或近期行为密集 | LLM 离线完整画像和个性化重排 |

所有用户都保留低成本的 SQL 统计特征，例如最近订单数、最近下单时间、常购品类、常用价格区间、常用时段和最近购买商品。只有达到活跃或高潜阈值的用户，才生成和持续更新完整 LLM 画像。

用户可以在不同层级之间晋级或降级：新增若干订单、画像过期或行为明显变化时更新；连续 60–90 天没有有效行为时降级为轻量统计或群体推荐。用户价值不能只按消费金额判断，还应考虑活跃度、复购倾向和潜在增长空间。

### 商品候选规模

这里需要区分全局商品语义库和推荐请求候选集。商品语义库是全局的，用于商品标签、相似度和后续候选召回；推荐候选集则是按站点、时段和公共业务条件临时/离线生成的子集，用户个性化在候选召回之后处理。

商品语义库不建议用固定数量硬截断，而是按商品有效订单和可用状态建立：

- 至少产生过 1 个有效支付订单的商品，才进入基础语义标签库；
- 至少被 3 个不同用户购买，或至少产生 5 个有效订单的商品，才进入稳定相似度计算库；
- 已下架、删除、无有效商品信息或只有取消/退款订单的商品不进入主库；
- 新商品可以单独进入“新品探索库”，但不能作为有购买行为的相似度证据。

初始规模以覆盖最近 90–180 天有效订单商品的 80%–90% 为目标，而不是简单指定一个总数。商品量较小的站点可以全部纳入；如果商品量较大，再按站点、品类和销量分层保留，建议 MVP 先控制在每个站点约 500–2,000 个有效商品，后续根据覆盖率和离线任务耗时调整。

商品规模应按不同阶段控制，而不是设置一个“所有商品都交给 LLM”的候选库：

| 阶段 | 建议规模 | 说明 |
|---|---:|---|
| 推荐全局候选池 | 每站点/时段 200–500 | 从商品语义库中按热门、新品、促销和可售状态生成的公共推荐候选；它不是商品语义库本身 |
| 推荐候选集 | 100–300 | 从全局候选池按站点、时段、可售状态和业务条件合并去重，不叠加用户个性化条件 |
| 离线初排集 | 30–50 | SQL/Java 确定性规则排序后交给 LLM |
| 离线 LLM 重排集 | 10–20 | 生成用户和场景对应的预排序推荐列表 |

候选规模不是固定常量，应根据商品总量、站点数量、用户数量、LLM 成本和离线任务时长通过实验调整。MVP 可先采用“全局池 300、推荐候选 150、初排 40、重排 10”的默认配置。

总体流程：

```text
订单/行为数据
    ↓
LLM 离线提取用户偏好
    ↓
结构化用户画像
    ↓
SQL 生成不带用户个性化的小规模候选集
    ↓
LLM 离线对候选商品重排并生成推荐列表
    ↓
在线读取推荐结果并执行确定性业务规则过滤与排序
    ↓
推荐结果及推荐理由
```

### 离线用户画像

周期性汇总用户近期订单和行为，交给 LLM 生成结构化画像，至少包含：

- 偏好品类、口味、食材及其权重；
- 价格区间和常用价格；
- 用餐时间偏好；
- 正向偏好、负向偏好和行为摘要；
- 画像置信度、覆盖订单数和更新时间。

画像不在每次请求时重新生成。用户完成若干新订单、画像过期、近期行为明显变化或主动修改偏好时再更新。输出必须使用结构化 JSON/Schema，并经过服务端校验后保存。

### 商品与用户标准归一化

推荐不能直接依赖商家不规范的商品名称、描述和用户原始行为。需要建立商品与用户共用的标准分类库，将商品信息和用户偏好映射到同一套可比较的标准标签中。

分类库至少覆盖：

- 品类和多级子品类；
- 食材及食材组合；
- 口味、风味和忌口属性；
- 份量、规格和价格区间；
- 用餐时段、消费场景和饮食属性；
- 同义词、别名、商家自定义名称及其标准映射关系。

对新增或变更商品进行归一化，形成标准品类、食材、口味、份量、场景和饮食属性等标签，并保留标签来源和质量置信度。一个商品可以对应多个品类、食材或口味标签，不能因为单一主标签丢失重要信息。

用户的购买、点击、收藏、加购和负反馈等行为，也应映射到同一分类库，沉淀为标准化的正向偏好、负向偏好、偏好权重和置信度。用户画像应优先引用标准标签，同时保留原始商品和行为记录，便于分类库调整后重新归一化。

分类库需要支持新增、合并、拆分和停用分类，并明确生效版本。商品语义信息和用户标准偏好与原始业务数据分开维护，原始商品名称、价格和可售状态仍以业务系统为准。

### SQL 候选召回

LLM 不直接读取完整商品目录。后端先通过确定性公共条件过滤并召回约 30–100 个候选商品，候选来源包括：

- 站点/店铺近期热门商品；
- 当前时段和公共消费场景适配的商品；
- 新上架商品和促销商品；
- 其他满足公共业务条件的可推荐商品。

候选集不得使用用户个人历史、偏好或价格习惯进行个性化筛选，并且必须先满足库存、上架、商家营业、配送范围、租户和站点等业务条件，再进入离线初排。

### LLM 离线候选重排

离线任务将用户画像、商品语义信息、时间段/站点等场景、候选商品、近期曝光记录和业务约束提交给 LLM，预先生成用户在不同场景下的推荐列表。要求其：

- 只能从候选商品 ID 中选择；
- 返回结构化排序结果、相对评分、推荐类型和理由码；
- 最多返回限定数量的商品；
- 同时考虑偏好匹配、当前场景、价格、热门程度和探索性；
- 控制同一店铺、品类和近期重复曝光。

LLM 分数只作为离线排序信号，不视为概率。在线请求只读取预生成结果，并重新校验商品 ID、可售状态、库存、营业状态、配送范围和促销规则。

建议在离线阶段保留确定性排序信号，例如热门度、商家质量、新鲜度和促销匹配度，与 LLM 排序信号组合。LLM 不得决定价格、库存、配送资格、营业状态或优惠是否适用。

### 冷启动与多样性

- 新用户：使用当前搜索词、点击行为、当前时间、站点热门商品，或让用户选择少量品类、口味和预算偏好。
- 新商品：使用商品语义信息参与候选召回和排序，不等待历史销量积累。
- 推荐角色：区分复购商品、安全选择、相似替代、新品发现、当前热门和促销匹配。
- 多样性：限制同一店铺/品类数量，避免短期重复曝光，并保留熟悉商品与探索商品的组合。

### 反馈闭环

记录推荐曝光、位置、来源、理由码、点击、收藏、加购和下单结果，按以下优先级更新用户画像：

```text
购买 > 加购 > 收藏 > 点击 > 曝光
```

一次忽略不能直接消除长期偏好；近期购买应比历史购买具有更高权重。推荐结果可缓存一段时间，画像或上下文发生明显变化时重新生成。

### 分阶段落地

1. **第一阶段：离线 SQL + LLM，在线读取结果**
   - 用户订单画像；
   - 商品语义标准化；
   - SQL 候选召回；
   - 离线生成候选推荐列表并重排；
   - 将结果写入缓存或数据库；
   - 在线只读取结果并执行业务过滤。
2. **第二阶段：行为反馈**
   - 接入曝光、点击、收藏、加购、购买和负反馈；
   - 优化画像更新和重复曝光控制。
3. **第三阶段：托管 Embedding（可选）**
   - 商品目录和流量扩大后，引入远程 Embedding 做语义召回；
   - 仍保留 SQL 和业务规则作为确定性过滤层。

离线任务异常或 LLM 不可用时，继续使用上一版推荐结果；如果没有可用结果，在线降级为热门、复购和规则排序。实时请求不调用 LLM，不影响商品浏览和下单时效。

## Acceptance Criteria

- [ ] 已有订单记录的用户能够获得符合其品类、口味、食材和价格偏好的商品推荐。
- [ ] 推荐结果结合当前时间、用餐场景和可购买范围进行调整。
- [ ] 推荐结果同时覆盖复购、相似替代、热门发现和促销匹配等不同类型。
- [ ] 新用户没有历史订单时，仍能根据当前场景、热门商品或主动选择的偏好获得推荐。
- [ ] 新上架商品在缺少历史销量时，也能基于商品信息参与推荐。
- [ ] 商品能够映射到统一的品类、食材、口味、规格、场景和饮食属性分类库，并支持同义词和商家自定义名称归一化。
- [ ] 用户的购买、点击、收藏、加购和负反馈能够映射到同一分类库，形成可用于推荐的标准化正负偏好及权重。
- [ ] 推荐结果不包含下架、无库存、未营业或不可配送的商品。
- [ ] 推荐结果限制同一商家、同一品类和近期重复曝光，保持一定多样性。
- [ ] 用户能够看到简短、可信的推荐理由。
- [ ] 系统能够记录推荐曝光、点击、收藏、加购和下单等反馈，用于后续优化。
- [ ] 推荐能力异常或超时不影响正常商品浏览和下单流程。
- [ ] 普通长尾用户不依赖 LLM 实时调用，也能通过轻量统计、群体画像或冷启动策略获得推荐。
- [ ] 活跃和高潜用户能够按策略生成和更新完整离线画像。
- [ ] 候选召回、离线初排和 LLM 重排的规模与职责明确，在线不调用 LLM。
