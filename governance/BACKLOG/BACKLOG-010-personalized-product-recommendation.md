## Problem / Need

当前商品展示主要依赖固定排序、分类和销量，无法充分利用用户的历史下单偏好、当前用餐场景和近期行为。

用户在商品较多时难以快速找到适合自己的商品，商家也缺少提升复购、发现新品和合理分发促销商品的能力。

需要建设轻量级的个性化推荐能力，使系统能够：

- 结合用户历史订单和行为，理解用户长期及近期偏好；
- 根据时间、店铺、场景和预算推荐更合适的商品；
- 兼顾复购商品、热门商品和新商品，避免推荐内容过于单一；
- 对新用户和新商品提供可用的推荐结果；
- 记录推荐曝光、点击和下单反馈，持续改善推荐效果。

## Context

- 推荐范围以当前用户可购买的商品为准，不应推荐无库存、已下架、商家未营业或无法配送的商品。
- 用户的购买行为比单次浏览或曝光更能代表长期偏好；近期行为应对当前推荐产生更大影响。
- 推荐结果需要能够说明推荐原因，并避免在短时间内重复展示同一商品。
- 推荐系统不应改变商品价格、库存、营业状态、配送范围或优惠适用规则。

## Proposed Solution Direction

采用“SQL 商品池 + LLM 商品特征/用户画像 + 确定性初筛 + LLM 离线匹配评分/SQL 排序 + Redis 在线读取”的 MVP 方案。不在本地训练推荐模型，实时推荐不调用 LLM。

总体流程：

```text
商品基本信息
    ↓
LLM 提取商品特征
    ↓
商品 JSON

近一个月有效订单超过 3 单的用户
    ↓
提取最近订单和商品信息
    ↓
LLM 提取用户偏好
    ↓
用户 JSON

商品池 500 个 + 用户 JSON
    ↓
确定性特征匹配，取前 50 个
    ↓
一次 LLM 离线匹配评分，SQL 排序取前 30 个
    ↓
写入 Redis
    ↓
实时校验可售状态、过滤并按顺序返回
```

推荐链路不应把“候选召回、初排和 LLM 重排”混成一个步骤，建议明确拆成：

```text
候选召回 → 离线初排 → 离线 LLM 重排 → 在线业务过滤
```

| 阶段 | 主要职责 | 是否个性化 | 是否使用 LLM | 结果规模 |
|---|---|---:|---:|---:|
| 候选召回 | 从热门、复购、偏好品类、价格、新品和促销等来源找到潜在商品 | 部分 | 否 | 100–500 |
| 离线初排 | 用 SQL/Java 的确定性规则缩小候选范围 | 是 | 否 | 30–50 |
| 离线 LLM 评分 + SQL 排序 | 对候选商品各维度匹配度和置信度评分，再由 SQL 计算总分并排序 | 是 | 是 | 50→30 |
| 在线业务过滤 | 处理库存、上架、营业、配送和促销等实时条件 | 是 | 否 | 最终结果 |

### 1. 商品库基本信息准备

以商圈为范围，通过 SQL 筛选商品主池：

- 商品在当前商圈可售；
- 月销量大于 10；
- 实际单点价格在 8–30 元；
- 商品支持单点购买；
- 每家店最多保留 5 个商品；
- 按月销量降序选择 500 个商品。

同时增加新品商品池。新品规则为：

```text
上架时间距当前时间 < 7 天 且 月销量 < 10
```

新品仍需满足当前商圈可售、实际单点价格在 8–30 元、支持单点购买等条件；每家店最多保留 2 个新品。新品商品单独标记为新品来源，不与主商品池的“月销量大于 10”规则混用。

月销量只统计有效支付订单，取消、关闭和退款订单不计入。价格需要明确按商品基础单价还是当前最低可购买价格计算；推荐使用用户实际可购买的单点价格，并保留原始价格。

每个商圈的商品主池应保留以下基本信息：

- `product_id`、`shop_id`、`tenant_id`、`business_area_id`；
- 商品名称、描述和图片；
- 实际单点价格、价格区间、规格信息；
- 上架时间、月销量、折扣状态；
- 店铺评分和商品评分；
- 当前上架状态、库存状态和可配送范围。

“每店最多 5 个”用于控制店铺集中度；如果全局销量排序导致店铺或品类过度集中，应在 SQL 选取时同步控制店铺和品类分布。

主池之外单独保留新品探索池，作为主商品池的补充来源，避免新商品永远无法进入推荐。

### 2. 商品特征提取

使用 LLM 对商品主池和新品探索池中的商品提取标准特征，参考《商品推荐标准分类库参考》3.1：

- `standard_category`：标准类目；
- `standard_ingredients`：核心食材组，可多选并区分主食材；
- `taste_profile`：口味风味，可多选；
- `price_range`：标准价格区间；
- `consumption_scene`：消费场景，可多选。

商品名称、描述和商家原始属性保留在业务信息中，不能被 LLM 生成的标准特征覆盖。食材、过敏原等无法从商品信息确认时，应标记为 `unknown` 并保留置信度，不得仅凭名称强行推断。

商品特征按商品内容版本缓存。只有新商品、商品名称或描述变更、分类库版本变更时才重新调用 LLM。LLM 输出必须使用 JSON Schema，并校验标准分类值、数组类型和置信度范围。

### 3. 组装商品 JSON

商品 JSON 同时包含业务属性和算法评估属性。原始业务字段保持原名；由 LLM 或其他算法评估、归一化的字段统一增加 `e_` 字母前缀，`e` 代表 `eval`，用于区分原始业务数据和算法结果。

算法评估字段包括：

- `e_standard_category`；
- `e_standard_ingredients`；
- `e_taste_profile`；
- `e_price_range`；
- `e_consumption_scene`；
- `e_feature_confidence`；
- `e_feature_version`。

示例：

```json
{
  "product_id": 10023,
  "tenant_id": 153,
  "business_area_id": 12,
  "shop_id": 301,
  "product_name": "超大杯冰霸芒果芝芝",
  "product_description": "冰饮芒果茶搭配芝士奶盖",
  "single_price": 18.0,
  "listed_at": "2026-08-01T10:00:00+08:00",
  "monthly_sales": 1280,
  "is_discounted": true,
  "shop_rating": 4.8,
  "product_rating": 4.7,
  "e_standard_category": "drinks",
  "e_standard_ingredients": [
    "fruit",
    "egg_dairy",
    "tea_coffee_beverage_base"
  ],
  "e_taste_profile": [
    "sweet_aroma",
    "fruity_tea_coffee",
    "creamy_cheesy"
  ],
  "e_price_range": "15_20",
  "e_consumption_scene": ["afternoon_tea", "office_meal"],
  "e_feature_confidence": 0.92,
  "e_feature_version": "taxonomy-v1"
}
```

后续匹配规则中的 `standard_category`、`standard_ingredients`、`taste_profile`、`price_range` 和 `consumption_scene` 表示逻辑维度；从商品 JSON 取值时对应使用带 `e_` 前缀的字段。

### 4. 用户信息提取

筛选近一个月有效支付订单数量大于 3 单的用户。用户订单范围应限定在当前租户和可推荐业务范围内，退款或取消订单不计入。

对符合条件的用户：

- 提取最近 3 个有效订单的商品明细和订单信息；
- 同时汇总近一个月全部有效订单的订单数、商品购买次数、常购类目、价格区间和消费时段；
- 订单信息至少包含下单时间、商品、单价、数量、店铺和可识别的消费场景；
- 近期 3 单权重高于更早订单；
- 不向 LLM 发送手机号、地址等无关个人信息。

不能只使用最近 3 单，否则同一批次购买可能过度代表用户偏好。最近 3 单用于表达近期兴趣，近一个月汇总用于表达稳定偏好。

### 5. 补全用户 JSON

使用 LLM 根据订单和商品 JSON 提取用户偏好，参考《商品推荐标准分类库参考》3.1；用户自身属性参考该文档 3.3。

用户 JSON 至少包含：

- 用户标识、租户、商圈和画像更新时间；
- 近一个月订单数、总订单数等统计属性；
- 标准类目、核心食材组、口味风味、价格区间和消费场景偏好；
- 正向偏好、负向偏好、近期偏好和长期偏好；
- 每个维度的权重和置信度；
- 覆盖订单数、画像版本和更新时间。

画像示例：

```json
{
  "user_id": 90001,
  "tenant_id": 153,
  "business_area_id": 12,
  "monthly_order_count": 8,
  "preferred_attributes": {
    "standard_category": [
      {"value": "drinks", "weight": 0.86, "confidence": 0.90}
    ],
    "standard_ingredients": [
      {"value": "fruit", "weight": 0.80, "confidence": 0.82}
    ],
    "taste_profile": [
      {"value": "sweet_aroma", "weight": 0.72, "confidence": 0.75}
    ],
    "price_range": [
      {"value": "15_20", "weight": 0.66, "confidence": 0.80}
    ],
    "consumption_scene": [
      {"value": "afternoon_tea", "weight": 0.78, "confidence": 0.72}
    ]
  },
  "negative_preferences": [],
  "recent_summary": "近期偏好水果茶饮，常在下午消费，价格集中在 15–20 元。",
  "profile_confidence": 0.83,
  "profile_version": "profile-v1"
}
```

LLM 不得根据性别等用户字段推断口味。无法确认的偏好保留未知状态，不作为强负向偏好。输出需要经过 JSON Schema、用户标识、分类值和置信度校验后保存。

没有达到近一个月 3 单以上的用户不进入本次个性化画像流程，统一使用商圈热门、时段热门、新品和规则排序结果；不能因为没有画像而没有推荐结果。

### 6. 确定性初筛：500 个商品取 50 个

将商圈商品主池中的 500 个商品与用户特征进行确定性匹配，不调用 LLM。先过滤不满足推荐范围的硬条件，再按标准属性计算匹配分。

硬条件包括商品属于当前租户和商圈、支持单点、价格处于商品池范围内，以及商品在生成时具备基本可售条件。库存、店铺营业、配送范围等易变化条件必须在实时阶段再次校验。

对于文档 3.1 的每个匹配维度，使用以下基础公式：

```text
总分 = Σ（维度权重 × 匹配度 × 商品特征置信度 × 用户偏好置信度）
```

其中：

- 维度包括标准类目、核心食材组、口味风味、价格区间和消费场景；
- 维度权重总和应为 1，并且需要版本化；
- `匹配度` 为 0–1，支持多标签部分匹配，不能只判断完全相等；
- `unknown` 不应直接视为不匹配；
- 用户负向偏好可作为排除条件或扣分项；
- 分数相同时，使用销量、新鲜度、店铺质量和店铺/品类多样性进行确定性排序。

按总分降序取前 50 个商品。若有效商品不足 500 个，应使用新品探索池、热门池或其他满足业务条件的商品补足，而不是降低在售和单点等硬条件。

### 7. LLM 离线匹配评分 + SQL 排序：50 个商品取 30 个

LLM 的调用粒度为“一个用户 + 一个商圈 + 一个消费场景”一次调用，不是每个商品调用一次 LLM。LLM 不直接返回最终排序，而是对 50 个候选商品的五个标准维度分别进行匹配度评分，并返回每个维度的 `confidence`：

```text
50 个候选商品 → 一次 LLM 请求评分 → SQL 计算总分并排序 → 取前 30 个商品
```

LLM 输入包括用户 JSON、50 个商品 JSON、当前商圈、消费场景和近期推荐曝光记录。评分维度与《商品推荐标准分类库参考》3.1 保持一致：

- `standard_category`：标准类目；
- `standard_ingredients`：核心食材组，可多选并区分主食材；
- `taste_profile`：口味风味，可多选；
- `price_range`：标准价格区间；
- `consumption_scene`：消费场景，可多选。

每个商品的 LLM 输出至少包含：

- 商品 ID；
- 每个维度的匹配度，范围为 0–1；
- 每个维度的 `confidence`，范围为 0–1；
- 可选的推荐类型、理由码和简短推荐理由；
- 使用结构化 JSON Schema 输出。

示例：

```json
{
  "product_id": 10023,
  "dimension_scores": {
    "standard_category": {"score": 0.92, "confidence": 0.95},
    "standard_ingredients": {"score": 0.88, "confidence": 0.90},
    "taste_profile": {"score": 0.76, "confidence": 0.82},
    "price_range": {"score": 0.80, "confidence": 0.96},
    "consumption_scene": {"score": 0.84, "confidence": 0.78}
  },
  "reason_codes": ["CATEGORY_MATCH", "PRICE_MATCH"],
  "reason": "商品类目和价格符合用户偏好，适合当前消费场景。"
}
```

SQL 根据 LLM 返回的各维度 `score`、`confidence` 和已配置的维度权重计算最终分数并排序：

```text
最终分数 = Σ（维度权重 × 匹配度 × confidence）
```

SQL 按最终分数降序取前 30 个商品；分数相同时，再按销量、新鲜度、店铺质量和多样性规则排序。LLM 不负责判断库存、店铺营业、配送范围、价格有效性或优惠适用性，这些由实时业务规则处理。LLM 返回的分数不是购买概率。

### 8. 写入 Redis

每个用户的推荐列表写入 Redis。推荐结果只保存商品 ID、顺序和推荐理由等结果信息，不保存会过期的库存和价格快照。

Redis key 至少应包含：

```text
tenant_id + business_area_id + user_id + scene + profile_version
```

列表内容至少包含：

- 商品 ID 和推荐顺序；
- 推荐类型、理由码和推荐理由；
- 生成时间、商品池版本、用户画像版本和分类库版本；
- 过期时间。

写入应采用完整列表原子替换，避免在线读取到半成品。Redis 无数据或数据过期时，降级为商圈热门、复购商品、新品和确定性规则排序。

### 9. 实时推荐与业务过滤

在线请求不调用 LLM，只读取 Redis 推荐列表并按原有顺序处理。返回前重新校验：

- 商品未删除、未下架且库存充足；
- 店铺当前营业；
- 商品价格和可购买规格有效；
- 商品属于当前租户、商圈并支持当前配送范围；
- 当前购买限制、促销适用条件等业务规则仍然满足。

过滤后不足 30 个商品时，按顺序从剩余候选、商圈热门、复购商品、新品探索池和规则排序结果中补充。实时推荐不应因为推荐服务异常、超时或 Redis 不可用而阻断商品浏览和下单。

### 10. 推荐反馈

记录推荐曝光、点击、收藏、加购、下单和负反馈，至少关联用户、请求、商品、位置、来源、理由码和发生时间。反馈用于后续画像和推荐优化，行为权重遵循：

```text
购买 > 加购 > 收藏 > 点击 > 曝光
```

一次忽略不能直接删除长期偏好；近期购买应比历史购买具有更高权重。推荐列表需要控制短期重复曝光，用户购买后可以重新允许相关商品进入复购推荐。

### 运行与更新

- 商品特征按商品内容版本增量更新；
- 用户画像按有效订单、画像过期或近期行为明显变化触发更新；
- 商品池、用户画像和推荐列表需要有版本号；
- LLM 失败时继续使用上一版商品特征、用户画像或推荐列表；
- 没有上一版结果时降级为热门、复购、新品和规则推荐；
- 所有离线任务应支持重复执行，不因任务重试产生重复或半成品推荐列表。

## Acceptance Criteria

- [ ] `Problem / Need` 中描述的问题和业务目标得到覆盖。
- [ ] 每个商圈能够通过 SQL 生成不超过 500 个商品的主商品池，每家店不超过 5 个商品，且满足月销量、价格和单点条件。
- [ ] 新品探索池能够筛选出上架时间距当前时间小于 7 天且月销量小于 10 的商品，每家店最多 2 个，并参与推荐。
- [ ] 商品能够按照分类库 3.1 生成标准类目、核心食材组、口味风味、价格区间和消费场景，并保留置信度和版本。
- [ ] 近一个月有效订单超过 3 单的用户能够提取最近 3 单详情和近一个月汇总信息，生成结构化用户 JSON。
- [ ] 用户特征和商品特征使用可配置、版本化的维度权重进行确定性匹配，500 个候选能够筛选出前 50 个商品。
- [ ] 每个用户、商圈和场景只需一次 LLM 评分请求，对 50 个商品的五个标准维度返回匹配度和 `confidence`，再由 SQL 排序取前 30 个商品。
- [ ] LLM 只能处理候选商品 ID，并能够返回结构化维度评分、`confidence`、推荐类型、理由码和推荐理由。
- [ ] 推荐列表能够带版本写入 Redis，并支持过期、原子替换和无数据降级。
- [ ] 实时推荐能够过滤删除、下架、售罄、店铺未营业、不可配送和其他实时不可购买商品。
- [ ] 实时过滤后不足 30 个商品时能够使用备用候选补充，并保持顺序。
- [ ] 新用户和订单不足的用户能够通过热门、新品和规则排序获得推荐。
- [ ] 系统能够记录曝光、点击、收藏、加购、下单和负反馈，并用于后续优化。
- [ ] 推荐流程异常、超时或缓存不可用时不影响商品浏览和下单。
