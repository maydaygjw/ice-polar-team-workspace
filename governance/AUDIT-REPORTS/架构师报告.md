## 二、架构蓝图 vs 现实差距

### 2.1 理想架构

```
[WeChat MiniApp]     [Admin Dashboard]
       ↓                    ↓
  [app-api/]          [admin-api/]
       ↓                    ↓
   [yshop-drink Backend] ←→ [Redis/MQ]
       ↓
  [icepolar-dms] ←── 仅 backend device 模块调用
```

### 2.2 现实偏差

```
[WeChat MiniApp] ──────→ [DMS] ❌ 直接绕过 backend
       ↓
  [app-api/] ←── 部分请求无 tenant 校验
       ↓
   [yshop-drink Backend] ←── 模块间 DAO 直接引用（非 API）
       ↓
  [icepolar-dms] ←── 硬编码弱密码
```

**关键偏差**：
1. MiniApp 直接调用 DMS，架构边界彻底失效
2. 模块间通过 DAO 直接耦合，而非通过 API 模块交互
3. system（基础设施层）反向依赖 store（业务层），分层倒置
4. CONTRACTS.md 严重缺失，API-first 沦为口号

## 三、P0 级问题（架构红线）

### P0-01：MiniApp 直接调用 DMS — 架构边界彻底失效

| 维度 | 详情 |
|------|------|
| 问题 | `miniapp/pages/device-detail/device-detail.js` 直接 `wx.request` 调用 DMS API |
| 位置 | `device-detail.js:67-68`（查询状态）、`:164-165`（下发指令） |
| 违反原则 | `governance/CLAUDE.md` 明确："DMS 仅由 backend device 模块调用，never by frontend" |
| 风险 | 租户隔离失效、权限校验缺失、无审计日志、设备可被未授权操控 |
| 修复 | backend 新增设备代理 API → 小程序全部改调 backend → 删除 `app.globalData.dmsUrl` |

### P0-02：订单状态枚举三套定义不一致 — 数据一致性危机

| 枚举 | STATUS_0 | STATUS_1 | STATUS_2 | STATUS_3 |
|------|----------|----------|----------|----------|
| OrderStatusEnum (order-api) | 未支付 | 待发货 | 待收货 | 待评价 |
| OrderInfoEnum (framework) | 默认 | 待收货 | **已收货** | 已完成 |
| OrderStatusEnum (merchant) | 待出单 | 待收货 | 已完成 | 待退款 |

**风险**：`STATUS_2` 在 order-api 中是"待收货"，在 framework 中是"已收货"——语义完全相反。订单状态由 `paid` + `refund_status` + `status` 三字段共同表达，叠加枚举不一致，状态判断极易出错。

**修复路线**：
1. 短期：冻结枚举变更，禁止新增代码引用 `OrderInfoEnum` 的状态常量
2. 中期：统一为单一定义，逐步迁移存量引用
3. 长期：将三字段状态模型重构为单一状态字段 + 辅助字段

## 四、P1 级问题（架构合规）

### P1-01：模块依赖图 — 大量 DAO 越界引用

**跨模块 DAO 引用统计**（仅列举高频场景）：

```
order-biz  → desk DO, product Mapper, member Mapper, store Mapper
member-biz → store Mapper, shop Mapper, card DO, coupon DO
merchant-biz → order Mapper/DO/VO, product DO, store Mapper
message-biz → member DO, mp Service
system-biz → store Mapper  ❌ 基础设施层依赖业务层
```

**影响**：
- 违反"模块间仅通过 `-api` 交互"的分层原则
- schema 变更产生级联影响
- 无法独立部署和测试模块

**修复策略**：
1. 引入 CI 架构守卫（Maven Enforcer 或 ArchUnit）
2. 分阶段将 DAO 引用替换为 API 调用
3. 优先解耦 `system → store`（分层倒置，最紧急）

### P1-02：CONTRACTS.md 仅覆盖 ~20% 跨仓库契约

| 缺失契约 | 影响方 | 风险 |
|----------|--------|------|
| Device API Contract | backend ↔ miniapp | DMS 直连的根源之一 |
| Order API Contract | backend ↔ miniapp/admin | 状态枚举不一致 |
| Payment API Contract | backend ↔ miniapp | 支付安全问题 |
| Member Auth Contract | backend ↔ miniapp | Token 刷新缺失 |
| DMS API Contract | backend ↔ icepolar-dms | 接口变更不同步 |

### P1-03：icepolar-dms 硬编码弱密码

- `DB_PASSWORD: "dms_password"`
- `SECRET_KEY: "change_this_to_a_random_secret_key"`
- `ADMIN_PASSWORD: "admin123"`

**架构要求**：DMS 作为设备管理核心，必须达到最高安全等级。当前配置在生产环境部署等于"门户洞开"。

### P1-04：@TenantIgnore 在业务代码中缺乏审计

- `UserBillServiceImpl`、`AppStoreOrderServiceImpl` 中的 `@TenantIgnore` 无文档说明
- 缺乏定期审计机制，存在权限扩大的风险

### P1-05：消息模块与 member/mp 模块紧耦合

- `message-biz` 直接 import `MemberUserDO` 和 `MpAccountService`
- 应通过 API 模块解耦，使用 DTO 传递数据
